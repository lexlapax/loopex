## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Give an operator a coding agent they can use from their own terminal. They run
`loopex` inside a Git repository, describe a change in ordinary words, and watch
the session read files, edit them, and run commands until the work is done. The
answer arrives as it is produced rather than after the run. The model sees the
whole conversation — the operator's prompt, its own prior messages, and the real
output of every tool it ran — so the loop runs as many turns as the task needs
instead of stopping after the second. The operator can redirect the run while it
is working, or queue the next piece of work behind it. Host policy can refuse a
call and the operator sees the refusal. Ctrl-C stops the owned work and reports
what actually happened. Tomorrow, `loopex sessions` finds today's work and
`loopex resume` continues it.

M2 is the foreground harness. One operator, one terminal, one process, one
durable session on the local disk. Everything an operator asks for is asked for
in that process and answered in that process.

M1 proved the durability kernel underneath that experience: a session survives
an untrappable kill, reconciles its effect without dispatching it again, and
loses no acknowledged fact. It did not prove a loop. Its loop is hardwired to
two turns, sends the model a synthesized string instead of the conversation,
never streams, and exposes two demonstration tools. This milestone turns that
kernel into a tool a developer actually uses.

The same source and gate execute on Darwin under both ADR 0002 validation pairs
and on Linux under the current pair. That is milestone execution evidence, not
an operating-system support freeze.

<a id="concept-plan-scope"></a>
### Scope

Product code intended to survive the milestone: a real multi-turn agent loop
with committed conversation history, declared bounds, and provider continuation;
streaming progress with exactly one durable reconstruction per turn; the prompt,
steer, and follow-up input algebra; a runtime-scoped tool registry; four
conformance-tested bootstrap coding tools; an artifact store for oversized
output; a host policy port with a working refusal; project-resource discovery
and trust admission; working cancellation; a session directory over a resolved
state root; one shipped composition module; and one operator command
application. All of it runs on the M1 kernel and through the M1 embedded API.

M2 ships a runnable `loopex` command built as an `escript` from the source tree.
That is an operator feature and is independent of any version number. The root
`VERSION` stays `0.0.0`, nothing is tagged, and nothing is published.

**The boundary behaviours M2 leaves in place are Store, Model, and Executor.**
It adds two narrow ones the founding vision already assigns. `Loopex.Policy` is
the host-control seam that replaces M1's literal `{:host_policy, :allow}` term,
and an `ArtifactStore` port owns oversized tool output so the model-facing
result can stay bounded without discarding what a tool produced. Each ships with
the smallest local adapter and a reusable conformance suite. Neither adds an
application. The tool registry is runtime-scoped data and resolution rules
inside core, not a boundary behaviour.

The `loopex` command is a client application and a peer surface: it owns no
loop, no durable session truth, no cursor truth, no Store access, and no
authority decision. Every operator flow it offers is a projection of the same
embedded API an embedder calls.

Darwin floor, Darwin current, and Linux current are three independent execution
lanes. Each runs the complete gate from a fresh owned root. The floor pair is
Elixir 1.17.0 on OTP 26.0, where neither Erlang's `:json` nor Elixir's `JSON`
exists, so every byte of encoding and decoding this milestone needs is
repository-owned code that runs there.

**Accepting this plan pair takes two decisions.** First, a seventh application,
`apps/loopex_cli`, with role `:client`, and a widened client rule: a `:client`
may declare production dependencies on the in-umbrella `:edge` applications it
composes, and still no external dependency and no dependency on another
`:client`. Second, the two new narrow ports named above, each with one local
adapter and one conformance suite, and no other new boundary behaviour.

**Accepting this plan pair does not, and cannot, dispose the M1 gate.** M1's
closed gate binds nine files by digest, and M2 must change two of them:
`apps/loopex/lib/mix/tasks/loopex.deps_budget.ex`, whose planned inventory
freezes the repository at exactly six applications with one `:client`, and
`apps/loopex/test/deps_budget_test.exs`, its adversarial corpus, which must gain
the cases that prove the new inventory and the widened client rule. Those
digests are not enforced only by M1's own runner. The repository status check
verifies every plan's declared bound artifacts against the working tree at every
revision and across the history reachable from `HEAD`, with no exemption for a
`Closed` milestone. The moment either file changes, `mix loopex.status` fails,
`bash scripts/check-bootstrap.sh` fails because it runs that check, and the
closed M0 gate goes red because it runs bootstrap. **Until an accepted M1 gate
amendment rebinds those two artifacts to the M2 bytes, M0, the bootstrap
aggregate, and the status check are red.** That amendment is a non-delegable
baseline exception requiring the maintainer's explicit disposition; this plan
plans it and does not execute it.

M1's protection is otherwise carried forward and re-run, not restarted. The M2
gate re-runs M1's eleven protected outcome roles — including both real-provider
roles — at their exact locked identities, states, and minima beside its own.

<a id="concept-plan-non-goals"></a>
### Non-Goals

**No wire, no daemon, no second client.** The vision's serial barriers put a
line-framed protocol before a reference daemon, and both after a useful local
loop. M2 stays in the foreground. It creates no JSONL RPC transport, no
line-framed protocol, no golden vectors, no socket, no daemon, no controller
lease, and no second-client attachment contract. A headless JSONL session
protocol is the next milestone's whole subject, and a durable multi-client
daemon is the one after it. Introducing either here would freeze a guess about a
surface no proven client has used yet.

**No cross-process cancellation.** Stopping a live run is Ctrl-C in the process
that is running it. A second `loopex` process cannot cancel the first: ADR 0008
permits one live Runtime Control per `(Store identity, runtime_id)` placement
key, the command re-presents one durable `runtime_id`, and M2 has no
out-of-band channel, so a second process is refused by mutual exclusion rather
than reaching the run. `loopex cancel <session>` is therefore narrow and says
so: it reconciles a session whose owning process died, driving it to a truthful
terminal state from durable evidence. Cancelling another process's live run
needs an attached second client and belongs with the daemon.

**No publication.** Nothing is published to Hex, to a binary release channel, or
to any other distribution point, and no version is tagged. Publishing one
package would permanently create the vision's seventh compatibility surface —
released package names, their contents, and the constraints they declare — which
is inert only while nothing is published. It would also require the name,
trademark, domain, and Hex clearance the roadmap keeps as an unscheduled
question. Neither is worth spending to make a local kernel usable, and both stay
available to a later milestone that has a consumer.

**Three of the seven tools wait.** M2 ships the bootstrap profile — `read`,
`write`, `edit`, `bash`. The `coding_search` profile — `grep`, `find`, `ls` — is
explicitly deferred, because the vision itself splits the surface that way and
asks for measured prompt cost and task utility before an accepted decision fixes
a reference default. The four shipped tools carry the shared conformance the
other three will inherit.

**Refusal now, interactive approval later.** Host policy owns `allow`, `deny`,
and `defer`. M2 delivers `allow` and a working `deny`, and documents the
trusted-local `AllowAll` default as a developer default rather than a permission
model. `defer` — interactive per-call approval with a mid-run round trip to the
operator — is explicitly deferred; it needs an interaction contract the
foreground rung has not earned. The project-resource trust decision in Outcome 8
is not a `defer`: it is settled before a run starts, or the run fails closed, so
it introduces no mid-run interaction.

**No context pipeline beyond exact staging.** M2 implements only the initial
local-kernel stage the vision names: canonical history, a fixed reference
project-resource stage, trust admission, total budget enforcement, and exact
receipts. Registered context providers, transformers, selectors, observers,
recall stores, memory, retrieval, embeddings, and prompt libraries are out.

Also out: changing the model within a run, branches and forks, compaction,
extension manifests or activation, isolated or remote hands, an executor broker
or fleet, a durable store selection or migration, a policy engine, sub-agents,
plans, objectives, background jobs, performance budgets, and any public
compatibility freeze. A terminal user interface is out: the command may stay
line-oriented, and only the semantics above are proved.

No checker, registry, document, evidence record, or status row substitutes for
the working loop and the working command. A component that does not serve one of
the thirteen outcomes is out of scope.

## Workstreams

Ownership and the required rejoin order are fixed in the
[technical envelope](M2-technical.md#technical-plan-ownership).

- **A — Tool contract and registry.** `loopex_protocol` and core own the tool
  definition shape and the runtime-scoped registry for Outcome 4. Nothing else
  can name a tool until this exists, so it rejoins first.
- **B — Loop, bounds, streaming, input algebra, and staging.** Core owns
  Outcomes 1, 2, 3, and 8: the turn machine, the canonical history projection,
  exact staging of each turn's request, the three declared bounds, the delta
  algebra and its single durable reconstruction, the prompt/steer/follow-up
  queue, and project-resource staging. It rejoins second.
- **C — Coding tools, artifacts, and host policy.** `loopex_executor_local` and
  `loopex_store_local` own Outcomes 5, 6, and 7 and the executor half of
  cancellation. They implement the registry's contract and rejoin third.
- **D — Cancellation and the session directory.** Core owns Outcomes 9 and 10.
  Cancellation needs C's owned-process termination and B's turn machine, so this
  rejoins fourth.
- **E — Operator surface and demonstration.** `loopex_cli` owns Outcomes 11, 12,
  and 13, the `escript` entrypoint, and the seventh-application inventory
  change. It rejoins last and proves one operator experience through every prior
  workstream.
