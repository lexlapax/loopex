## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Give an operator a coding agent they can use from their own terminal. They run
`loopex` inside a Git repository, describe a change in ordinary words, and watch
the session read files, edit them, and run commands until the work is done. The
model sees the whole conversation — the operator's prompt, its own prior
messages, and the real output of every tool it ran — so the loop runs as many
turns as the task needs instead of stopping after the second. Host policy can
refuse a call and the operator sees the refusal. Stopping the task stops the
owned work and reports what actually happened. Tomorrow, `loopex sessions` finds
today's work and `loopex resume` continues it.

M1 proved the durability kernel underneath that experience: a session survives
an untrappable kill, reconciles its effect without dispatching it again, and
loses no acknowledged fact. It did not prove a loop. Its loop is hardwired to
two turns, sends the model a synthesized string instead of the conversation, and
exposes two demonstration tools. This milestone turns that kernel into a tool a
developer actually uses, and ships it as version `0.1.0` from the source tree.

The same source and gate execute on Darwin under both ADR 0002 validation pairs
and on Linux under the current pair. That is milestone execution evidence, not
an operating-system support freeze.

<a id="concept-plan-scope"></a>
### Scope

Product code intended to survive the milestone: a real multi-turn agent loop
with committed conversation history and provider continuation, a runtime-scoped
tool registry, four conformance-tested bootstrap coding tools, host policy with
a working refusal, working cancellation, a session directory over a resolved
state root, one shipped composition module, and one operator command
application. All of it runs on the M1 kernel and through the M1 embedded API.

The milestone still has exactly three product boundary behaviours: Store, Model,
and Executor. The tool registry is runtime-scoped data and resolution rules
inside core, not a fourth behaviour. The `loopex` command is a client
application and a peer surface: it owns no loop, no durable session truth, no
cursor truth, no Store access, and no authority decision. Every operator flow it
offers is a projection of the same embedded API an embedder calls.

M2 ships version `0.1.0` as a tagged source tree with a runnable `escript`
entrypoint. Nothing is published. Every public surface is labelled
`experimental`: the embedded Elixir API, the `loopex` command surface, the
private journal and store schema, the executor job and receipt protocol, and the
tool contract. An experimental surface may break in a later minor release with
explicit migration notes.

Darwin floor, Darwin current, and Linux current are three independent execution
lanes. Each runs the complete gate from a fresh owned root. The floor pair is
Elixir 1.17.0 on OTP 26.0, where neither Erlang's `:json` nor Elixir's `JSON`
exists, so every byte of encoding and decoding this milestone needs is
repository-owned code that runs there.

M1 code and its locked protected behaviour are carried forward, not restarted.
The M2 gate re-runs M1's eight protected outcome selectors at their exact locked
identities beside its own.

<a id="concept-plan-non-goals"></a>
### Non-Goals

**No publication.** Nothing is published to Hex, to a binary release channel, or
to any other distribution point. `0.1.0` is a tagged source-tree version with a
runnable entrypoint and nothing more. Publishing one package would permanently
create the vision's seventh compatibility surface — released package names,
their contents, and the constraints they declare — which is inert only while
nothing is published. It would also require the name, trademark, domain, and Hex
clearance the roadmap keeps as an unscheduled question. Neither is worth
spending to make a local kernel usable, and both stay available to a later
milestone that has a consumer.

**No second client and no wire.** The vision's serial barriers put multi-client
attachment and a protocol candidate at the rung after durable local truth. M2
stays inside the first rung. It creates no JSONL RPC transport, no line-framed
protocol, no golden vectors, no daemon, no socket, no controller lease, and no
second-client attachment contract. The roadmap projects JSONL RPC alongside this
rung; this plan explicitly defers it to a later milestone rather than carrying
it silently, because a wire contract before one client is proven useful freezes
guesses. The one operator command attaches as M1's single caller does.

**Three of the seven tools wait.** M2 ships the bootstrap profile — `read`,
`write`, `edit`, `bash`. The `coding_search` profile — `grep`, `find`, `ls` — is
explicitly deferred, because the vision itself splits the surface that way and
asks for measured prompt cost and task utility before an accepted decision fixes
a reference default. The four shipped tools carry the shared conformance the
other three will inherit.

**Refusal now, interactive approval later.** Host policy owns `allow`, `deny`,
and `defer`. M2 delivers `allow` and a working `deny`, and documents the
trusted-local `AllowAll` default as a developer default rather than a permission
model. `defer` — interactive per-call approval with a round trip to the operator
— is explicitly deferred; it needs an interaction contract the single-caller
rung has not earned.

**No context pipeline beyond exact staging.** M2 implements only the initial
local-kernel stage the vision names: canonical history, a fixed reference
project-resource stage, trust admission, total budget enforcement, and exact
receipts. Registered context providers, transformers, selectors, observers,
recall stores, memory, retrieval, embeddings, and prompt libraries are out.

Also out: model switching mid-session, branches and forks, compaction, extension
manifests or activation, isolated or remote hands, an executor broker or fleet,
a durable store selection or migration, a policy engine, sub-agents, plans,
objectives, background jobs, performance budgets, and any public compatibility
freeze.

No checker, registry, document, evidence record, or status row substitutes for
the working loop and the working command. A component that does not serve one of
the nine outcomes is out of scope.

## Workstreams

Ownership and the required rejoin order are fixed in the
[technical envelope](M2-technical.md#technical-plan-ownership).

- **A — Tool contract and registry.** `loopex_protocol` and core own the tool
  definition shape and the runtime-scoped registry for Outcome 2. Nothing else
  can name a tool until this exists, so it rejoins first.
- **B — Loop, committed history, and continuation.** Core owns Outcome 1: the
  turn machine, the canonical history projection, exact staging of each turn's
  request, and the provider continuation binding. It rejoins second.
- **C — Coding tools and host policy.** `loopex_executor_local` owns Outcomes 3
  and 4 and the executor half of cancellation. It implements the registry's
  contract and rejoins third.
- **D — Cancellation and the session directory.** Core owns Outcomes 5 and 6.
  Cancellation needs C's owned-process termination and B's turn machine, so this
  rejoins fourth.
- **E — Operator surface and demonstration.** `loopex_cli` owns Outcomes 7, 8,
  and 9, the `escript` entrypoint, and the `0.1.0` version train. It rejoins
  last and proves one operator experience through every prior workstream.
