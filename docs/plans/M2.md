## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Give an operator a coding agent they can use from their own terminal. They run
`loopex` inside a Git repository, describe a change in ordinary words, and watch
the session read files, edit them, and run commands until the work is done. The
answer arrives as it is produced rather than after the run. The model sees the
whole conversation — the operator's prompt, its own prior messages, and the real
output of every tool it ran — so the loop runs as many turns as the task needs
instead of stopping after the second. The operator can redirect the run while it
is working, or queue the next piece of work behind it. Host policy can refuse a
call and the operator sees the refusal. Ctrl-C stops the owned work and reports
what actually happened. Tomorrow, `loopex sessions` finds today's work and
`loopex resume` continues it.

M2 is the foreground harness. One operator, one terminal, one process, one
durable session on the local disk. Everything an operator asks for is asked for
in that process and answered in that process.

M1 proved the durability kernel underneath that experience: a session survives
an untrappable kill, reconciles its effect without dispatching it again, and
loses no acknowledged fact. It did not prove a loop. Its loop is hardwired to
two turns, sends the model a synthesized string instead of the conversation,
never streams, and exposes two demonstration tools. This milestone turns that
kernel into a tool a developer actually uses.

The same source and gate execute on Darwin under both ADR 0002 validation pairs
and on Linux under the current pair. That is milestone execution evidence, not
an operating-system support freeze.

The Gate selector cells identify the protected selector files. The gate contract
locks the complete repository-owned invocation, including role, seed, minimum,
exclusion policy, expected test identities and states, and credential channel.

Three things the gate locks just as hard are deliberately not outcomes. The
runtime-scoped tool registry is the internal mechanism Outcomes 1 and 4 both
resolve through, not something an operator asks for; it is an implementation
constraint with locked supporting coverage. The attended real-provider
demonstration is not a feature either; it is the mandatory closure evidence that
the eleven outcomes above add up to a coding agent, and closure without it is
refused. The third is the governance machinery this milestone's own prerequisite
rides on: M2 cannot be implemented without rebinding a closed gate's artifacts,
and the two corpora that make such a rebinding provable rather than assertable
are locked here so the transaction cannot be performed with the check on it
allowed to rot.

Every claim in this milestone that a real provider answered must leave behind
something a person can check outside this repository. A real provider's reply
carries the provider's own identifier for that response and the token usage the
provider reported; the milestone retains both, per real-provider role, beside
the non-secret provider, model, endpoint, and adapter identity it already keeps,
and a case that claims a real provider answered fails when no such identifier is
present. This is stated here with its limit attached, because the limit is the
point: no check that runs offline can prove a network call happened. What the
mechanism achieves is that fabricating one becomes detectable — the retained
identifiers either exist in the provider's account or they do not — and
confirming them there is a closure-review step performed by a person. No plan,
gate, evidence record, or report in this milestone may describe an automated
check as proving a real call occurred.

The gate has no opinion about which providers exist. The retained record names
the provider and declares the identifier form that provider documents, and the
check validates the recorded identifiers against that declared form rather than
against a list of providers the gate carries, so adding a provider is an
ordinary adapter change and not a governance event. That is deliberately weaker
than checking a form the gate already knows — a fabricator declares their own
form — and it is stated as weaker, because the protection that was ever
load-bearing here is the auditor's lookup against the provider account and never
the shape of the string.

The runner's own isolation is held to the same standard as the behaviour it
judges. A gate that claims to compile and run outside the checkout must actually
do so under an ambient environment it did not choose, and that claim carries its
own locked definition rather than resting on the runner's prose about itself.

<a id="concept-plan-scope"></a>
### Scope

Product code intended to survive the milestone: a real multi-turn agent loop
with committed conversation history, declared bounds, and canonical-history
continuation; streaming progress with exactly one durable reconstruction per
turn; the prompt, steer, and follow-up input algebra; a runtime-scoped tool
registry; four conformance-tested bootstrap coding tools; an artifact store for
oversized output with an operator retrieval path; a host policy port with a
working refusal; project-resource discovery and trust admission; working
cancellation; a session directory over a resolved state root; one wiring-only
composition application, the shipped reference local stack the command depends
on and an embedder on the reference adapters can depend on rather than copying;
and one operator command application. All of it runs on the M1 kernel and
through the M1 embedded API.

The command surface exposes one operation the outcome list does not derive from
a durable session: `loopex artifact` retrieves a spilled artifact by its opaque
reference. It exists because Outcome 5 promises the operator can read back what
a tool actually produced, and a spill the operator cannot retrieve is a bounded
result that quietly discarded the remainder. It is a projection of the same
`ArtifactStore` port an embedder calls and owns nothing durable.

M2 ships a runnable `loopex` command built as an `escript` from the source tree.
That is an operator feature and is independent of any version number. The root
`VERSION` stays `0.0.0`, nothing is tagged, and nothing is published.

**The boundary behaviours M2 leaves in place are Store, Model, and Executor.**
It adds two narrow ones the founding vision already assigns. `Loopex.Policy` is
the host-control seam that replaces M1's literal `{:host_policy, :allow}` term,
and an `ArtifactStore` port owns oversized tool output so the model-facing
result can stay bounded without discarding what a tool produced. Each ships with
the smallest local adapter and a reusable conformance suite. Neither adds an
application. The tool registry is runtime-scoped data and resolution rules
inside core, not a boundary behaviour.

The `loopex` command is a client application and a peer surface: it owns no
loop, no durable session truth, no cursor truth, no Store access, and no
authority decision. Every operator flow it offers is a projection of the same
embedded API an embedder calls.

Darwin floor, Darwin current, and Linux current are three independent execution
lanes. Each runs the complete gate from a fresh owned root. The floor pair is
Elixir 1.17.0 on OTP 26.0, where neither Erlang's `:json` nor Elixir's `JSON`
exists, so every byte of encoding and decoding this milestone needs is
repository-owned code that runs there.

**Accepting this plan pair takes three decisions.**

**First, two new applications and a new application role — an eighth application
in the repository and one added application role in the rules.**
`apps/loopex_cli` is the operator command with role `:client`.
`apps/loopex_composition` is a wiring-only application with the new role
`:composition`: it names the concrete Store, Model, Executor, and ArtifactStore
implementations and starts the application tree and a runtime, and the `loopex`
command depends on it while an independent fixture composes through it without
depending on the command, which is what makes it wiring an embedder on those
same reference adapters can depend on rather than re-derive. What is being
decided is a shipped reference local stack, not a generic wiring toolkit: an
embedder choosing a different Store, Model, Executor, or ArtifactStore composes
the public ports and the `Loopex` facade itself, and a wiring layer general
enough to serve both waits until a second real composition exists to give
evidence for one. It owns no authority: the host supplies the policy that
governs the run, and the composition refuses to start without one. The role exists because a
composition fits neither existing role — an `:edge` may not import a concrete
sibling, and a `:client` may not be depended on at all — so a `:composition` may
depend on `:loopex`, optionally on `:loopex_protocol`, and on the `:edge`
applications it composes, may declare no external dependency, and may depend on
no `:client` and on no other `:composition`. A `:client` may depend on
`:loopex` and on at most one `:composition`,
may compose `:edge` applications only in tests exactly as M1 already permitted,
may declare no external dependency, and still may not depend on another
`:client`. The alternative was widening `:client` to permit one client-to-client
dependency, which reopens the narrow rule an acceptance review deliberately
kept; this role keeps it closed, and unlike the earlier shape of this decision
it opens no production edge dependency for every client forever.

**Second, the two new narrow ports named above,** each with one local adapter
and one conformance suite, and no other new boundary behaviour.

**Third, two shipped permissive policies rather than one.** A `:client` may not
depend on another `:client`, so the command cannot reach the reference client's
and names its own, and the composition cannot supply one for either of them
because a permissive default shipped there would be inherited by every embedder
that depends on it. Both are permission-granting modules an operator can select,
so both are named explicitly, both print the same single notice, both carry
locked coverage, and neither is ever an implicit fallback.

**Accepting this plan pair does not, and cannot, dispose the M1 gate.** M1's
closed gate binds nine files by digest, and M2 must change two of them:
`apps/loopex/lib/mix/tasks/loopex.deps_budget.ex`, whose planned inventory
freezes the repository at exactly six applications with one `:client` and no
`:composition` role at all, and `apps/loopex/test/deps_budget_test.exs`, its
adversarial corpus, which must gain the cases that prove the eight-application
inventory, the `:composition` role rule, and the client rule that admits exactly
one composition. Those two artifacts are where the inventory and role change is
proved; this milestone binds no third artifact for it. Those
digests are not enforced only by M1's own runner. The repository status check
verifies every plan's declared bound artifacts against the working tree at every
revision and across the history reachable from `HEAD`, with no exemption for a
`Closed` milestone. The moment either file changes, `mix loopex.status` fails,
`bash scripts/check-bootstrap.sh` fails because it runs that check, and the
closed M0 gate goes red because it runs bootstrap. **Until an accepted M1 gate
generation rebinds those two artifacts to the M2 bytes, M0, the bootstrap
aggregate, and the status check are red.** M1 is `Closed`, so that rebinding is
an `amendment-transaction-v2` gate generation rather than the ordinary
amendment: both of M1's authority rows stay byte-immutable and the closed plan
gains one appended generation row. It is a non-delegable baseline exception
requiring the maintainer's explicit disposition; this plan names it, fixes its
shape, and does not execute it.

M1's protection is otherwise carried forward and re-run, not restarted. The M2
gate re-runs M1's eleven protected outcome roles — including both real-provider
roles — at their exact locked identities, states, and minima beside its own.

<a id="concept-plan-non-goals"></a>
### Non-Goals

**No wire, no daemon, no second client.** The vision's serial barriers put
useful local session and operation truth before multi-client attachment and a
protocol candidate, which they name as one step rather than as two ordered ones.
Splitting that step into a headless protocol milestone and then a daemon
milestone is this project's own sequencing decision, and M2 precedes both. It
stays in the foreground. It creates no JSONL RPC transport, no
line-framed protocol, no golden vectors, no socket, no daemon, no controller
lease, and no second-client attachment contract. A headless JSONL session
protocol is the next milestone's whole subject, and a durable multi-client
daemon is the one after it. Introducing either here would freeze a guess about a
surface no proven client has used yet.

**No cross-process cancellation.** Stopping a live run is Ctrl-C in the process
that is running it. A second `loopex` process cannot cancel the first: ADR 0008
requires one live Runtime Control per `(Store identity, runtime_id)` placement
key and the command surface enforces that over its own state root, the command
re-presents one durable `runtime_id`, and M2 has no
out-of-band channel, so a second process is refused by mutual exclusion rather
than reaching the run. `loopex cancel <session>` is therefore narrow and says
so: it reconciles a session whose owning process died, driving it to a truthful
terminal state from durable evidence. Cancelling another process's live run
needs an attached second client and belongs with the daemon.

**No publication.** Nothing is published to Hex, to a binary release channel, or
to any other distribution point, and no version is tagged. Publishing one
package would permanently create the vision's seventh compatibility surface —
released package names, their contents, and the constraints they declare — which
is inert only while nothing is published. It would also require the name,
trademark, domain, and Hex clearance the roadmap keeps as an unscheduled
question. Neither is worth spending to make a local kernel usable, and both stay
available to a later milestone that has a consumer.

**Three of the seven tools wait.** M2 ships the bootstrap profile — `read`,
`write`, `edit`, `bash`. The `coding_search` profile — `grep`, `find`, `ls` — is
explicitly deferred, because the vision itself splits the surface that way and
asks for measured prompt cost and task utility before an accepted decision fixes
a reference default. The four shipped tools carry the shared conformance the
other three will inherit.

**Refusal now, interactive approval later.** Host policy owns `allow`, `deny`,
and `defer`. M2 delivers `allow` and a working `deny`. A permissive policy is a
host's own decision to trust its own workspace, so each reference host names one
for itself; no port, edge, or core module supplies one, and starting a runtime
with an executor-backed tool and no named policy is refused. `defer` —
interactive per-call approval with a mid-run round trip to the operator — is
explicitly deferred; it needs an interaction contract the foreground rung has
not earned. The project-resource trust decision in Outcome 7 is not a `defer`:
it is settled before a run starts, or the block is withheld and the run proceeds
without it, so it introduces no mid-run interaction.

**No promise that stopping is always clean.** Ctrl-C stops the owned work and
reports what actually happened, which is not the same as always finishing
`cancelled`. A run finishes `cancelled` only where every owned operation reached
a validated terminal fact and every owned process tree was confirmed cleaned;
otherwise it finishes `outcome_unknown` carrying a reconciliation reference. No
document, transcript, or help text in this milestone says an interrupt ends a
run cleanly.

**No context pipeline beyond exact staging.** M2 implements only the initial
local-kernel stage the vision names: canonical history, a fixed reference
project-resource stage, trust admission, total budget enforcement, and exact
receipts. Registered context providers, transformers, selectors, observers,
recall stores, memory, retrieval, embeddings, and prompt libraries are out.

Also out: changing the model within a run, branches and forks, compaction,
extension manifests or activation, isolated or remote hands, an executor broker
or fleet, a durable store selection or migration, a policy engine, sub-agents,
plans, objectives, background jobs, performance budgets, and any public
compatibility freeze. A terminal user interface is out: the command may stay
line-oriented, and only the semantics above are proved.

No checker, registry, document, evidence record, or status row substitutes for
the working loop and the working command. A component that does not serve one of
the eleven outcomes, or the two named mechanisms that support them, is out of
scope.

## Workstreams

Ownership and the required rejoin order are fixed in the
[technical envelope](M2-technical.md#technical-plan-ownership).

- **A — Tool contract and registry.** `loopex_protocol` and core own the tool
  definition shape and the runtime-scoped registry that Outcomes 1 and 4 resolve
  through. Nothing else can name a tool until this exists, so it rejoins first.
- **B — Loop, bounds, streaming, input algebra, and staging.** Core owns
  Outcomes 1, 2, 3, and 7: the turn machine, the canonical history projection,
  exact staging of each turn's request, the three declared bounds, the delta
  algebra and its single durable reconstruction, the prompt/steer/follow-up
  queue, and project-resource staging. It also carries both port arity changes.
  It rejoins second.
- **C — Coding tools, artifacts, and host policy.** `loopex_executor_local` and
  `loopex_store_local` own Outcomes 4, 5, and 6 and the executor half of
  cancellation; `loopex_reference_client` gains the shipped permissive policy
  and its own lane. They implement the registry's contract and rejoin third.
- **D — Cancellation and the session directory.** Core owns Outcomes 8 and 9.
  Cancellation needs C's owned-process termination and B's turn machine, so this
  rejoins fourth.
- **E — Operator surface, composition, and demonstration.** `loopex_cli` owns
  Outcome 10, the attended demonstration, and the `escript` entrypoint;
  `loopex_composition` owns Outcome 11. The workstream carries the
  eighth-application inventory and the `:composition` role rule with them. It
  rejoins last and proves one operator experience through every prior
  workstream.
