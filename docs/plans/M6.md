<a id="concept-plan-purpose"></a>
### Purpose

Technical depth: [Prerequisites and acceptance points](M6-technical.md#technical-plan-prerequisites).

**M6 is the minimal runnable Loopex, the `0.3.0` candidate.** Its product
question is:

> Can Loopex be run as a minimal standalone agent loop — called from an
> Elixir host in one function call, from a shell or from another agent in one
> command — and still be the full durable Loopex when that is what the caller
> asks for, all over one kernel?

Loopex already is a working coding harness, but only in its heaviest form.
Every composition needs:

- a state root on disk and the local store;
- a provider companion BEAM with a built worker artifact and digests;
- a named policy;
- one pinned model.

The command needs a subcommand, `--policy`, `LOOPEX_HOME` and the companion
build. It has no model flag and no machine-readable output, and a failed run
exits 0. Nothing lets a host ask one question and get one answer.

M6 does not write a second, simpler loop: the vision forbids a surface owning
an alternate loop. It composes the unchanged kernel with lighter parts behind
its existing ports:

- a memory store;
- an in-process model adapter that runs ReqLLM inside the host's VM for a
  local Ollama model and for the hosted providers, reading a hosted provider's
  credential at the moment of each call;
- the local executor on a temporary root.

The result is three instances of one Loopex:

| Instance | Called by | Composed with | Promises |
| --- | --- | --- | --- |
| **Embedded, ephemeral** | An Elixir host: `LoopexComposition.Ephemeral.run/2`, `start_session/1`, `ask/3`, `answer/3`, `last_result/1`, `history/1`, `stop_session/1` | The memory store, the in-process model adapter, the local executor | A whole multi-turn session inside one VM; no session truth persists; no recovery claim |
| **Standalone command** | A shell, CI or another agent: `loopex ask "…"`, or its alias `loopex -p "…"` | The ephemeral profile by default; the durable profile with `--state-root` | The answer on stdout, or one JSON object when asked; an exit status that reports the run's outcome |
| **Full Loopex** | Operators and multi-client work | The durable local store, the provider companion, the daemon | Everything M1 to M5 proved, plus named skill directories through the public manifest helper and `ask --state-root`, and optional model, bound, sampling and active-tool composition options |

The ephemeral row selects the in-memory adapter that the technical vision
§12.2 already authorizes for simple embedding. It does not weaken the Concept
§12 or technical §3.1 guarantees of sessions represented as durable; those
remain the full Loopex profile's contract.

The embedded API lives in `loopex_composition`, not in core. Assembling the
memory store, the adapter and the executor is exactly the work the dependency
direction keeps out of core, and M6 leaves core's runtime library unchanged.
The closure tooling's two Mix tasks join core's existing development tasks.

**Why this rung, and why now.** A second person, or a second agent, can use
Loopex only once it can be called without assembling the durable stack. Every
comparable minimal harness offers exactly that: one library call, one command
and a small fixed tool set. The installed operator milestone, drafted as M7,
depends on it, because its configuration and lifecycle commands sit on top of
the profiles and the command M6 fixes.

The new sequence, recorded here and projected into the roadmap on acceptance:

- **M6:** this milestone, the minimal runnable Loopex.
- **M7:** the installed durable operator.
- **M8:** the store engine successor.
- **M9:** the governed extension runtime.

M7, M8 and M9 are drafted in [docs/drafts](../drafts/README.md) and are
refined as M6 proceeds.

**The M5 baseline, and permission to rework it.**
- **Baseline:** M5 closed on 2026-09-26 at the tested implementation `fe020e24`
  (administrative closure `3f81b048`, tagged `v0.2.0`, integrated on `main`).
- **Rework permission:** the maintainer authorized M6, on the same day, to rework
  code delivered by M1 to M5 where the minimal profile needs it. M6 uses that
  permission for a small set of changes, each additive and each held to the
  unchanged M5 suites:
  - the durable composition gains model, bound, sampling and active-tool
    options, and its default policy revision stops following the release
    version; named directories use the public helper and the released
    `resource_manifest` path rather than an unfulfillable raw-runtime option;
  - ReqLLM, Req and Finch stay embedded but are no longer started automatically
    with the adapter's application;
  - the companion's pure request mapping is shared;
  - credential-bearing ephemeral sessions activate no tools, while an executor
    carrying the ephemeral gate capability also clears every provider
    credential variable from OS child environments as defense in depth;
  - the memory store is promoted from a test wrapper;
  - three read-only tools are defined;
  - the release check gains two rows and a rollback lane.
- **What the permission does not cover:** the vision's non-negotiables. Those
  are dependency direction, one serial owner, durability truth, plain boundary
  data, and credential isolation, except as ADR 0039's vision amendment
  states.

**The embedded API.** One module in `loopex_composition` that composes the
ephemeral profile and follows the session through core's existing public
facade. Every terminal form carries one bounded observation. It returns the
last assistant text on `completed`, and the same text, tool and skill projection
with fixed details for every other outcome. A timed-out call returns that
  partial projection. Its wait deadline does not kill a granted facade call: a
  timeout before the owner grants dispatch cancels with no possible admission
  and preserves `last_result`; after the grant, the one command resolves under
  its independent bound. Late refusal preserves the prior observation and
  reopens the session; late acceptance stores the timeout projection and the
  sole owner keeps draining. Timely acceptance of a new prompt clears
  `last_result/1` to `:none`; timely acceptance of an answer clears the answered
  question to `:none`; the next question or ending replaces it, and another ask
  remains `run_open` while a validated ask owns the one public-mutation slot,
  including before its actor grant, or while its run remains open. A second
  answer while an answer owns that slot is immediately
  `invalid_interaction_answer`; neither concurrent refusal queues nor starts a
  wait deadline. If the command or attachment path fails after a prompt
may have been admitted while `ask/3` or `answer/3` is still waiting, the absent
terminal event leaves cleanup unproved: that call returns `cleanup_unproved`,
names the retained root and carries the same partial projection under its
`session_unavailable` ending. Before admission, proved cleanup returns the bare
lifecycle error; unproved cleanup names the retained root with no ending. After the
earlier call timed out and left only the background drain, later calls receive
the bare lifecycle error. A policy that defers is surfaced as a
  pending interaction and is not answered for the host; the one-shot `run/2`
  form reports that a session is required after it stops the run. Stopping
  removes the temporary root only when effect cleanup, executor process groups,
  and every child of the per-session store, lease, executor, trace-capability
  and runtime subtree
  are proved gone, and the credential/tool gate acknowledges removal of the
  session's final registration and lease, before root removal succeeds;
  otherwise it returns `cleanup_unproved` and names the kept root and pending
  obligation. Its pending list contains each cleanup phase that was reached and
  failed proof; it omits a downstream phase whose prerequisites prevented it
  from running. Final gate release is named only after the earlier cleanup
  phases proved, root removal only after gate release proved, and those two
  names never occur together. A startup rollback also carries its fixed failing-step cause;
  ordinary stop cleanup carries no cause. When `stop_session/1` returns that
  error on a surviving session
  handle and only the subtree or removal remains, the owner keeps a retry state
  in which only a later stop is accepted. One-shot and true no-waiter paths,
  including creator exit with no registered borrowed waiter and post-timeout
  drain failure, exit after logging any retained root. A live registered
  borrower instead receives the concurrent-stop result before creator-exit
  cleanup ends: a terminal value when observed; before possible prompt or answer
  admission, a bare lifecycle error after proved cleanup or a cleanup error with
  no ending; after possible admission without a terminal event, the cleanup
  error containing the bounded no-ending value. Creator exit never creates retry state. An unproved
  ending, effect, process group or final gate release is
  permanent: the owner exits unmarked and every later call returns
  `session_unavailable`. A returned startup, session-create, attachment,
  resource-admission or ordered skill-activation failure tears down every
  per-session resource whose start is known before returning. A startup phase
  granted but lacking an exact return is conservative after an exact successful
  root claim: no handle is returned, cleanup stays unproved, and the temporary
  root is retained with the missing subtree obligation even when every known
  parent ended. Loss in side-effect-free root-candidate preparation proves no
  root exists. A lost exclusive-root
  claim names the possible path with unknown ownership and never authorizes its
  deletion. Every rollback after the owner exchanged its gate reservation also
  submits one final disposition after the actor, subtree and applicable process
  groups are gone, and requires the gate's exact acknowledgement before root
  removal or a proved failure. If that reached acknowledgement is unproved, a
  possible root is retained with `gate_release`; when no root could exist,
  composition instead returns `credential_tool_gate_unavailable`, logs no path
  and keeps both gate modes poisoned. A no-root actor that cannot be proved down
  prevents that exchange, returns its fixed phase error and also poisons the
  gate; it does not report an exchange that never ran. If the session owner itself dies after its successful gate exchange
  but before it returns a handle, the entrypoint returns bare
  `session_unavailable`: it does not become a second owner or invent a cleanup
  map. Before the root-start token no root exists; afterward the private subtree
  collapses through the owner's monitor and any root can remain unnamed under
  the unexpected-owner limitation. The explicitly VM-lifetime ReqLLM and Req infrastructure is not
  session state. A failed root removal uses the same named error. A successful stop closes the
  handle: repeated stops return `:ok` without retaining an owner process, other
  calls return `session_closed`, and a dead owner that never marked a successful
  stop returns `session_unavailable` rather than false success.
  The first accepted stop atomically closes admission: concurrent stops share
  its one bounded result, while every later non-stop call returns
  `session_unavailable` immediately and cannot wait behind cleanup or start new
  work.

Its session option set is closed and validated before composition; unknown,
duplicate or malformed options refuse by name. `ask/3` may override only its
wait timeout. Model, policy, tools, skills, workspace, bounds, sampling and
provider address are session choices and cannot drift between turns. For a
combined model/address fault, an unknown provider prefix wins; for a known
prefix, replacement of its fixed provider module wins before address
normalization.

The process that calls `start_session/1` owns the session lifetime. It may pass
the opaque handle to other processes for calls, but that does not transfer
ownership: when the creating process exits, the session owner performs the
same bounded cleanup and borrowed handles become unavailable. A borrowed caller
already registered in `ask/3` or `answer/3` receives the serialized,
  admission-state-specific stop result before the owner exits: no ending is
  invented before possible command admission, while a possibly admitted command
  for which no terminal event arrives receives `cleanup_unproved` with the
  bounded `session_unavailable` no-ending projection and retained root. Creator
  death still supplies no retryable lifetime.
If a non-creator process dies while waiting in `ask/3` or `answer/3`, it does
not end the creator's session. Before the request can have reached core it has
  no effect; after the conservative possible-admission boundary the owner lets
  the one command resolve. Refusal preserves the pre-command observation;
  acceptance clears it to `:none` and keeps the sole attachment drain until the
  next question or ending, so the creator can observe it with `last_result/1` or
  stop the session. Another ask remains `run_open` while that command is
  unresolved or its accepted run is open.
Owner admission closed for application stop, a poisoned or unavailable gate,
owner-child start failure and owner registration failure are distinct fixed
composition refusals; none creates a root or session handle.
After closed option and prompt validation, workspace and skill resolution,
provider admission and the pre-start safety guards, every embedded entrypoint
that creates a session—`start_session/1`, and `run/2` through that path—also
starts the `loopex_composition` OTP application when needed, so an escript
or a direct embedding host does not need a separate manual start call. It does
so before ReqLLM hygiene or owner admission. That bootstrap
is bounded before gate admission; an exact failure or unproved bootstrap
returns `composition_application_start_failed` with no root, credential read or
session. An OTP application-controller request may still finish after a bounded
refusal, so a later call re-evaluates the application state rather than assuming
that nothing started.
The packaged escript names no application for its generated pre-main wrapper.
Its `main/1` performs only literal command classification before startup: a
literal `ask` or `-p` completes its command grammar, prompt bounds and profile
selection before any Loopex application start, and every invalid form refuses without
one. A valid ephemeral form reaches the bounded embedded bootstrap with no
  Loopex application already started. A valid durable form uses an ask-specific
  helper whose `:loopex_cli` startup failure enters the fixed bounded
  `application_start_failed` renderer. Every other argv uses the private helper
  that exactly reproduces the former generated `:loopex_cli` success or
  formatted-error-and-status-1 branches before existing main logic. Existing commands therefore keep the M6 application order—the
separately declared ReqLLM, Req and Finch load-only change still applies—and
their M1–M5 behavior, while a delayed first composition start cannot trap ephemeral `ask`
before its bound begins.
Handle-consuming `ask/3`, `answer/3`, `last_result/1`, `history/1` and
`stop_session/1` never restart the application. They retain their lifecycle-
first precedence; loss of the application tree makes the existing handle closed
or unavailable through its owner and gate monitors.

**The model adapter.**
- **One path:** in the ephemeral profile every model, local or hosted, runs
  through one in-process adapter in `loopex_llm_reqllm` that calls ReqLLM
  inside the host VM, sharing the companion's pure request and reply mapping.
  The durable profile keeps the companion for every model and refuses `ollama:`
  in M6.
- **Credentials:** the runtime names each hosted provider's credential
  variable; the one process that makes a call reads it immediately before the
  call and passes it to ReqLLM for that call only. That process is excluded
  from Loopex tracing and marked sensitive. The value stays out of every Loopex
  plane, and a mapped reply containing the exact value is discarded. The host
  environment keeps its copy for the host's lifetime. During the call and
  cleanup, the caller, provider HTTP/TLS state, a crash report, a crash dump or
  host telemetry can expose it; a host-made copy has the host's lifetime. ADR
  0039's vision amendment accepts that for this profile only.
- **Ephemeral scheduling gate:** active-tool ephemeral sessions and owned
  hosted-call paths take mutually exclusive VM-wide leases. An unproved tool
  process group, any unproved registered call root or loss of the gate poisons
  both lease modes until VM restart. Credential-free Ollama calls take no
  credential-call lease: their start-blocked caller and call root are instead
  registered under the enclosing ephemeral owner, so the default Ollama/tools
  combination remains runnable and cleanup stays in the gate census. A gate or
  owner-supervisor crash terminates every
  active ephemeral session, whose handles then report `session_unavailable`.
  Only the composition application's explicit clean-stop handshake may clear
  the unclean marker, after admissions are closed, no lease obligation remains
  and no ephemeral owner is live; ordinary child or supervisor termination
  never clears it.
  Durable compositions, directly constructed executors and trusted host code do
  not participate, and the fixed 5,000 ms post-caller quarantine does not prove
  a slower socket or TLS controller has drained.
- **Guards:** the adapter refuses to call while `:req`'s global default options
  or `SSLKEYLOGFILE` are set, or while ReqLLM's registered module for the
  provider is not its own. The base URL may carry a normalized path prefix but
  has no user information, query or fragment; its scheme, host and port pin the
  origin: `https` for OpenAI, Anthropic and OpenRouter, and `http` or `https`
  for credential-free Ollama. Every call names that address,
  never taking one from ReqLLM's configuration or catalog, disables retry,
  redirect and caching, and never hands the call to a ReqLLM task.
- **A call-owned pool:** the cleanup owner starts one uniquely tagged,
  user-managed Finch pool with one HTTP/1 slot for the call. Concurrent calls,
  even to the same origin, have different reference tags and connections.
  `Req.Finch` supplies only the shared worker and pool-supervisor registries; no shared default pool carries
  a model request. HTTPS disables TLS 1.2 session reuse, TLS 1.3 tickets and TLS
  secret retention.
- **One dispatch:** a thin Req adapter validates the final origin, adapter,
  fixed Finch name and tag and the absence of any alternate transport or
  proxy. It removes Loopex's private call context and obtains one atomic grant
  plus the exact monitored HTTP/1 worker PID from the cleanup owner, then builds
  the Finch request and invokes that worker directly. It performs no
  pool-manager lookup, so a missing or restarted pool cannot auto-start a
  replacement or receive the request. A retry, redirect or second adapter
  invocation is refused before network activity.
- **Bounded response:** that adapter installs an internal 8 MiB collector. A
  larger fixed-length or chunked body halts the request and records a private
  `model_response_too_large` sentinel. It requests identity encoding and uses a
  private `model_response_encoding_unsupported` sentinel rather than
  decompressing an encoded body. Both become the public `model_call_failed`
  result.
- **Dependency-visible tool calls:** both ReqLLM adapters share one validator
  over the buffered `%ReqLLM.ToolCall{}`. It requires a non-empty id and name
  plus binary JSON that decodes without repair to an object, and it refuses a
  call that ReqLLM still marks provider-executed or provider-native. Those
  classes are not replayable application calls and never become local tool
  requests. Invalid text, `null`, arrays, incomplete JSON, visible error metadata
  and either visible non-application marker fail the whole started call instead
  of becoming an empty-argument execution. Locked ReqLLM
  has already generated, normalized, forced or omitted some provider-wire
  fields before this seam; M6 pins that behavior as a named limitation instead
  of claiming the erased distinctions are reconstructible. A visible `{}`
  still passes ordinary tool resolution, schema validation and policy.
- **HTTP/1 only, for now:** both ways of using HTTP/2 through the locked Finch
  are unsafe here, one resending requests silently and the other failing any
  request over 64 KiB, so every call uses HTTP/1, ReqLLM's own default. HTTP/2
  waits for a Finch release that removes one of those limits.
- **Failures stay contained:** the calling process catches every failure and
  ends with a fixed reason, so no exception carrying the request or its
  credential reaches the cleanup owner, which is also marked sensitive.
- **Dispatch boundary:** the provider call itself is the adapter boundary. A
  returned refusal before it may be retried by the kernel. The unchanged core's
  process-local provider-lifetime registration is the conservative exception: if
  core interrupts registration or registered-owner activation, the adapter emits
  no result, core keeps its provider-failure or unproved-cleanup classification,
  and the attempt is not retried even though network dispatch was not authorized.
  Anything from the ReqLLM call on is treated as possibly sent and never retried.
- **In-flight cleanup:** before creating a per-call process, the callback obtains
  the unchanged kernel's invocation-local child starter. An unmanaged invocation
  refuses without a proxy, child, credential read, pool or poison. A managed
  invocation creates an authority-free owner candidate behind a bounded start
  proxy. It holds no request, credential, gate, root, pool, caller or dispatch
  authority. Exact managed core lifetime registration converts that candidate
  into the one cleanup owner; only then can a one-use activation token let it
  proceed. An unknown queued start poisons ephemeral admission; no token is
  sent, and a later undisclosed candidate can only observe its expired start
  deadline or dead callback and exit. In the locked kernel's narrow
  worker-retained/guard-unregistered interval, core can finish the model attempt
  with no registered provider-resource obligation before that authority-free
  candidate is scheduled and `DOWN`. Such a candidate permanently disables
  activation and exits on its
  first scheduled protocol step after observing callback `DOWN`; if registration
  committed first, its exit without the
  registered stop handshake makes provider cleanup unproved. Complete
  session-subtree cleanup still reaps every candidate before public session
  cleanup can be proved. Every admitted cleanup owner
  stays responsive throughout, and one calling process alone can return a
  result. The owner creates and monitors a start-blocked, request-free
  pool-lifecycle root, registers it with the scheduling gate, and only then lets
  it build the pool subtree. The root registers each child before proceeding and
  performs the bounded graceful stop while the owner stays responsive. Once the
  lifecycle root starts, every later pool-child failure or partial start,
  terminal reply, refusal, spawn failure or exit starts or joins that stop. On the
  transport path the Req adapter requests it early and waits
  until the root and pool are gone and both tagged registry entries are absent.
  A failure before that adapter runs reaches the same owner-gated proof. The owner then ends
  the caller before returning the reply. On a stop or deadline it first makes
  results inadmissible, kills and awaits the caller, then tears down the pool
  cooperatively before acknowledging. It never kills the lifecycle root and
  treats the root's failure to prove its descendants as unproved cleanup.
  Failure to prove any required `DOWN` or registry removal takes the existing
  unproved-cleanup path. A checked-out socket and its OTP TLS controller may
  drain after the caller and pool are gone. The isolated release witness
  requires both gone within 5,000 ms of caller `DOWN`, but runtime cleanup does
  not wait for or prove that threshold; no reusable TLS state or result route
  remains. The reply arrives whole, with no streamed progress.
- **Host hygiene:** ReqLLM, Req and Finch are not automatic runtime dependencies
  of a Loopex application. The guarded composition step first checks the Req and
  key-log guards and refuses `TIDEWAVE_REPL="true"`, which would make ReqLLM
  open a development listener. It then explicitly starts ReqLLM and its OTP
  dependency graph. The step turns off automatic `.env` loading as a persistent
  ReqLLM setting and marks that it did, so later compositions and later restarts
  of ReqLLM stay clean. The VM-wide gate serializes the complete
  read/configure/start decision and bounds it to 5,000 ms plus 1,000 ms to reap
  its worker. Only an unproved worker lifecycle adds one separate 1,000 ms
  poison-result handoff to the already admitted cohort before the shared tree
  ends, so every admitted hygiene request has a 7,000 ms outer bound. It
  records a provisional result, directs the worker to finish and
  requires its exact normal `DOWN` before it commits or restores the marker. A
  proved failure before the first configuration or application-controller
  mutation preserves the prior hygiene marker. Any uncertainty after that first
  mutation directive leaves a persistent uncertain-start marker and refuses
  every later ephemeral composition until VM restart; no owner, root,
  credential read or effect exists at that point. Once
  started, ReqLLM and Req's shared infrastructure remain until the host stops
  them or the VM exits; Loopex does not reference-count them, and per-call
  cleanup leaves them with no request or credential. A ReqLLM the host started is accepted only when the host
  declares it with `.env` loading off, and one running with loading on is
  refused. Every model is named inline, so no catalog lookup or
  unverified-model warning occurs, and Loopex changes no other ReqLLM setting.

**The store.** `Loopex.Store.Memory`: the shipped pure store state that the
local store replays, behind a small supervised process, the same logic the
conformance suite already proves in memory. There is no artifact store in the
ephemeral profile, so oversized tool output is truncated with the existing
notice.

**Composition.**
- The ephemeral profile as above.
- On the durable `LoopexComposition.start/1`, `with_runtime/2` and
  `start_edges/2`: optional `:model`, `:bounds`, `:sampling` and
  `:active_tools`, whose defaults reproduce M5 exactly. Named directories do
  not become a fifth raw-runtime option: the helper returns the manifest and
  decision inputs a host needs for the released `:resource_manifest` and ADR
  0025 session-command workflow.
- `LoopexComposition.ResourcePacks.read_directories/2` builds a resource manifest from named skill
  directories, classified against the workspace root: a project skill
  (`.agents/skills/<name>` in the workspace) as `project:<name>`, a user skill
  (outside the workspace, such as `~/.agents/skills/<name>`) as `user:<name>`,
  and the project skill winning a shared name, in both profiles. The result names
  the omitted user pack by its exact `user:<name>` source id.

**The command.**
- `loopex ask`, and its `-p` alias, in `loopex_cli`: text or JSON output and the
  prompt from words or stdin.
- **Escript entry:** the built command reaches `main/1` before starting any
  Loopex application. Invalid `ask`/`-p` input refuses before one. A valid
  ephemeral form delegates first application start to the bounded embedded
  entrypoint; a valid durable form uses the bounded ask diagnostic on startup
  failure, while every released or unknown command keeps the exact former
  `:loopex_cli` startup outcome before its existing dispatch.
- **JSON output:** for each public run outcome or no-ending observation, the
  compact encoding of exactly one object followed by one LF and no other
  standard-output byte. Its members are the ones ADR 0039 lists:
  `schema`, `session_id`, `run_id`, `profile`, `outcome`, `text` and
  `text_truncated`, `tools` and `tools_truncated`, `shadowed_skills`,
  `cleanup`, and `details` with fixed members per outcome. An unmarked owner or
  scheduling-gate crash that leaves no public cleanup proof writes no object.
- **Exit map:** `0` for completed, `1` for a refusal or cleanup failure before
  any run observation, for that unproved command/lifecycle failure, or for the
  named no-output ordinary worker-reap hard halt; `2` to `5` for failed, bound
  reached, outcome unknown and cancelled, `6` when no ending
  is observed after a prompt may have been admitted because the wait expired or
  the session path became unavailable, and the existing `130` interrupt. No
  `ask` policy defers, so
  `ask` has no deferred-interaction status.
- **Ephemeral completion:** a worker result is provisional. The command proves
  that worker ended through a private 1,000 ms reap, performs the mandatory
  bounded `stop_session/1`, and then makes one serialized signal-handler
  decision before it renders. A result whose worker cannot be proved ended is
  discarded and hard-halts status 1 without output or a cleanup claim. A first
  signal processed before that decision wins the interrupt path and status 130;
  otherwise the observation and stop return use the same precedence as
  `run/2`. Handler loss or an unproved decision emits no result. This leaves no
  live ephemeral handle behind a normal command result.
- **Bounded diagnostics:** except for the named ordinary worker-reap hard halt,
  which terminates before rendering and promises no output, a status-1 path
  reports only one fixed code selected by the failed boundary; it never prints
  an arbitrary facade return, exception, path, option spelling or inspected
  term. A caller-visible unproved cleanup
  instead reports the kept root as a JSON-encoded string, its fixed
  `owned` or `unknown` ownership label and the fixed ordered pending names.
  `unknown` is diagnostic only and never authorizes deletion. That line is
  bounded by the admitted path ceiling.
- **Policy names:** `ask` maps `allow-all`, `shell-allowlist` and `refuse-all`
  to the reference CLI's policy modules.
- **Crash output:** `ask` turns the logger off, renders its own lines, and runs
  with crash dumps disabled, so ReqLLM's failure paths cannot write request
  data.
- **Dispatch:** `ask` is an offline form, and `--daemon` is not accepted. The
  CLI's credential discard waits until `ask` has chosen its profile: the
  durable profile then consumes `LOOPEX_PROVIDER_API_KEY` as `run` does, and
  the ephemeral profile discards it unread and reads only the chosen hosted
  provider's own variable at each call.
- **Durable fresh session:** `ask --state-root` reads and validates named skill
  directories before touching the root, then takes placement, consumes the
  durable credential and composes with the helper's manifest. The composition's
  released manifest-retention seam is the only snapshot write. It creates and
  tracks the fresh session before attach, admission or activation. A lost create
  reply can leave a committed Store session whose id the command never learned;
  a tracking failure can occur before entry publication or after publication but
  before directory fsync succeeds. The command never retries either uncertain
  mutation and makes no listing or recovery claim for it. Once
  tracking succeeds, a later attach, admission, catalog, activation, status or
  pre-acceptance prompt failure leaves the listed session and its actual possibly
  committed prefix resumable; that prefix may include the attempted mutation when core
  committed before its reply was lost. The command never sends a prompt before
  every activation returned success, never retries an uncertain mutation, exits
  1 and writes no result. The released `with_runtime/2` cleanup result overrides
  any callback result when runtime cleanup is unconfirmed.
- **`run`** keeps its behaviour.

**Tools.** `grep`, `find` and `ls` join the existing `read` tool as the exact
`[loopex.read, loopex.grep, loopex.find, loopex.ls]` `:read_only` preset. The
four accept only workspace-contained paths under pathname checks and are
byte-bounded in-VM tools. Those checks are not an OS sandbox against a
concurrent same-user filesystem swap. `:none` activates no
tool and is required for a credential-bearing hosted model.
They are active only where a composition names them, in either profile. The
durable default stays `read`, `write`, `edit` and `bash`.

**Closure tooling.** Two Mix tasks and three shell scripts:
- the five-path confinement proof;
- hostile-umask archive staging;
- the archive-identity comparison;
- the floor lane with its open-file and signal preconditions;
- an attended-release runner using the platform's `script(1)`, in which a person
  answers the attended notices by default. Its automatic mode is refused unless
  the caller names a recorded maintainer disposition that authorizes automatic
  answers for this milestone and this exact candidate commit, as M5's did for
  M5 only.

They are tested against a fixture repository and replace every script the M5
closure kept outside the repository.

**Documentation.** `README.md` and `docs/operator/getting-started.md` show the
three runnable forms. `docs/operator/runtime.md` owns profile selection,
temporary-state and cleanup behavior; `docs/operator/tools-and-policy.md` owns
the presets, named skills and hosted-model restriction.
`docs/developer/getting-started.md` and its technical companion own the build
and package path; `docs/developer/runtime-and-embedding.md` owns the embedded
API and library-host obligations; and
`docs/developer/compatibility-surfaces.md` records the added 0.3 contracts and
0.2 rollback exceptions. The library-host obligations include its own logger
and crash dumps for request data, and `req_llm`, `req` and `finch` as `:load` in
its own OTP release.

**Defaults and limits** (all witnessed):
- **Model:** the ephemeral profile uses `LOOPEX_MODEL`, then
  `ollama:llama3.2`; the durable profile keeps its pinned Anthropic model when
  `:model` is omitted.
- **Run:** 16 steps, a 600_000 ms deadline, 4_096 output tokens and a context
  budget of 8_192. The embedded API waits the deadline plus 30_000 ms and polls
  every 10 ms.
- **Presets only for tools,** each measured under ADR 0017's system-class
  limit.
- **At most four skills,** ADR 0025's selection limit.
- **Read-only tools:** 30 s and 16 KiB each, at most 1_000 `grep` matches and
  2_000 `find` or `ls` entries, `ls` depth at most 8, and Elixir `Regex`
  patterns for `grep`.
- **Release:** the release check's Ollama model is named by
  `LOOPEX_RELEASE_OLLAMA_MODEL`. The hosted real-provider row is Anthropic,
  because the release credential is an Anthropic key.
- **API refusals and history:** `ask/3` refuses `:run_open` while a run is
  open. `history/1` returns at most the 256 most recent user, assistant and tool
  entries in order, marks older entries omitted and caps each returned user or
  assistant text at 64 KiB with a truncation flag.
  `stop_session/1` waits an open run's abort for its `cleanup_grace_ms` plus
  5_000 ms. `grep` skips files over 1 MiB.
- **Result and prompt bounds:** answer text is at most 64 KiB, at most 256 tool
  entries are returned and every other result string is at most 1 KiB except a
  kept cleanup-root path, which is at most 65,536 bytes. The separately returned
  pending interaction keeps its exact 65,536-byte `tool_call_id` bound. Every
  API or command prompt is non-empty valid UTF-8 and at most 32,768 bytes,
  reserving half of the Store item ceiling for its durable envelope.
- **Floor lane:** it raises the soft open-file limit to 65_536 (or the hard
  limit) and refuses below 4_096, the values the release check already uses
  (`check-release.sh:42-49`).

**Version.** `VERSION` moves from `0.2.0` to `0.3.0` in the tested candidate.
That changes `Loopex.version()`, and with it the daemon's readiness version.
The durable policy identity's revision no longer follows it: it stays at its
`0.2` value, so a pending interaction survives both the upgrade and a rollback.
The M5 tests that assert the literal `0.2.0` against the running build read
`Loopex.version()` instead. The release check's pinned `release_version` and
`DEVELOPMENT.md` move to `0.3.0`.

<a id="concept-plan-non-goals"></a>
### Non-Goals

Technical depth: [Deferrals and named limitations](M6-technical.md#technical-plan-limitations).

- **The M7 draft's scope:** no installed release archive, no saved
  configuration file, no default home, no provider profiles, no per-provider
  credential configuration, and no lifecycle commands beyond `ask`.
- **The M8 draft's scope:** no store engine, migration, format marker, backup
  or restore.
- **The M9 draft's scope:** no extension activation.
- **Model features:** no model switching within a run, no in-process adapter
  in the durable profile, and no HTTP/2.
- **Protocol:** no protocol change.
- **Integrations:** no MCP client or server.
- **Loop features:** no streaming UI, no parallel tool fan-out, no multi-agent
  trees, and no progressive skill disclosure.
- **Persistence:** no persistent memory for the ephemeral profile, and no
  migration between profiles.
- **Publication:** no Hex publication; that is a separate later decision.
- **Core:** no change to core's runtime library or dependency list.
- **Credential isolation:** no weakening of it in the durable profile; the
  ephemeral profile's narrower rule is ADR 0039's vision amendment.
- **Project discovery:** none in the ephemeral profile or `ask`. They admit
  only the skill directories they are given, so a headless caller is never
  prompted.

**Accepted limitations**, named in the technical plan:
- In the ephemeral profile the host environment keeps a hosted provider's
  credential for the host's lifetime. During a call and cleanup the caller,
  provider HTTP/TLS state, crash reports, crash dumps and host telemetry can
  expose the credential and request; a host-made copy has a host-owned
  lifetime. Cleanup proves the caller and tagged Finch pool gone, while a
  checked-out socket and its OTP TLS controller may drain after caller `DOWN`;
  the release lane requires them gone within 5,000 ms under isolated witness
  conditions, but runtime cleanup does not prove that threshold, synchronous
  transport-process closure or arbitrary host-memory erasure. ADR 0039 amends
  the vision to accept that for this profile.
- ReqLLM's start settings and, once Loopex starts it, its application and Req's
  shared infrastructure stay for the VM's life unless the host stops them. They
  retain no per-call request or credential after owned cleanup. A host-started
  or host-restarted ReqLLM may already have opened its optional Tidewave
  listener; Loopex cannot undo that host side effect.
- A host-started Req/Finch may have opened an environment-selected key-log file
  before composition. Loopex never sends a model request through that pool and
  refuses while `SSLKEYLOGFILE` is set, but cannot undo the earlier host side
  effect.
- A hard VM kill or an unexpected crash of the ephemeral owner itself can leave
  the temporary root, which holds the executor's receipt ledger but no committed
  session truth. Unlike caller exit or an ordinary failed stop, an owner crash
  has no surviving result path on which to name that root. If `ask` cannot
  obtain a public cleanup proof after an owner or scheduling-gate crash, it
  writes no JSON and exits with command-error status 1 even when it had already
  observed a run result.
- If starting a temporary owner times out, loses its guard or worker, or
  otherwise ends without a correlated result, composition returns no handle and
  treats the start as unknown even when every known process is already `DOWN`:
  the shared supervisor may still report a start-blocked child whose PID was
  never returned. The attempted session has created no root, read no credential
  and dispatched no effect. To fail closed it ends the shared ephemeral-owner
  supervisor, which makes every other active ephemeral owner reject new work and
  enter bounded cleanup through its lifetime monitor. An unreported suspended
  owner or an already-sent process kill may outlive the refusal until scheduled.
  The scheduling gate stays poisoned and a VM restart is required before more
  ephemeral work; a missing `DOWN` for a known process adds a bounded-reap
  failure but is not the condition that creates the poison.
- The unchanged kernel can finish a pre-registration model attempt with no
  registered provider-resource obligation while
  an authority-free owner candidate has not yet been scheduled to observe its
  callback's `DOWN`. That result proves no request or option reached the
  candidate and no credential, gate, root, pool, caller or dispatch authority
  exists; it does not prove the candidate itself already ended. The candidate
  accepts no later activation and exits on its first scheduled protocol step.
  It remains beneath the session worker supervisor, so complete session-subtree
  cleanup still reaps it. Once exact
  managed registration returns, the stronger registered-owner cleanup proof
  applies instead.
- A helper that has already received an untrappable kill can remain scheduled
  past a bounded return when its exact `DOWN` is unavailable. That applies to a
  composition-bootstrap guard or worker, core client actor, cleanup or root-
  removal worker, owner-start helper, provider owner-candidate start proxy and
  the durable `FollowReader`. The single-use provider proxy can remain blocked
  until its already-queued child-start request returns; it holds no call input,
  cannot submit another start and retires after callback `DOWN`. Every such
  helper's result is inadmissible. Cleanup helpers retain their monitor or fixed
  diagnostic, and no successor that could repeat the same cleanup starts until
  its predecessor is proved down. A later session-creation call may start a new
  bootstrap guard after the fixed refusal: that helper received no session
  input or authority, and its only submitted action is OTP's idempotent,
  serialized application start.
- After `ask/3` or `answer/3` returns a timeout, a later command or attachment
  failure in the sole-owner background drain has no waiting caller for a second
  snapshot. The timeout remains the only public observation; cleanup runs, any
  retained root is sent only to the host logger, and later handle calls report
  the bare `session_unavailable` lifecycle error. Standalone `ask` suppresses
  that logger, so its retained root can be unnamed in this case.
- The first interrupt after `ask` has an ephemeral session handle performs its
  bounded stop and exits 130 even if the monitored ask worker has not yet
  registered with the session owner. That race invents no observation and
  writes no result. After stop the command kills and boundedly reaps that worker
  before rendering; a missing exact process end is the named hard-kill case.
  The worker starts only after correlated ask-mode handler
  installation succeeds; an installation or live signal-manager failure stops the
  session before rendering and exits 1. An interrupt before the handle exists, a second
  interrupt or interrupt-backstop expiry may leave a root without machine
  output. The launcher latches and forwards a pre-child signal instead of
  losing it, but the pre-handle interval has no Loopex cleanup or exit-status
  guarantee; the platform child status is returned.
- After an ordinary ephemeral `ask` worker sends a provisional result, failure
  to prove that exact worker ended through the 1,000 ms kill-and-reap protocol
  hard-halts status 1 with no output or cleanup promise. Rendering or entering
  stop while the unproved worker can still use the handle would admit two
  command-progress paths.
- A durable model must match the single `LOOPEX_PROVIDER_API_KEY` and needs
  the built companion; the durable profile refuses a local Ollama model in M6.
- The ephemeral profile never deletes a host's credential variable, because it
  reads the variable at each call.
- `ask` offers no deferring policy.
- The JSON result carries no usage or model identity, because those are not
  public events.
- An ephemeral session's memory grows with its history.
- An unproved stop or failed recursive root removal keeps and names an owned
  temporary root for the host to remove only after its pending users end. A lost
  root-claim result instead marks the named possible path's ownership unknown;
  it is diagnostic and does not authorize the host or Loopex to remove it.
- The VM-wide scheduling gate covers only ephemeral compositions. Durable or
  directly constructed executors and trusted host code may overlap its provider
  path, and a transport that drains longer than the fixed quarantine may overlap
  a later ephemeral tool. An unproved tool group or call root poisons both lease
  modes; a gate/supervisor crash ends every active ephemeral session and
  keeps admission poisoned until VM restart.
- Rolling back to `0.2` fails a not-yet-dispatched call to an M6-only tool as
  `unknown_tool`; `0.2`'s daemon withholds all skill context of a session with
  a user skill, project skills included, which its offline `loopex resume`
  restores; and `0.2` cannot admit a new user skill.
- The adapter refuses to run while the host sets any global Req default
  options, because those reach every request.
- Model calls use HTTP/1; HTTP/2 waits for a Finch release that handles it
  safely for this adapter.
- Locked ReqLLM's buffered provider builders can generate a replacement for a
  missing tool-call id, turn missing, nil, empty or unsupported arguments into `{}`, force the
  function type, omit a malformed call and remove earlier error metadata before
  Loopex's shared mapper. The mapper fails closed only for malformed binary
  arguments and invalid fields still visible at its seam. An omitted call
  executes nothing; a normalized `{}` remains subject to tool resolution,
  schema validation and policy.
- A model's reply arrives whole, with no streamed progress, in the ephemeral
  profile.
- Each call owns a new tagged pool and uses a fresh connection. Cleanup removes
  the owned pool; a checked-out transport may drain asynchronously as stated
  above, and the persistent `Req.Finch` infrastructure retains neither request
  nor connection.
- The exact resolved credential is refused if a provider echoes it in a reply;
  transformed or encoded derivatives are not claimed detectable.
- A provider response body over 8 MiB, or one with a content encoding, is
  refused after dispatch; the in-process adapter never performs response
  decompression.
- Same-VM host code is trusted and can deliberately race a guard or tamper with
  ReqLLM's registry or request routing after validation; the final adapter
  closes the route it can validate but is not a sandbox from its host.
- The local executor's path checks, including the read-only walker, do not pin
  directory handles. A concurrent same-user process can race a pathname check
  and filesystem access, so these tools do not claim confinement against an
  adversarially changing workspace or mount.
- The read-only walker materializes one directory's complete entry-name list
  before it can sort or apply its traversal caps. The caps bound the subsequent
  walk and output, not enumeration or allocation for one exceptionally large
  directory.
- The public named-skill helper walks and reads each pack once without following links at
  depth 32, 256 visited directories, 4,096 entries and 1 MiB of
  pack-root-relative path bytes before applying the existing 64-file and 1 MiB
  content limits. Its portable filesystem API also materializes one named
  directory's complete entry-name list before those traversal caps apply, so one
  exceptional directory remains an unbounded synchronous input cost.
- The daemon is unchanged, so a durable session with a user skill that is
  resumed through the daemon has all of its skill context withheld, project
  skills included.

### Design Decisions

Technical depth: [Prerequisites and acceptance points](M6-technical.md#technical-plan-prerequisites).

One decision is proposed with this plan:

| Decision | What it settles | Outcomes that wait on it |

**Decisions settled here rather than in an ADR,** because each is host behaviour
or internal structure that no accepted decision binds:

- The embedded API lives in `loopex_composition` and follows the session only
  through core's public facade.
- The `ask` command and its `-p` alias are a new subcommand beside `run`. The
  existing parser grammar and `run`'s behaviour are unchanged.
- The escript's generated wrapper starts no project application. The CLI main
  owns the command split: invalid `ask` input starts nothing, only a valid
  ephemeral form enters the bounded composition bootstrap directly, valid
  durable `ask` uses the ask-specific fixed-diagnostic helper, and every pre-M6
  command uses the private exact-Mix-compatible legacy-start helper first.
- In text mode, standard error for `ask` carries the same bounded tool and
  ending summaries as `run`. JSON mode carries those facts only in its object;
  its standard error is empty for a proved outcome and otherwise carries only
  the fixed command or retained-root diagnostic. `run` and the daemon keep
  their exit statuses.
- The attended-release runner keeps a person answering by default.
- The new read-only tools are defined for every composition and active only
  where a composition names them.

**Maintainer decisions recorded for this plan (2026-09-26):**
- every model in the ephemeral profile, local or hosted, runs through one
  in-process ReqLLM path with more guards, and the vision, and AGENTS.md's
  matching non-negotiable, are amended for its credential exposure; this
  replaces the earlier choice to keep hosted models on the companion, and the
  durable profile keeps the companion;
- user skill directories are admitted in both profiles, the project skill
  winning a shared name;
- the durable profile may activate the new read-only tools, with the rollback
  claim narrowed accordingly;
- the ReqLLM call and result path are non-streaming in one sensitive caller,
  and each call owns one uniquely tagged Finch pool plus its one-shot dispatch
  adapter;
- model calls use HTTP/1 in M6, with HTTP/2 as future work gated on Finch.

**Selected implementation boundary:** the ReqLLM call and result path are
non-streaming and run in one sensitive caller, while each call
owns a uniquely tagged Finch pool and one-shot dispatch adapter. Cleanup ends
the caller and locally tears down that pool. This replaces both the earlier
streaming-tree walk, which could not be made complete, and the later shared
pool plus `Connection: close` design, which could neither force peer closure
nor prevent retained TLS session state.

**Prerequisites that are not ADRs.** M5 closure is satisfied (2026-09-26). The
M7, M8 and M9 drafts are refined, not accepted, during M6.

### How Each Outcome Is Verified

Technical depth: [Evidence obligations and mapping](M6-technical.md#technical-plan-evidence).

Acceptance also means the plan is ready to implement. An implementer may make
ordinary private coding choices, but may not have to invent a public return,
process owner, lifecycle transition, failure precedence, trust boundary,
dependency route or proof strategy. Any such open choice is a plan defect to
resolve before its workstream starts, not an implementation detail to settle in
code.

Verification is the current suite plus the two check commands.

**The fast check** proves, credential-free:
- the embedded API against a scripted model;
- the memory store's conformance and the ephemeral composition;
- the in-process adapter's mapping, options, errors and host hygiene against
  a scripted ReqLLM transport, and the local teardown of its caller and tagged
  pool against HTTP and TLS test servers, including failures before the
  one-shot adapter and before delegation;
- the adapter's guards, one-shot dispatch fence, concurrent pool isolation,
  hosted-provider HTTPS requirement, scoped key-log-file behavior, TLS
  non-resumption, exact-value reply gate, and a canary credential's absence
  from every Loopex plane;
- the command grammar, output modes, JSON contract and exit map;
- agent delegation: a separate OS process running `loopex -p` and reading its
  JSON;
- the read-only tools, skill directories and each tool preset's measured
  context size;
- the closure tooling against fixtures.

**The release check** grows from nine real-provider rows to eleven: the
ephemeral profile through `loopex -p` against a local Ollama model with no
credential, and the embedded API in-process against Anthropic, the provider the
release credential serves. A credential-free `rollback` lane runs
beside them.

A reachable local Ollama model becomes a stated release-host precondition. If it
is missing, that is evidence unavailable, not a skip.

**Also required:**
- The M5 suites and lanes pass. Version-literal expectations become
  version-derived, and the one exact tool-definition inventory assertion moves

  the original four. Core's runtime library diff from `v0.2.0` is empty.

- An independent read-only security review of the in-process credential path
  names the tested SHA and is retained with its digest.
- Closure follows the two-commit procedure, run with outcome 6's repository

## Workstreams

P2's governance documentation lands first, before any provider-touching merge.
Five implementation workstreams then have non-overlapping ownership and one
integrator:

1. model adapter and memory store;
2. the complete local-executor change, including its inward gate boundary;
3. composition, after the first two foundations rejoin;
4. the command, after composition;
5. closure tooling and documentation.

The first two workstreams may develop in parallel and rejoin in either order;
the remaining order is fixed. The single acceptance demonstration is written
first as a failing script, but incomplete workstreams use their focused evidence
witnesses as rejoin checks. The complete demonstration first becomes runnable
after the command rejoins; closure evidence is retained only from the closure
candidate on each platform.
