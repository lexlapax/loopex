## Concept

Technical depth: [Prerequisites, evidence, compatibility and packaging](M6-technical.md#technical-depth).

<a id="concept-plan-purpose"></a>
### Purpose

Technical depth: [Prerequisites and acceptance points](M6-technical.md#technical-plan-prerequisites).

**M6 is the installed durable operator milestone, the `0.3.0` candidate.** Its
product question is:

> Can an operator download Loopex, configure it once, run the daemon without a
> source checkout or an Elixir toolchain, preserve and migrate sessions
> safely, and inspect exactly which configuration is in effect?

That is one coherent loop, and the milestone is that loop end to end:
install, configure, run, disconnect, restart, resume, back up or restore.

Today Loopex is usable in the narrow sense and not in the ordinary one. The
foreground loop works and M5 makes it a daemon, but every capability sits on
a source tree: the operator index says Loopex is not packaged or published for
consumers, the coding-sessions guide calls the CLI a source-tree surface, the
provider companion records absolute build-tree paths, the state root is a
required environment variable with no default, and the `0.2` store is a
full-replay log that stops at 256 MiB and asks the operator to retire the
root. M5 states each of those limits truthfully and excludes their removal by
name. M6 removes them.

| Capability | Today | After M5 | M6 target |
| --- | --- | --- | --- |
| Real coding work | Working foreground loop | Working daemon loop | The same loop from an installed artifact |
| Installation | Build from a clean Git checkout | Build from a source archive | Download, verify, extract, run |
| Runtime requirement | Git, Mix, Elixir/OTP | Mix, Elixir/OTP | None; the runtime system is bundled |
| Session operation | Run, list, resume, cancel | Daemon, attach, takeover, reconnect | The same, with stable paths and diagnostics |
| Configuration | Flags and environment variables | More flags and environment fallbacks | Saved, typed, validated host configuration with a visible effective view |
| Persistence | Full-replay local log | The same log, 256 MiB ceiling, root retirement | Daemon-grade indexed store with explicit migration, backup and restore |
| Verdict | Maintainer and developer usable | Source-operator usable | Ordinary local-operator usable |

**Why this rung, and why now.** The roadmap projects a governed extension
runtime as the `v0.3` candidate, and it also says its labels are navigation
aids and an accepted plan may resequence projected work beneath the vision's
serial barriers. Two facts argue for inserting this rung before extensions.
First, M5 leaves the daemon-grade store and its migration to its successor by
ADR 0031's own words; publishing a binary around a full-replay log that
terminates at 256 MiB would solidify the wrong operator experience at the
moment it first becomes public. Second, governed extensions bring their own
set of trust and durability problems: package acquisition, retained artifacts,
VM-global loading, quiescence, state upgrade and downgrade, signing,
activation and exact rollback. Combining those with a store migration, a
configuration schema, credential references and the first binary release
would make one milestone carry four. So the sequence is M6, the installed
durable operator, then the governed extension runtime as its successor. The
serial barriers are respected: durable local truth and multi-client
attachment precede this rung, and extension namespaces and activation proof
still precede any public-protocol decision. The roadmap projection is
updated when this plan is accepted, not before.

**What is deliberately not in M6.** No trusted extension activation, no typed
decision models or ADR 0035 evaluation seams, no live model switching, no
protocol v1, no Hex publication, no service-manager installation, no
automatic updates, no desktop or rich terminal UI, no multi-user identity, no
isolated hands, no remote workers, and no persistent credential store.

**The M5 baseline.** M6 is a planning candidate beside the accepted M5 and
cannot be accepted or implemented until M5 closes, because every M6 outcome
starts from the exact `0.2` root, daemon and workflow M5 proves. The register
says so and enforces it.

<a id="concept-plan-outcomes"></a>
### Outcomes

Technical depth: [Evidence obligations and mapping](M6-technical.md#technical-plan-evidence).

| # | Outcome | Proved by |
| --- | --- | --- |
| 1 | **Installed distribution.** One platform-specific release archive per supported platform, with the runtime system bundled, the existing `loopex` launcher promoted as the one installed command, the protected provider companion inside it discovered relatively and verified by digest, and a manifest with source commit, toolchain, platform, file digests and archive checksum | A clean supported host with no Git, Mix, Elixir or Erlang installed verifies, extracts and runs the exact archive; the manifest verifies from inside the installation |
| 2 | **Host configuration.** A versioned closed-schema `config.json` under a default home, named provider profiles with credential references, an explicit policy selection, one precedence rule, per-value provenance, atomic writes and a redacted effective view | An empty temporary home is initialized, configured, validated, restarted and shown to produce the same effective configuration; every refusal names its exact path |
| 3 | **Daemon-grade persistence.** An evidence-selected store adapter behind the unchanged private Store ports, with bounded open and replay, a definite survivable capacity refusal, explicit `0.2` migration that converges when interrupted, and backup and restore | The shared conformance suite and the fault matrix on the new adapter, the measured open and replay bounds, and the migration, interrupted-migration and restore demonstrations |
| 4 | **Operator lifecycle.** `version`, `paths`, `init`, `config`, `doctor`, `store migrate`, `store backup`, `store restore` and `daemon status` beside the existing session commands, each with a stable exit class | An operator diagnoses a missing configuration, a bad path, an unresolvable credential reference, a store fault, a pending migration and a version mismatch from the command output alone, never from internal files |
| 5 | **Packaged workflow.** The M5 daemon collaboration workflow driven entirely through the installed artifact | A real provider session, detach, observer attach, takeover, daemon restart, list, resume and completion, from the installed command on both supported platforms |
| 6 | **Upgrade and rollback.** An exact reader boundary and recovery procedure between `0.2` and `0.3` roots and between the two binaries | A `0.2` root migrates to `0.3`; an interrupted migration converges; the `0.2` binary refuses the `0.3` root by name; the pre-migration backup restores under the previous release and serves the sessions it held |

**The single acceptance demonstration** begins with an empty temporary home
and the released archive on each supported platform: verify the artifact,
initialize the configuration, select a provider profile and a credential
reference, run `doctor`, start the daemon, complete real work, disconnect and
reattach, restart the daemon, list and resume the session, then back up and
restore or migrate the root. It proves that nothing is written outside the
selected home, the workspace and the explicitly selected temporary
locations.

<a id="concept-plan-scope"></a>
### Scope

Technical depth: [Ownership and rejoin](M6-technical.md#technical-plan-ownership).

**Distribution.** A `mix release` of the umbrella per supported platform,
macOS on Apple silicon and Linux on x86-64, with ERTS included. The launcher
gains one branch to find the release beside itself and otherwise keeps its
interrupt contract verbatim. The provider build task writes release-relative
paths and the launch configuration resolves them once at start. A manifest
and a checksum file accompany every archive. `loopex version` reads the
manifest; `loopex version --verify` recomputes it. The source archive M5
produces still builds the same release. Publication is not scope; retaining
the built artifact with its evidence is.

**Configuration.** One module family in the reference host that reads,
validates, resolves and writes `config.json` and produces the composition
options the existing composition already validates. The default home is
`~/.loopex`; `LOOPEX_HOME` and `--state-root` override it in that order of
precedence, below flags. Six closed domains: paths, daemon, runtime,
providers, policy, diagnostics. No policy and no credential has a permissive
default. A change takes effect at the next daemon start.

**Persistence.** A new store adapter application selected by the retained
experiment ADR 0036 prescribes, running the shared conformance suite and the
fault matrix; `loopex store migrate`, `backup` and `restore`; a format version
in the root; a `0.2` reader boundary; a definite capacity refusal proved on
every adapter. The daemon's listing index is rebuilt from a migrated root.

**Operator surface and documentation.** The lifecycle commands above, each
with an exit class added to the M5 exit-status map, and an operator guide
that starts from a downloaded archive rather than a checkout. The developer
documentation states what M6 changed for its reader.

**Version.** `VERSION` moves from `0.2.0` to `0.3.0` in the tested candidate,
under the 0.x policy.

<a id="concept-plan-non-goals"></a>
### Non-Goals

Technical depth: [Deferral acceptance points](M6-technical.md#technical-plan-prerequisites).

No change to core beyond what the new adapter and the definite capacity
refusal require through the existing ports, and no new core dependency. No
trusted extension activation, extension source configuration, package
acquisition or VM-global loading; those retain their vision barrier and their
own milestone. No ADR 0035 evaluation, no second provider, no live model
switching. No protocol change: generation 2 is served unchanged and no
generation 3 exists. No Hex packages, no Homebrew or distribution packages,
no installer beyond extract-and-run, no service-manager units, no automatic
updates, no self-update command. No persistent credential store, keychain
integration or credential bytes in any file Loopex writes; a credential is a
reference to an environment variable in `0.3.0`. No project-local
configuration until a project-trust rule exists. No hot reload of
configuration. No multi-user identity, tenancy, isolated hands or remote
workers. No platform beyond the two named; a build that succeeds elsewhere is
not a supported platform. No compaction policy, retention cutoff or history
rewrite in the new store beyond sealing and compacting segments of unchanged
records.

<a id="concept-plan-decisions"></a>
### Design Decisions

Technical depth: [Prerequisites and acceptance points](M6-technical.md#technical-plan-prerequisites).

Three decisions are proposed with this plan. Each is accepted before the
implementation that depends on it, not before unrelated work, and none may be
outstanding at closure.

| Decision | What it settles | Outcomes that wait on it |
| --- | --- | --- |
| [ADR 0036](../adr/0036-daemon-grade-store-engine-and-migration.md#concept) | The selection procedure and criteria for the daemon-grade store engine behind the unchanged private ports, with the engine cell filled from a retained measured experiment before acceptance; the explicit, offline, idempotent `0.2` migration that converges when interrupted; backup and restore as the rollback; the `0.2` reader boundary; the definite survivable capacity refusal. Supersedes ADR 0031's selection | 3, 6 |
| [ADR 0037](../adr/0037-host-configuration-and-path-discovery.md#concept) | The default home resolved by the reference host's launcher and configuration layer only, as a narrow amendment to ADR 0003; one closed versioned schema in six domains; one precedence rule; per-value provenance; atomic conservative writes; credential references and no credential bytes; an immutable snapshot at composition with no hot reload | 2, 4 |
| [ADR 0038](../adr/0038-installed-distribution-and-release-artifact.md#concept) | One platform-specific OTP release archive with ERTS bundled as the binary release; the existing launcher promoted as the one installed command; the provider companion inside the release, discovered relatively and verified by digest; the manifest and checksum; the two supported platforms; the install, upgrade, rollback and uninstall contract; publication as a separate maintainer decision gated on name clearance | 1, 5 |

**Decisions settled here rather than in an ADR**, because each is internal
structure or a naming choice that no accepted decision binds:

- The release's application list is drawn from the umbrella's role table, so
  a new adapter joins the release by the same reviewed change that admits it
  to the dependency budget.
- The configuration layer lives in `apps/loopex_cli`, beside the launcher and
  the command grammar, and produces exactly the keyword list
  `LoopexComposition.start/1` validates; nothing below the reference host
  reads the file or the home.
- Every new command's exit classes extend the M5 exit-status map from the
  next free value, keeping the map contiguous and injective.
- The daemon's listing index is rebuilt from the migrated root rather than
  migrated, because ADR 0032 defines it as a projection.

**Prerequisites that are not ADRs.** M5 closes before M6 can be accepted;
public-name clearance completes before any artifact is published, which is
after closure and outside this plan.

<a id="concept-plan-verification"></a>
### How Each Outcome Is Verified

Technical depth: [Evidence obligations and mapping](M6-technical.md#technical-plan-evidence).

Verification is the current suite plus the two check commands. The fast check
proves the configuration layer, the launcher's release branch, the new
adapter's conformance and fault matrix, the migration and restore mechanics
against fixtures, and every exit class, credential-free. The release check
gains one installed-artifact lane per supported platform, run on a host of
that platform with no toolchain on the `PATH`, which performs the single
acceptance demonstration end to end with the real provider and retains its
output, manifest and digests outside the repository. Closure follows the
two-commit procedure the milestone guide fixes from M5 onward.

<a id="concept-plan-rollout"></a>
### Rollout and Compatibility

Technical depth: [Compatibility](M6-technical.md#technical-plan-compatibility).

Technical depth: [Migration and rollback](M6-technical.md#technical-plan-migration).

Technical depth: [Packaging](M6-technical.md#technical-plan-packaging).

`0.3.0` is a minor release under the 0.x policy. It creates two experimental
surfaces, the configuration schema and the released archive contents, and one
private migration, the store format. Every `0.2` root migrates forward once by
an explicit command; a `0.2` binary refuses a `0.3` root by name; the
pre-migration backup restores under the previous release. The public
protocol, the embedded API and the executor protocol are unchanged. The
source tree keeps working as before for developers; the released offline
commands keep their flag and environment behaviour when no home is
initialized.

## Workstreams

Four workstreams with non-overlapping ownership, one integrator, rejoin in
the order the technical plan fixes: distribution, configuration and lifecycle
commands, store adapter and migration, operator and developer documentation.
The single acceptance demonstration is written first as a failing script and
turned green as each workstream lands.
