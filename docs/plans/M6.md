<a id="concept-plan-purpose"></a>
### Purpose

Technical depth: [Prerequisites and acceptance points](M6-technical.md#technical-plan-prerequisites).

**M6 is the minimal runnable Loopex, the `0.3.0` candidate.** Its product
question is:

> Can Loopex be run as a minimal standalone agent loop — called from an
> Elixir host in one function call, from a shell or from another agent in one
> command — and still be the full durable Loopex when that is what the caller
> asks for, all over one kernel?

Loopex already is a working coding harness, but only in its heaviest form.
Every composition needs:

- a state root on disk and the local store;
- a provider companion BEAM with a built worker artifact and digests;
- a named policy and its identity;
- one pinned model.

The command needs a subcommand, `--policy`, `LOOPEX_HOME` and the companion
build. It has no model flag and no machine-readable output, and a failed run
exits 0. Nothing lets a host ask one question and get one answer.

M6 does not write a second, simpler loop, because the vision forbids a surface
owning an alternate loop. It composes the existing kernel with lighter parts
behind its existing ports:

- a memory store;
- an in-process model adapter;
- the local executor on a temporary root.

The result is three instances of one Loopex:

| Instance | Called by | Composed with | Promises |
| --- | --- | --- | --- |
| **Embedded, ephemeral** | An Elixir host: `Loopex.run/2`, `start_session/1`, `ask/2`, `history/1`, `stop_session/1` | The memory store, the in-process model adapter, the local executor | A whole multi-turn session inside one VM; nothing persists; no recovery claim |
| **Standalone command** | A shell, CI or another agent: `loopex -p "…"` | The ephemeral profile by default; the durable profile with `--state-root` | The answer on stdout, JSON when asked, an exit status that reports the run's outcome |
| **Full Loopex** | Operators and multi-client work | The durable local store, the provider companion, the daemon | Everything M1 to M5 proved, unchanged |

**Why this rung, and why now.** A second person, or a second agent, can use
Loopex only once it can be called without assembling the durable stack. Every
comparable minimal harness offers exactly that: one library call, one command
and a small fixed tool set. The installed operator milestone, drafted as M7,
depends on it, because its configuration and lifecycle commands sit on top of
the profiles and the command form M6 fixes.

The new sequence, recorded here and projected into the roadmap on acceptance:

- **M6:** this milestone, the minimal runnable Loopex.
- **M7:** the installed durable operator.
- **M8:** the store engine successor.
- **M9:** the governed extension runtime.

M7, M8 and M9 are drafted in [docs/drafts](../drafts/README.md) and are
refined as M6 proceeds.

**The M5 baseline.** M5 closed on 2026-09-26 at the tested implementation
`fe020e24` (administrative closure `3f81b048`, tagged `v0.2.0` and integrated
on `main`). The full Loopex instance is that closed baseline, and M6 changes
none of its bytes' meaning.

**The single acceptance demonstration**, on macOS and on Linux from a clean
checkout, with no `LOOPEX_HOME`, runs four things in turn:

1. `Loopex.run/2` answers a coding question against a local Ollama model with
   the four coding tools and one skill directory.
2. `loopex -p … --output json` does the same from a shell, and exits non-zero
   when the run is made to fail.
3. A second agent delegates a task to `loopex -p` and reads the JSON result.
4. The same prompt with `--state-root` runs under the durable profile and is
   resumable, exactly as in M5.

<a id="concept-plan-scope"></a>
### Scope

Technical depth: [Ownership and rejoin](M6-technical.md#technical-plan-ownership).

**Kernel facade.** Five thin public functions in `apps/loopex` over the
existing facade: `create_session`, `attach`, `command` and `next_event`. They
add no state and no second loop, and they return the assistant's final text,
or `{:error, reason}` with the run outcome.

**Model.** One in-process ReqLLM adapter in `apps/loopex_llm_reqllm` beside the
companion adapter. Composition selects exactly one per runtime, by profile.

**Store.** `Loopex.Store.Memory`, promoted from the core test fixture into an
edge module that passes the store conformance suite, with its artifact half.

**Composition.** One ephemeral entry in `apps/loopex_composition` that
produces the runtime options the kernel already validates.

**Command.** The `-p` form in `apps/loopex_cli`: flags, a prompt on stdin,
text or JSON output, the outcome exit map, and skill directories by path.
Naming the path is the admission decision.

**Tools.** The read-only `grep`, `find` and `ls` join the local executor behind
the existing tool contract. They complete the vision's seven-tool surface and
form a `:read_only` preset. The default `:coding` set stays `read`, `write`,
`edit` and `bash`.

**Closure tooling.** Repository commands for:
- the five-path confinement proof;
- the hostile-umask archive staging and archive-identity comparison;
- the floor lane's preconditions: the open-file limit, default signal
  dispositions and no `nohup`;
- a supported way to run the attended release cases.

**Documentation.** A getting-started path for each instance, and the operator
and developer pages the profiles change.

**Version.** `VERSION` moves from `0.2.0` to `0.3.0` in the tested candidate.

<a id="concept-plan-non-goals"></a>
### Non-Goals

Technical depth: [Deferral acceptance points](M6-technical.md#technical-plan-prerequisites).

- **The M7 draft's scope:** no installed release archive, no saved
  configuration file, no default home, no provider profiles, and no lifecycle
  commands beyond `-p`.
- **The M8 draft's scope:** no store engine, migration, format marker, backup
  or restore.
- **The M9 draft's scope:** no extension activation.
- **Model features:** no model switching within a run.
- **Protocol:** no protocol change.
- **Integrations:** no MCP client or server.
- **Loop features:** no streaming UI, no parallel tool fan-out, no
  multi-agent trees and no progressive skill disclosure.
- **Persistence:** no persistent memory for the ephemeral profile, and no
  migration between profiles.
- **Publication:** no Hex publication; that is a separate later decision.
- **Core:** no change to core's dependency list, and no weakening of the
  durable profile's credential isolation.

<a id="concept-plan-decisions"></a>
### Design Decisions

Technical depth: [Prerequisites and acceptance points](M6-technical.md#technical-plan-prerequisites).

One decision is proposed with this plan:

| Decision | What it settles | Outcomes that wait on it |
| --- | --- | --- |
| [ADR 0039](../adr/0039-ephemeral-embedded-profile.md#concept) | Two composition profiles over one kernel. The ephemeral profile: the memory store's truth statement, the in-process model adapter and its credential rule, and the default Ollama model. The durable profile keeps ADRs 0019 and 0034 unchanged. Neither profile has a default authority | 1, 2, 3, 4 |

**Decisions settled here rather than in an ADR,** because each is host behaviour
or internal structure that no accepted decision binds:

- The facade functions live in core's public module and call only its existing
  public facade. The composition entry, not core, knows about memory stores or
  adapters.
- The `-p` form's exit map extends the existing CLI statuses from the next free
  value. A successful run exits `0`, and each other outcome has its own status.
  The existing `run` subcommand keeps its documented behaviour.
- `--output json` writes exactly one JSON object on stdout at the end of the
  run: the final text, the outcome, the session id, usage and the model
  identity. Progress, when asked for, goes to standard error.
- Skill directories passed by path are admitted by that act. Project-local
  discovery keeps its existing explicit prompt.

**Prerequisites that are not ADRs.** M5 closure is satisfied (2026-09-26). The
M7, M8 and M9 drafts are refined, not accepted, during M6.

<a id="concept-plan-verification"></a>
### How Each Outcome Is Verified

Technical depth: [Evidence obligations and mapping](M6-technical.md#technical-plan-evidence).

Verification is the current suite plus the two check commands:

- **The fast check** proves the facade, the memory store's conformance, the
  composition entry, the command grammar and exit map, the new read-only tools
  and the adapter's mapping against a scripted ReqLLM stub. It is
  credential-free.
- **The release check** gains ephemeral-profile real-provider lanes, one against
  a local Ollama model and one against a hosted provider, and the
  agent-delegation lane.

The M5 lanes run unchanged. Closure follows the two-commit procedure, run with
outcome 6's repository commands.

### Rollout and Compatibility

Technical depth: [Compatibility](M6-technical.md#technical-plan-compatibility).

Technical depth: [Migration and rollback](M6-technical.md#technical-plan-migration).

`0.3.0` is a minor release under the 0.x policy. It adds three experimental
surfaces: the facade functions, the `-p` command form and the ephemeral
profile's model strings. It changes no durable byte, protocol or executor
contract, and every M2 to M5 invocation keeps working. On acceptance the
roadmap names this rung the `v0.3` candidate and moves the later rungs by one
label, as the drafts record.

## Workstreams

Four workstreams with non-overlapping ownership and one integrator, rejoining
in the order the technical plan fixes:

1. model adapter and memory store;
2. composition and facade;
3. command and tools;
4. closure tooling and documentation.

The single acceptance demonstration is written first as a failing script and
turned green as each workstream lands.
