<a id="concept-plan-purpose"></a>
### Purpose

Technical depth: [Prerequisites and acceptance points](M6-technical.md#technical-plan-prerequisites).

**M6 is the minimal runnable Loopex, the `0.3.0` candidate.** Its product
question is:

> Can Loopex be run as a minimal standalone agent loop — called from an
> Elixir host in one function call, from a shell or from another agent in one
> command — and still be the full durable Loopex when that is what the caller
> asks for, all over one kernel?

Loopex already is a working coding harness, but only in its heaviest form.
Every composition needs:

- a state root on disk and the local store;
- a provider companion BEAM with a built worker artifact and digests;
- a named policy;
- one pinned model.

The command needs a subcommand, `--policy`, `LOOPEX_HOME` and the companion
build. It has no model flag and no machine-readable output, and a failed run
exits 0. Nothing lets a host ask one question and get one answer.

M6 does not write a second, simpler loop: the vision forbids a surface owning
an alternate loop. It composes the unchanged kernel with lighter parts behind
its existing ports:

- a memory store;
- an in-process model adapter that runs ReqLLM inside the host's VM for a
  local Ollama model and for the hosted providers, reading a hosted provider's
  credential at the moment of each call;
- the local executor on a temporary root.

The result is three instances of one Loopex:

| Instance | Called by | Composed with | Promises |
| --- | --- | --- | --- |
| **Embedded, ephemeral** | An Elixir host: `LoopexComposition.Ephemeral.run/2`, `start_session/1`, `ask/3`, `answer/3`, `last_result/1`, `history/1`, `stop_session/1` | The memory store, the in-process model adapter, the local executor | A whole multi-turn session inside one VM; nothing persists; no recovery claim |
| **Standalone command** | A shell, CI or another agent: `loopex ask "…"`, or its alias `loopex -p "…"` | The ephemeral profile by default; the durable profile with `--state-root` | The answer on stdout, or one JSON object when asked; an exit status that reports the run's outcome |
| **Full Loopex** | Operators and multi-client work | The durable local store, the provider companion, the daemon | Everything M1 to M5 proved, plus named skill directories and optional model, bound, sampling and active-tool options |

The embedded API lives in `loopex_composition`, not in core. Assembling the
memory store, the adapter and the executor is exactly the work the dependency
direction keeps out of core, and M6 leaves core's runtime library unchanged.
The closure tooling's two Mix tasks join core's existing development tasks.

**Why this rung, and why now.** A second person, or a second agent, can use
Loopex only once it can be called without assembling the durable stack. Every
comparable minimal harness offers exactly that: one library call, one command
and a small fixed tool set. The installed operator milestone, drafted as M7,
depends on it, because its configuration and lifecycle commands sit on top of
the profiles and the command M6 fixes.

The new sequence, recorded here and projected into the roadmap on acceptance:

- **M6:** this milestone, the minimal runnable Loopex.
- **M7:** the installed durable operator.
- **M8:** the store engine successor.
- **M9:** the governed extension runtime.

M7, M8 and M9 are drafted in [docs/drafts](../drafts/README.md) and are
refined as M6 proceeds.

**The M5 baseline, and permission to rework it.**
- **Baseline:** M5 closed on 2026-09-26 at the tested implementation `fe020e24`
  (administrative closure `3f81b048`, tagged `v0.2.0`, integrated on `main`).
- **Rework permission:** the maintainer authorized M6, on the same day, to rework
  code delivered by M1 to M5 where the minimal profile needs it. M6 uses that
  permission for a small set of changes, each additive and each held to the
  unchanged M5 suites:
  - the durable composition gains model, bound, sampling, active-tool and
    skill-directory options, and its default policy revision stops following
    the release version;
  - ReqLLM is no longer started automatically with the adapter's application;
  - the companion's pure request mapping is shared;
  - the executor clears every provider credential variable from tool processes;
  - the memory store is promoted from a test wrapper;
  - three read-only tools are defined;
  - the release check gains two rows and a rollback lane.
- **What the permission does not cover:** the vision's non-negotiables. Those
  are dependency direction, one serial owner, durability truth, plain boundary
  data, and credential isolation.

**The single acceptance demonstration**, on macOS and on Linux from a clean
checkout, with no `LOOPEX_HOME`, runs four things in turn:

1. `LoopexComposition.Ephemeral.run/2` answers a coding question against a
   local Ollama model with the four coding tools and one skill directory, with
   no credential set.
2. `loopex -p … --output json` does the same from a shell, and exits with the
   `failed` status when the run is made to fail.
3. A second process delegates a task to `loopex -p` and reads the JSON result.
4. The same prompt with `--state-root` runs under the durable profile and is
   resumable exactly as in M5. This step needs what the durable profile always
   needs: the built companion and `LOOPEX_PROVIDER_API_KEY`.

The demonstration is `scripts/m6-demonstration.sh`. Each platform's run is
retained with its reference and SHA-256 digest in the M6 evidence page, and
closure needs both.

**The embedded API.** One module in `loopex_composition` that composes the
ephemeral profile and follows the session through core's existing public
facade. It returns the last assistant text on `completed`, and the outcome's
fixed details for every other outcome. A policy that defers is surfaced as a
pending interaction and is not answered for the host. Stopping removes the
temporary root only when the session's tool processes and every process
that could return a provider result are proved gone;
otherwise it returns `cleanup_unproved` and names the kept root.

**The model adapter.**
- **One path:** in the ephemeral profile every model, local or hosted, runs
  through one in-process adapter in `loopex_llm_reqllm` that calls ReqLLM
  inside the host VM, sharing the companion's pure request and reply mapping.
  The durable profile keeps the companion for every model and refuses `ollama:`
  in M6.
- **Credentials:** the runtime names each hosted provider's credential
  variable; the one process that makes a call reads it immediately before the
  call and passes it to ReqLLM for that call only. That process is excluded
  from Loopex tracing and marked sensitive. The value stays out of every Loopex
  plane, but while the call is in flight it is inside ReqLLM, Req, Finch and TLS
  processes, where a crash report, a crash dump or a host telemetry handler can
  see it; ADR 0039's vision amendment accepts that for this profile only.
- **Guards:** the adapter refuses to call while `:req`'s global default options
  are set, or while ReqLLM's registered module for the provider is not its own.
  Every call names its address explicitly, never taking one from ReqLLM's
  configuration or catalog, allows no retry, follows no redirect, uses no
  response cache, and never hands the call to a ReqLLM task.
- **Loopex's own pools:** each call names a connection pool whose options
  Loopex fixes, so nothing the host configured for ReqLLM's shared pool can
  carry it. The pool follows the address's scheme: `https` uses HTTP/2,
  multiplexed, with each connection retired after a fixed maximum age, and
  such an endpoint must offer HTTP/2; plain `http`, such as a local Ollama or
  OpenAI-compatible server, uses HTTP/1.
- **Failures stay contained:** the calling process catches every failure and
  ends with a fixed reason, so no exception carrying the request or its
  credential reaches the cleanup owner, which is also marked sensitive.
- **Dispatch boundary:** the provider call itself is the boundary. Anything that
  fails before it may be retried by the kernel. Anything from the call on is
  treated as possibly sent and never retried.
- **In-flight cleanup:** each call has one cleanup owner that the kernel's
  existing provider cleanup owns from before the call starts, and that stays
  responsive throughout, and one calling process that alone can return a
  result. On a stop or a deadline the owner kills that process; on completion
  it exits itself; the owner acknowledges, or returns the reply, only after it
  has seen it exit. Shared connection and TLS processes close the call's
  connection afterwards; nothing they hold can reach the session. The reply
  arrives whole, with no streamed progress.
- **Host hygiene:** Loopex starts ReqLLM itself, never the OTP application
  graph, after turning off its automatic `.env` loading as a persistent setting
  and marking that it did, so later compositions, and later restarts of
  ReqLLM, stay clean. A ReqLLM the host started is accepted only when the host
  declares it with `.env` loading off, and one running with loading on is
  refused. Every model is named inline, so no catalog lookup or
  unverified-model warning occurs, and Loopex changes no other ReqLLM setting.

**The store.** `Loopex.Store.Memory`: the shipped pure store state that the
local store replays, behind a small supervised process, the same logic the
conformance suite already proves in memory. There is no artifact store in the
ephemeral profile, so oversized tool output is truncated with the existing
notice.

**Composition.**
- The ephemeral profile as above.
- On the durable `LoopexComposition.start/1`: optional `:model`, `:bounds`,
  `:sampling`, `:active_tools` and `:skill_directories`, whose defaults
  reproduce M5 exactly.
- `ResourcePacks.read_directories/2` builds a resource manifest from named skill
  directories, classified against the workspace root: a project skill
  (`.agents/skills/<name>` in the workspace) as `project:<name>`, a user skill
  (outside the workspace, such as `~/.agents/skills/<name>`) as `user:<name>`,
  and the project skill winning a shared name, in both profiles.

**The command.**
- `loopex ask`, and its `-p` alias, in `loopex_cli`: text or JSON output and the
  prompt from words or stdin.
- **JSON output:** exactly one object whose members are the ones ADR 0039 lists:
  `schema`, `session_id`, `run_id`, `profile`, `outcome`, `text` and
  `text_truncated`, `tools` and `tools_truncated`, `shadowed_skills`,
  `cleanup`, and `details` with fixed members per outcome.
- **Exit map:** `0` for completed, `1` for a refusal before the run, `2` to `5`
  for failed, bound reached, outcome unknown and cancelled, `6` for no ending
  within the wait, and the existing `130` interrupt. No `ask` policy defers, so
  `ask` has no deferred-interaction status.
- **Policy names:** `ask` maps `allow-all`, `shell-allowlist` and `refuse-all`
  to the reference CLI's policy modules.
- **Crash output:** `ask` turns the logger off, renders its own lines, and runs
  with crash dumps disabled, so ReqLLM's failure paths cannot write request
  data.
- **Dispatch:** `ask` is an offline form, and `--daemon` is not accepted. The
  CLI's credential discard waits until `ask` has chosen its profile: the
  durable profile then consumes `LOOPEX_PROVIDER_API_KEY` as `run` does, and
  the ephemeral profile discards it unread and reads only the chosen hosted
  provider's own variable at each call.
- **`run`** keeps its behaviour.

**Tools.** `grep`, `find` and `ls` join the local executor as read-only,
workspace-confined, byte-bounded in-VM tools and form a `:read_only` preset.
They are active only where a composition names them, in either profile. The
durable default stays `read`, `write`, `edit` and `bash`.

**Closure tooling.** Two Mix tasks and three shell scripts:
- the five-path confinement proof;
- hostile-umask archive staging;
- the archive-identity comparison;
- the floor lane with its open-file and signal preconditions;
- an attended-release runner using the platform's `script(1)`, in which a person
  answers the attended notices by default. Its automatic mode is refused unless
  the caller names a recorded maintainer disposition that authorizes automatic
  answers for this milestone and this exact candidate commit, as M5's did for
  M5 only.

They are tested against a fixture repository and replace every script the M5
closure kept outside the repository.

**Documentation.** A getting-started path for each instance, and the operator
and developer pages the profiles change, including a library host's
obligations: its own logger and crash dumps for request data, and
`req_llm: :load` in a host's own OTP release.

**Defaults and limits** (all witnessed):
- **Model:** `LOOPEX_MODEL`, then `ollama:llama3.2`.
- **Run:** 16 steps, a 600_000 ms deadline, 4_096 output tokens and a context
  budget of 8_192. The embedded API waits the deadline plus 30_000 ms and polls
  every 10 ms.
- **Presets only for tools,** each measured under ADR 0017's system-class
  limit.
- **At most four skills,** ADR 0025's selection limit.
- **Read-only tools:** 30 s and 16 KiB each, at most 1_000 `grep` matches and
  2_000 `find` or `ls` entries, `ls` depth at most 8, and Elixir `Regex`
  patterns for `grep`.
- **Release:** the release check's Ollama model is named by
  `LOOPEX_RELEASE_OLLAMA_MODEL`. The hosted real-provider row is Anthropic,
  because the release credential is an Anthropic key.
- **API refusals and history:** `ask/3` refuses `:run_open` while a run is
  open. `history/1` returns user, assistant and tool entries in order.
  `stop_session/1` waits an open run's abort for its `cleanup_grace_ms` plus
  5_000 ms. `grep` skips files over 1 MiB.
- **JSON output:** the answer text at most 1 MiB, at most 256 tool entries and
  every other string at most 1 KiB; the prompt at most 1 MiB.
- **Floor lane:** it raises the soft open-file limit to 65_536 (or the hard
  limit) and refuses below 4_096, the values the release check already uses
  (`check-release.sh:42-49`).

**Version.** `VERSION` moves from `0.2.0` to `0.3.0` in the tested candidate.
That changes `Loopex.version()`, and with it the daemon's readiness version.
The durable policy identity's revision no longer follows it: it stays at its
`0.2` value, so a pending interaction survives both the upgrade and a rollback.
The M5 tests that assert the literal `0.2.0` against the running build read
`Loopex.version()` instead. The release check's pinned `release_version` and
`DEVELOPMENT.md` move to `0.3.0`.

<a id="concept-plan-non-goals"></a>
### Non-Goals

Technical depth: [Deferrals and named limitations](M6-technical.md#technical-plan-limitations).

- **The M7 draft's scope:** no installed release archive, no saved
  configuration file, no default home, no provider profiles, no per-provider
  credentials, and no lifecycle commands beyond `ask`.
- **The M8 draft's scope:** no store engine, migration, format marker, backup
  or restore.
- **The M9 draft's scope:** no extension activation.
- **Model features:** no model switching within a run, and no in-process
  adapter in the durable profile.
- **Protocol:** no protocol change.
- **Integrations:** no MCP client or server.
- **Loop features:** no streaming UI, no parallel tool fan-out, no multi-agent
  trees, and no progressive skill disclosure.
- **Persistence:** no persistent memory for the ephemeral profile, and no
  migration between profiles.
- **Publication:** no Hex publication; that is a separate later decision.
- **Core:** no change to core's runtime library or dependency list.
- **Credential isolation:** no weakening of it in the durable profile; the
  ephemeral profile's narrower rule is ADR 0039's vision amendment.
- **Project discovery:** none in the ephemeral profile or `ask`. They admit
  only the skill directories they are given, so a headless caller is never
  prompted.

**Accepted limitations**, named in the technical plan:
- In the ephemeral profile a hosted provider's credential, and every
  request, are inside ReqLLM, Req, Finch and TLS processes while a call is in
  flight, where a crash report, a crash dump or a host telemetry handler can
  see them; ADR 0039 amends the vision to accept that for this profile only.
- ReqLLM's start settings stay for the VM's life.
- A hard VM kill leaves the temporary root, which holds the executor's receipt
  ledger but no committed session truth.
- A durable model must match the single `LOOPEX_PROVIDER_API_KEY` and needs
  the built companion; the durable profile refuses a local Ollama model in M6.
- The ephemeral profile never deletes a host's credential variable, because it
  reads the variable at each call.
- `ask` offers no deferring policy.
- The JSON result carries no usage or model identity, because those are not
  public events.
- An ephemeral session's memory grows with its history.
- An unproved stop keeps the temporary root for the host to remove.
- Rolling back to `0.2` fails a not-yet-dispatched call to an M6-only tool as
  `unknown_tool`; `0.2`'s daemon withholds all skill context of a session with
  a user skill, project skills included, which its offline `loopex resume`
  restores; and `0.2` cannot admit a new user skill.
- The adapter refuses to run while the host sets any global Req default
  options, because those reach every request.
- Over HTTP/2, Anthropic's key stays in the pooled connection until that
  connection is retired, at the later of about five and a half minutes after
  it opened and the deadline of the last call sent on it; and a killed call's
  HTTP/2 stream runs on until the server answers or the call's deadline
  passes. Neither can return anything to the session.
- An `https` model endpoint must offer HTTP/2; the three built-in hosted
  providers do.
- A local model's reply arrives whole, with no streamed progress.
- The daemon is unchanged, so a durable session with a user skill that is
  resumed through the daemon has all of its skill context withheld, project
  skills included.

**Decisions settled here rather than in an ADR,** because each is host behaviour

- The attended-release runner keeps a person answering by default.

**Maintainer decisions recorded for this plan (2026-09-26):**

  replaces the earlier choice to keep hosted models on the companion, and the

- user skill directories are admitted in both profiles, the project skill
  winning a shared name;
- the durable profile may activate the new read-only tools, with the rollback
  claim narrowed accordingly;
- the in-process call is non-streaming and runs in one process, which its
  cleanup ends; presented for confirmation at acceptance, because it replaces
  the maintainer's earlier choice to walk ReqLLM's streaming process tree,

<a id="concept-plan-verification"></a>
### How Each Outcome Is Verified

Technical depth: [Evidence obligations and mapping](M6-technical.md#technical-plan-evidence).

Verification is the current suite plus the two check commands.

**The fast check** proves, credential-free:
- the embedded API against a scripted model;
- the memory store's conformance and the ephemeral composition;
- the in-process adapter's mapping, options, errors and host hygiene against
  a scripted ReqLLM transport, and the cleanup of its calling process against
  a local test server;
- the adapter's guards, and a canary credential's absence from every Loopex
  plane;
- the command grammar, output modes, JSON contract and exit map;
- agent delegation: a separate OS process running `loopex -p` and reading its
  JSON;
- the read-only tools, skill directories and each tool preset's measured
  context size;
- the closure tooling against fixtures.

**The release check** grows from nine real-provider rows to eleven: the
ephemeral profile through `loopex -p` against a local Ollama model with no
credential, and the embedded API in-process against Anthropic, the provider the
release credential serves. A credential-free `rollback` lane runs
beside them.

A reachable local Ollama model becomes a stated release-host precondition. If it
is missing, that is evidence unavailable, not a skip.

**Also required:**
- The M5 suites and lanes run unchanged, except the version literal, and core's
  runtime library diff from `v0.2.0` is empty.
- The acceptance demonstration's retained run on macOS and on Linux.
- An independent read-only security review of the in-process credential path
  names the tested SHA and is retained with its digest.
- Closure follows the two-commit procedure, run with outcome 6's repository
  commands.

`0.3.0` is a minor release under the 0.x policy.

**New experimental surfaces:**
- the embedded API;
- `ResourcePacks.read_directories/2`;
- the `ask` command and its JSON contract;
- the `provider:model` strings.

**Additive reworks of M1 to M5 code:**
- the durable composition's five options, and its default policy revision fixed
  at the `0.2` value;
- ReqLLM removed from automatic application start, the companion already
  starting it explicitly;
- the shared companion mapping;
- the executor clearing every provider credential variable;
- the promoted memory store;
- three defined tools;
- two release rows and the rollback lane;
- the version-literal test expectations.

It changes no durable format, protocol, executor contract or core runtime
library, and every M2 to M5 invocation keeps working. A `0.2` binary resumes
every root `0.3` writes, pending interactions included, except that a
not-yet-dispatched call to an M6-only tool fails as `unknown_tool`, `0.2`'s
daemon withholds all skill context of a session with a user skill, which its
offline `loopex resume` restores, and `0.2` cannot admit a new user skill. There is no new application and no new dependency. On acceptance
the roadmap names this rung the `v0.3` candidate and moves the later rungs by
one label, as the drafts record.

## Workstreams

Four workstreams with non-overlapping ownership and one integrator, rejoining
in the order the technical plan fixes:

1. model adapter and memory store;
2. composition;
3. command and tools;
4. closure tooling and documentation.

The single acceptance demonstration is written first as a failing script and
turned green as each workstream lands.
