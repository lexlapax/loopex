## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Make Loopex usable through one coherent single-machine trace. An embedded caller
starts an explicit runtime, creates or resumes a durable session, sends a real
prompt to a real model, executes one host-granted controlled local tool, and
observes committed events. After the runtime's BEAM OS process is killed at a
defined recovery fault point, a newly started process resumes the same session,
reconciles the effect without dispatching it again, makes the next real model
call, and reaches a durable terminal result.

M0 proved isolated feasibility properties. This milestone turns the minimum set
needed for that trace into product code and claims no more than one machine and
one attached caller.

<a id="concept-plan-scope"></a>
### Scope

Product code intended to survive the milestone: one machine, one attached
caller, one active run per session, explicit runtime references, a durable local
store, a provider-neutral model boundary, a trusted-local executor, and a direct
embedded API. An in-memory implementation supports deterministic conformance
tests for the store's live transaction semantics; it is not presented as a
durable embedding mode. The durable implementation alone proves persistence,
restart, replay, and reconciliation.

The milestone has exactly three product boundary behaviours: store, model, and
executor. The embedded API is a direct runtime facade, not a fourth replaceable
boundary. The host owns policy and issues grants; Loopex coordinates durable
mechanics; the executor alone starts the controlled effect after final
validation.

M0 code is reused only where its behavior conforms to the accepted M1 contracts
and the working trace needs it. M0 journals and retained evidence are not an
installed data source or a compatibility promise for M1.

<a id="concept-plan-non-goals"></a>
### Non-Goals

Multi-client attachment, a portable protocol candidate, a daemon or network
transport, distribution across nodes, isolated or remote hands, an executor
fleet or broker, extension manifests or activation, package publication, an
installed-store migration, and any public compatibility claim.

The trusted-local grant is checked for exact binding but is not claimed to be
unforgeable, tamper-evident, or safe to transport. The durable local store proves
the accepted port on one machine; choosing PostgreSQL, SQLite, or another future
adapter is outside this milestone.

VM code generation remains M0 evidence rather than production extension work.
Nothing here promotes the spike to quiescent activation, atomic module-set
loading, or rollback of a trusted code generation.

No checker, registry, generic transport, or framework layer may stand in for the
working trace. A component that does not serve one of the eight outcomes is out
of scope.

## Workstreams

Ownership and the required rejoin order are fixed in the
[technical envelope](M1-technical.md#technical-plan-ownership).

- **A — Store and durable truth.** Outcome 3 and the durable ownership basis of
  outcome 2. Rejoins first.
- **B — Runtime and embedded API.** Outcomes 1, 2, and 4. Builds only on the
  integrated store contract and rejoins second.
- **C — Model and executor boundaries.** Outcomes 5 and 6. Builds on the
  integrated runtime/API path and rejoins third.
- **D — Client and combined demonstration.** Outcomes 7 and 8. Rejoins last and
  proves one trace through all prior workstreams.
