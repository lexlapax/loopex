## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Let independent client processes share one durable session without any of
them owning its lifetime. A local daemon owns every session in a state root:
it keeps sessions running while no client is connected, serves several client
processes over a Unix-domain socket with the same protocol the M4 foreground
server speaks, lets exactly one client drive while others observe, survives
the driver's crash with an explicit takeover, replays snapshot and cursor to a
reconnecting client without gaps or duplicates, cancels work across
processes, and keeps all of it on a store built for a long-lived service.
Complete M5 as an operator-usable, source-only `0.2.0` release: from the
exact source candidate, an operator follows the documented setup, starts the
daemon, and drives one session from two real client processes with their own
inputs before the reviewed integrated closure is tagged `v0.2.0`.

M5 answers the vision's durable-service question and carries the roadmap's
v0.2 candidate rung. It reuses M4's protocol, interactions, transfers and
observability unchanged and adds the daemon, its store and its collaboration
rule above the core; the core gains no lease, no transport and no second
loop.

<a id="concept-plan-scope"></a>
### Scope

The daemon owns session lifetime, the socket, attachment residency, the
collaboration lease and its own store root. Core owns durable session truth
exactly as accepted through M4. Hosts still supply workspace, identity,
policy, provider configuration and project resources when the daemon starts;
no client connection replaces any of them, and the daemon's configuration may
narrow who may take control but never widens what host policy allows.

The socket carries ADR 0023's JSONL protocol unchanged. Generation
`loopex.experimental/2` adds the daemon methods and the lease fields and lifts
the one-attachment-per-process rule to residency limits; generation-1 clients
are served exactly as the foreground server serves them. Attach is the
runtime's race-free cursor transaction; the daemon adds a bounded resident
window, bounded per-attachment queues, detachment at the last emitted cursor,
idle eviction and `cursor_expired` beyond retention. The residency and lease
numbers are exact in the technical envelope and bound at acceptance with the
accepted ADRs 0032 and 0033: 64 attachments per session, 512 per daemon, a
1,024-event queue, a 4,096-event resident window, ten idle minutes, a
thirty-second lease renewed every ten seconds.

Exactly one controller holds a daemon-owned lease per session; every other
attachment is read-only. Commands carry the writer epoch; a stale epoch is
refused before any durable write. Takeover is explicit, only after release or
expiry, and advances the epoch durably before the successor's first command.
The lease lives in the daemon's runtime-control namespace, never in the
session journal, and the core keeps mandating no lease. Cancellation crosses
processes because the core owns dispatch: the current controller's
`session.abort` cancels work an earlier controller started, with the truthful
two-phase outcome the core already commits.

The daemon-grade store is a new adapter behind the unchanged private Store
ports, selected between a BEAM-native segmented-log candidate and a
SQLite-backed candidate by the shared conformance and fault-injection suites
before ADR 0031 is accepted; the recommendation is the native candidate. It
imports an M4 local log one way, retains the original as the rollback pair,
records every migration step, and stamps a format version the previous
binary refuses. The foreground server and the CLI keep working on the local
adapter.

M4's observability continues without change: every daemon boundary emits the
ADR 0030 spans, and a trace session scoped to the daemon's runtime captures
identities only. The socket path is bounded by the platform and refused when
too long; the socket is owner-only and a foreign peer is refused before
initialize; the daemon never runs as a service manager unit by itself and the
documented launch is a foreground command an operator or their service
manager runs.

The release is one annotated `v0.2.0` tag on the exact integration commit on
`main` that contains the independently reviewed closure transition, and a
source archive of that tagged commit. The full gate first retains a report
for a staged candidate archive and runs the attended two-process workflow
from its fresh extraction. The release publishes no Hex package, binary,
installer or service unit and freezes no public protocol or embedded API. Tag
creation and publication follow closure review and explicit release
authority; neither is implied by a green gate alone.

<a id="concept-plan-non-goals"></a>
### Non-Goals

No controller lease, transport, socket or collaboration rule inside core. No
WebSocket, HTTP, TCP, remote or native-BEAM transport; no multi-host or
multi-user identity, tenancy or authorization beyond the socket's owner-only
peer rule; no trusted extension activation, isolated hands, ACP mapping,
public-protocol freeze, hosted store, Hex package, binary, installer or
service-manager integration. Generation 2 adds daemon methods and lease
fields only; no other protocol breadth. Those capabilities retain their
vision barriers and require their own evidence.

## Workstreams

Settle the three prerequisite decisions first, because the store choice fixes
the migration evidence and the residency and lease numbers fix the wire.
Build the daemon's lifetime and socket over the existing core and the local
adapter before the daemon-grade store rejoins, so lifetime, transport and
collaboration are proved against a known store; land the store and its
migration next; then join the two-process workflow with the reference CLI and
the TypeScript consumer before method breadth. Reuse M4's focused
checkpoints, clause witnesses and integrated self-audit; full inherited checks
remain at contract moments and scheduled CI. No second loop, lease in core or
transport registry.

M5 opened as the one permitted planning lookahead on branch `m5` from the
integrated M4 acceptance checkpoint
`6f973f774a403f76330058e3d0a59f7b83e038f1`. M4 is Accepted and remains the
sole implementation authority; this Open plan holds no implementation
authority. M5 cannot be accepted, integrated or implemented until M4 is Closed
and integrated; it must then absorb that exact product base, re-prove every
inherited gate green and its own distinct red, settle its prerequisites, and
receive a fresh exact-SHA review. The inherited gates cannot be green before
M4's Workstream 0 lands, because the Closed M1 and M2 runners refuse the
refreshed floor until their gate generations admit a post-closure re-capture;
this opening therefore records their state as unavailable, not green, under
the
[M1 and M2 waiver](../developer/agent-context-map.md#override-disposition-m4-m1-m2-inherited-reproof-waiver-2026-09-14)
and the
[M0 deferral](../developer/agent-context-map.md#override-disposition-m4-m0-reproof-deferred-to-implementation-2026-09-14).
