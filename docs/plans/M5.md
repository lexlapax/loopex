## Concept

Technical depth: [Durable service mechanics](M5-technical.md#technical-depth).

<a id="concept-plan-purpose"></a>
### Purpose

Let independent client processes share one durable session without any of them
owning its lifetime. A local daemon owns every session in a state root: it
keeps sessions running while no client is connected, serves several client
processes over a Unix-domain socket with the same protocol the M4 foreground
server speaks, lets exactly one client drive while the others observe,
survives the driver's crash with an explicit takeover, replays snapshot and
cursor to a reconnecting client contiguously and at least once with no gap,
cancels work across processes, and does all of it on the existing local store
adapter, whose Store process it owns while serving. Orderly shutdown and
failed-start reverse cleanup stop that Store last; a fatal fail-stop instead
stops the executor and then the still-live Store before halting the remaining
VM-local components. All paths stay within the adapter's documented limits.

Finish M5 as an operator-usable, source-only `0.2.0` release candidate. From a
fresh extraction of the exact closure candidate an operator follows the
documented setup, starts the daemon, and drives one session from two real
client processes with their own inputs; a release-ready source archive of that
candidate extracts, compiles and carries that same workflow. The release
itself — one annotated `v0.2.0` tag on the **administrative closure commit** —
is the maintainer's separate decision after closure, as the
[milestone guide](../developer/milestones.md#concept-milestones-release) sets
out. It is not a closure condition, because closure cannot wait on a tag that
closure authorizes.

M5 also settles one debt M4's verification work left explicitly open. The
provider adapter resolves its credential by reading a process-wide environment
variable inside each call, which is both a weaker property than the rest of
its credential plane and the reason the **thirteen** heavy provider test
modules declare `async: false` — **eleven of the thirteen** reference the
credential variable directly, and the other two are serial beside them for
their own reasons.

Thirteen rather than twelve, and the difference is one file whose membership
was settled by running it rather than by reading a glob:
`apps/loopex_llm_reqllm/test/support/provider_entry_test.exs`, which sits
under `test/support/` and is loaded by an ordinary `mix test` all the same.
The thirteen are listed by name, the two credential-independent ones marked,
and the executed derivation — 179 excluded, 164 from the non-recursive glob,
the difference of 15 being that one file — recorded once in
[ADR 0034's technical companion](../adr/0034-provider-credential-handoff-over-bootstrap-channel-technical.md#technical-adr-0034-serial-modules),
which this and every other carrier cites rather than recounting. M5 moves that
resolution from the process-wide environment to a composition-bound opaque
token resolved per invocation through host custody; the sender still writes
the credential over the private channel the launcher already opens.

M5 answers the vision's durable-service question and carries the roadmap's
v0.2 candidate rung. It builds on M4's protocol, interactions, transfers and
observability contract and adds the daemon and its collaboration rule above
the core. Core gains exactly six narrow things: support for several
independent attachments to one session, including several attachments held by
one process — which is one change with coordinated parts: implicit
same-session supersession is removed; `Control` and the dispatcher hold a
holder-to-attachment-set keyed by attachment identity; each installs its own
holder monitor or consumes one explicit release notification; one holder
`DOWN` releases that holder's complete set and its transfers; and replacement
names the exact attachment identity rather than an ambiguous boolean, so the
command path resolves the attachment handle without guessing which of one
holder's attachments it means; one read-only query surface that answers
whether a session ID exists durably in the root and whether an exact create
command identity plus canonical options has a historical session result;
`Loopex.Trace.exclude_self/2`, which installs both the match-specification
exclusion accepted ADR 0030 names and the process-level exclusion its callees
need before credential context or the token is delivered, with an OTP delivery
barrier that drains the deliberately observed token-free pre-clear traffic
before the exclusion acknowledgement and pending-call cleanup after process exit, plus
routing trace-session start, replacement and stop through `Control` so start,
stop, exclusion and both mailbox orders of predecessor `DOWN` versus replacement
hello are one serialized lifecycle, with full handles held only in a
Trace-owned private ETS table that only the Trace process can read, Trace's
callback state carrying only that table's identifier and weak session
identities, Control retaining only the exact weak identities, and the private
table disappearing with its Trace owner, while Trace's status and crash
formatting replaces state, message and reason and empties the log,
together with the one `Loopex.Trace.Entry` clause that redacts a keyword
list's values under their own keys, which is what keeps the credential token
out of an entry on its way to the adapter; `quiesce/1`, the bounded settle an orderly stop
drains through — whose first `Control` call atomically installs the terminal
    create/resume/attach/ordinary-route gate, projects the monotonic session-ID
    set for which a writer ever started and freezes that writer-domain key set
    through fencing,
whose drain-specific coordinator call closes ordinary command admission before
proposing the abort, and whose coordinator change then pauses a drained abort
where cleanup would have begun and presents its commit only once on an
ambiguous answer; plus the later read-only census over the same keys and the
one-shot fence-mode coordinator; and two
plain fields on **two new runtime-side functions beside** create and
resume — `create_session_detailed/3` and `resume_session_detailed/3`, so the
existing pair keeps its exact return and the embedded facade forwards what it
forwards today — `disposition`, saying whether this invocation started a
coordinator (`activated`) or did not (`no_activation`),
and `control_entry`, saying whether core's `Control` holds that session as
active, acquiring or dormant at the instant of the call. `control_entry` is deliberately not
called `residency`: that word is a **daemon** fact on the wire, about this
daemon's lifetime, and the two differ exactly when `Control` still lists a
session whose coordinator has died; and one managed provider-lifetime starter
that makes each guardian and credential sender a temporary child of the
existing per-owner worker supervisor, so teardown waits for both before a
replacement tracer starts. The public protocol result is unchanged. It gains
no lease, no transport, no second loop and no new durable command.

<a id="concept-plan-scope"></a>
### Scope

The daemon owns session lifetime, the socket, attachment residency, the
collaboration lease, its session index and the local store root it holds for
its process's lifetime. Core owns durable session truth, supports several
independent attachments to one session through its existing race-free attach
barrier and dispatcher, and answers one narrow read-only surface: whether a
session ID exists durably and whether an exact create command has a historical
result.

That query surface is the second of core's six M5 changes, and it exists because
the alternative was worse. The daemon has to validate durable existence before
it grants a lease, and before it records a session its index does not hold,
and it may not read Store internals to do it. Learning existence by *calling*
`attach` or `resume` — the earlier draft, rejected by the maintainer on
2026-09-20 — means taking a side effect to ask a question: `attach`
establishes a cursor barrier and an attachment incarnation, `resume` is a
durable mutation under ADR 0008's placement rules, and neither is safe to run
speculatively on an ID that may not exist. The query answers plain data,
creates nothing, changes nothing, and is the smallest thing that can be asked
honestly. Its create-history arm accepts a `command_id` and the same canonical
session options the create command binds. Its domain result inside
`{:ok, result}` is only `historical` with the committed session ID, `absent`,
`conflict`, `store_unavailable`, or `unexpected`; loss of the exact core
`Control` is the separate `{:error, :runtime_unavailable}`, which the daemon
treats as fatal `runtime_lost`. It starts no coordinator and writes nothing. That discriminator
lets an exact replay recover an unreturned session ID even when all 64
activation slots are occupied, while a genuinely fresh create still refuses
before core is called. Hosts still supply workspace, identity, policy,
provider configuration, the root `AGENTS.md` manifest and its launch-time trust
decision, and the independent project-skills manifest when the daemon starts;
no client connection replaces any of them, and the daemon's configuration may
narrow who may take control but never widens what host policy allows.

The socket reuses ADR 0023's framing, initialize handshake, admission, and
snapshot, event and progress semantics. Generation 2 adds one bounded request
field: every existing-session mutation carries `writer_epoch`, which is what
ADR 0033's admission check reads. Its complete wire delta also includes ADR
0032's enumerated daemon and lease methods, notification record families,
error codes and seven initialize-limit keys. Both
generations retain ADR 0023's optional boolean `replace`; because each
connection may hold at most one attachment, an adapter maps `replace: true`
to that attachment's exact identity at the new core boundary. No attachment
identity crosses the wire. The writer-epoch addition is additive — a
generation-1 client never sees it, because the daemon serves generation 2
only. The daemon serves generation `loopex.experimental/2` only. It keeps
one attachment per connection while core lifts the one-attachment-per-holder
rule for embedded callers. It adds no durable
method: core owns durable session truth and its **six** M5 changes are
concurrent attachment, one read-only existence-and-create-history query
surface, trace exclusion, the
bounded `quiesce/1` — whose new `Control` enumeration is part of that one
change and not another one — two fields on the runtime-side create and resume
results, and managed provider lifetime, none of which is a durable command, so
a daemon method that ended a session durably would have to add
one, which M5 does not do. Ending a client's involvement
is releasing control and disconnecting; the session itself keeps running,
which is the point of a daemon, and another client reaches it again by
acquiring control and attaching.

Idle eviction is about attachments, never about a coordinator. A session the
daemon has activated remains `active` for this daemon lifetime, and the daemon
never evicts its coordinator: idle eviction releases an **observer's**
attachment, its resident window and its output buffer — a connection holding a
controller lease is exempt while it holds it, its renewals being its activity —
and the work beneath them continues while the coordinator lives. `Dormant` is reserved for a session that
durably exists but this daemon has never activated. It has to be that way for two reasons. A session
with every client detached may still have a model request in flight, a tool
effect dispatched, an interaction awaiting an answer, a recovery running, an
unresolved `commit_unknown` or an admission executing inside core, so "idle"
is not "quiescent" and stopping on idleness would destroy exactly what
Outcome 1 exists to prove. And there is nothing to stop it with: core owns
coordinator lifetime, and M5's six core changes — concurrent attachment with
daemon-only routed-command discrimination, a
read-only existence-and-create-history query surface, trace exclusion, the
bounded `quiesce/1`, the create and resume results' two new fields, and managed
provider lifetime —
none of them stops a coordinator.

The cost is a real limitation and is recorded as one rather than hidden: at
most 64 sessions are activated per daemon lifetime, the 65th activation
refuses with `activation_ceiling_reached`, and the operator's remedy is to
restart the daemon. **Creating a session spends one of those 64**, because a
created session has a coordinator like any other: `loopex run --daemon` costs
an activation exactly as `loopex resume --daemon` does, and an operator
planning a long-lived daemon should count both. And `residency` means what the daemon can actually know: *this daemon
activated this session in this lifetime*, true by construction, never *a live
coordinator exists*. A coordinator is core's `restart: :temporary` child and
its loss is core's to supervise. The reference live-resume path normally finds
that loss through its bounded post-attach `session.inspect`; generation 2 maps
core's exact `:session_unavailable` to the correlated `session_unavailable`
code before any driving mutation. The same death can race a later mutation:
the daemon-only route returns `session_unavailable` when it proves the exact
coordinator died before any coordinator call, and `admission_unknown` when a
route succeeded but the reply was lost, retaining the method, command ID and
semantic input for exact re-presentation. Both keep the connection open;
neither invents a refusal from a generation change. Because the activation
fact is one-way, later inspection against the same daemon still repeats the
unavailable result. The operator recovery after a resolved or retained command
disposition is to release while the socket is writable, restart the daemon and
run `loopex resume --daemon` again: the new lifetime sees the session as
dormant, performs the governed resume, reattaches and inspects the new
coordinator. Making the daemon recover it
within the same lifetime would need a core notification or a
monitorable handle — a **further** core change M5 does not make, beyond the
six it does. Lifting it needs a core operation that can tell quiescent from idle,
which is its own decision and not M5's.

`session.list` is a daemon convenience, not an enumeration of durable truth.
It answers from a versioned, integrity-checked daemon index stored beside the
root and capped before it is read; daemon startup never materializes or scans
the unbounded legacy session directory. A legacy root with session entries and
no index refuses `session_index_upgrade_required` until an explicit offline
import builds the bounded index; a root with neither starts with an empty one.
That import is strict rather than a best-effort projection. Its daemon-owned
reader requires the legacy directory's owner UID to equal the daemon's effective
UID and holds that owner plus its non-symlink directory type, device and inode
across one materialized name list. It excludes only released temporary names and validates
every other regular non-symlink entry through a stable bounded read and safe,
uncompressed decode. The stored session ID must match the filename and the map
must have the exact legacy row shape and bounds; its runtime ID and every
command ID must be bounded, NUL-free UTF-8. A corrupt, oversized, invalid UTF-8
or otherwise invalid non-temporary row refuses the whole
import before publication and leaves any prior index byte-for-byte unchanged;
the released listing projection is not reused because it deliberately skips
rows it cannot decode.
The index is not Store truth: a process that commits a session and dies before
its index row is written leaves a session the Store holds and the index does
not. So `session.list` promises exactly what it can keep true — the sessions
this root records, each with its identity, its recorded placement identity,
whether the daemon currently holds it active, and whether a controller lease
is currently held — and no more.
Dormancy is cheap but not free: an indexed dormant session holds a row against
the entry ceiling, and every dormant session's history still sits in the root's shared
append-only log against the capacity ceiling, which is why retiring a root is
what frees them. What it costs nothing in is what activation buys — no
coordinator, no replay at start, no attachment, no window, no buffer.
Lineage, lifecycle state and committed sequence are not in a list entry,
because a daemon index cannot keep them current without reading the Store on
the request path; a client that needs them attaches, and the snapshot carries
them authoritatively.

A session missing from the list is never a lost session, and the plan says
exactly how it is recovered. The daemon learns durable existence from core,
through a read-only query that asks only that: given a session ID, does the
root hold it durably. No attach, no resume, no side effect. Its domain answer
inside `{:ok, result}` is one of a closed set — `present`, `absent`,
`invalid_id`, `store_unavailable` — and only `{:ok, :present}` lets control be
granted. The other three domain results fail
closed, leaving nothing created, nothing attached and no lease, and each names
its own reason, because an unreadable store and an unknown session are
different facts an operator acts on differently. The distinct outer
`{:error, :runtime_unavailable}` means core disappeared and makes the daemon
fail-stop as `runtime_lost`; it is never reported as a Store or session fact.
The daemon reads no Store
internals, so an incomplete index is never a correctness problem. A client that never received the session ID — the cut where the
Store committed and the process died before the reply — recovers through the
create command's durable `command_id`, which returns the historical result
instead of creating a second session — and then, because a replayed create
starts no coordinator, `session.resume` with a fresh resume command ID under
the acquired writer epoch is what actually brings the session back. ADR 0032
writes that sequence out step by step, and its witness asserts a live
coordinator and a prompt landing at the end of it, not merely an identity
returned. If recording the index row fails during activation, the causing
client receives `daemon.notice` with `index_write_failed`; a compatibility
directory failure is logged as a bounded operator warning. The session is
fully usable either way. An index failure before rename is retryable in this
daemon lifetime only when the publisher proved its exact `.next` file clean;
the next command carrying that session ID retries the idempotent publication.
A mismatched or unverifiable temporary identity, failed removal or cleanup
directory sync, or a directory-sync failure after rename instead poisons index
publication for the rest of this daemon lifetime, so later commands keep
serving the session without another index write. Restart validates whichever
complete index the filesystem presents and performs the bounded temporary-file
recovery, but cannot discover an omitted row by scanning. A later exact-ID
reach or replay of the create command supplies the identity and may republish
it in that new lifetime. The compatibility-directory retry remains independent
and runs on later ID-bearing commands. And if
the index is already at its 4,096-entry ceiling, a session reached by ID is
still activated, simply not recorded, with `session.list` carrying
`index_full` so an operator is told the listing is incomplete rather than
reading an omission as an absence. The ceiling is on recorded entries; it is
never on reachability.

A client offering only generation 1 is refused at initialize; generation-1
clients keep the M4 foreground server, whose wire and behavior do not change.
Attach is the runtime's race-free cursor transaction, and delivery is
contiguous and at least once: gaps are forbidden, duplicates are permitted,
and a client deduplicates by session ID, event sequence and event ID as the
vision requires. Core is the only replay owner: every attach, reattach and reconnect
goes through its cursor transaction, and the daemon's resident window is a
droppable cache of already-delivered encoded bytes that anchors no snapshot
and establishes no cursor. Above that the daemon adds daemon-owned bounded
socket output buffers, detachment at the last emitted cursor and idle
eviction; on the local adapter every durable event stays replayable until the
operator retires the root, so `cursor_expired` remains a defined protocol
response no M5 path produces.

Session creation makes an uncontrolled session; a client then acquires control
before existing-session mutation. Exactly one controller holds a daemon-owned
lease per session; every other attachment is read-only. For an existing
session, the daemon admits a mutation only when its requesting connection is
the holder of a held, unexpired lease and carries its current writer epoch.
Takeover is explicit. While the current lease owner remains live, it becomes
eligible only after release or expiry, waits for any mutation already in flight
under the outgoing lease to resolve, and mints a fresh epoch before the
successor's first command. If the lease owner itself fails, no successor starts
until the exact dead-owner pop, owner-loss classification and terminal
holder-close or correlated-refusal settlement. Its first grant additionally
waits until every retained predecessor ticket and retirement completion has
settled. The lease lives in the daemon's memory
for the daemon process's lifetime, never in the session journal or any durable
record; every writer epoch is minted fresh and never reused, so a daemon
restart leaves every session uncontrolled with every earlier epoch stale, and
the core keeps mandating no lease. One owner process per session serializes that
session's transitions against its own admissions. Its failure is scoped to
that session rather than to the daemon, on the maintainer's decision of
2026-09-20: the controller's connection is sent `control_owner_lost` and
closed with its attachment, every
observer stays, and the next acquisition starts a fresh owner with a fresh
epoch — the takeover mechanics that already exist for a released lease. The
admission relay claims every pending acquire or release whose immutable
intended-actor binding names the dead owner, every executing acquire or release
whose actor binding names it, and every pending or queued mutation bound to the
dead owner; an unpromoted mutation
starts no core task, while every promoted mutation remains owned until its real
core result. It withholds successor start until exact mirror pop,
classification acknowledgement and terminal notification settle, and the first
grant until every predecessor ticket and retirement completion settles; the fresh
epoch then keeps the old tenure from adding another. Cancellation
crosses processes because the core owns dispatch: the current controller's
`session.abort` cancels work an earlier controller started, with the truthful
two-phase outcome the core already commits.

The daemon runs every session on the existing local store adapter, selected
for this release by ADR 0031: one state root, the local log the M4 foreground
server and CLI already write, and the local writer marker held by the Store
process as physical-writer exclusion. The daemon separately acquires the same
crash-reclaimable host placement lock the reference CLI uses, before it opens
the Store or touches the socket. On orderly shutdown it attempts that lock's
acquisition-specific release only after the old Control is gone and the Store
stops last; on Store self-loss the Store runs its best-effort marker release
but the placement lock remains until the fatal halt, so no successor overlaps
the old Control. Either unchanged release may leave a residual after an
ignored filesystem error; the next acquirer applies the existing
dead/live/unverifiable-holder rule. The daemon asks for
stale-writer recovery explicitly, so a marker left by a dead daemon is
reclaimed where the adapter can prove its holder dead and refused where it
cannot. The adapter's limits are the daemon's limits and the operator
documentation states them: a hard 256 MiB log capacity, a log already past
that bound refused at open as `store_log_too_large`, a 4 MiB frame ceiling,
full-history retention with no compaction, and full replay at open.

Reaching capacity is not a survivable refusal on this adapter and the plan
does not pretend otherwise. The adapter answers `store_capacity_exceeded` for
the append and terminates the Store process, so the caller receives
`commit_unknown`; the daemon treats that exactly as it treats any other loss
of the store, closing the listener and every connection and exiting, with the
capacity named in the close so an operator is not left guessing. Nothing
committed is lost and nothing false is recorded. The root is then retired by
moving it aside and starting a fresh one; a root whose log is already past the
bound refuses at open rather than being opened and truncated. Making capacity
a definite pre-write refusal that a live daemon survives would be a change to
the Store adapter's own behaviour, with the conformance and fault-injection
evidence that carries; ADR 0031 records why that is the successor's work and
not M5's. No new store adapter, journal format version, Store/journal-format
migration or backup tooling enters M5. The bounded daemon-index import below
is an offline compatibility projection over the unchanged journal, not a
Store migration.

A daemon activates a session when a client creates or resumes it, not at startup — those are the two operations that start a coordinator, and acquiring control or attaching is neither.
Every session the root holds durably is dormant until then — indexed or not,
since the index decides only what `session.list` shows — and the daemon holds
at most a bounded number of active ones at a time. A dormant session costs its
journal and directory entry on disk and, when indexed, a row in the daemon's
bounded index, itself capped at 4,096 entries.
Dormancy itself runs no coordinator and holds no attachment, window or buffer,
and it spends none of the 64 activations until create or resume. Acquiring
control of a durably existing dormant session may create one bounded lease
owner before resume; that collaboration process does not activate the session.
This is the sense in which dormancy is cheap, rather than free. One root is one host composition, so a recorded session the daemon's
current composition cannot serve is reported at activation, by session, rather
than failing a startup that never reads it.

The provider child keeps the per-invocation private credential channel ADR
0019 already gave it; M5 changes the parent-side source for the unchanged
credential frame. Instead of reading a process-wide environment variable
inside each call, the adapter resolves a composition-bound token through a
host-owned registry and custody process. The host binds that opaque token where it composes the
runtime — `complete/3` takes a request and composition-time options and
nothing per-call, so that is the only seam there is — composes the routing
registry and custody process, and supplies a mandatory tracing capability
bound after the runtime starts. What happens per invocation is the
**resolution**: the managed path registers an inert guardian with Core, then
starts and adopts an inert sender whose exact initial arguments are its start
reference, callback owner, guardian and tracing capability. The sender remains
parked until the provider child proves exact readiness. It then excludes itself
synchronously, starts a sink that monitors it as well as linking for abnormal
exit, and only after both pids are verified clear receives the token, registry
and non-secret channel context — accepted socket and invocation nonce — by
message and routes the token to custody. The managed absolute invocation deadline is
allocated before either supervised start and never reset; after registration,
adoption and initialize, the guardian applies that instant to provider
launch/readiness, sender release, exclusion, token routing, custody resolution
and the credential-frame write. Direct mode has no Core gate: its raw guardian
carries the request's same pre-launch absolute instant through inherited-session
clearing, sink installation, routing, custody and frame write. Either deadline
expiry is `:timeout`; outside the host's custody process, the
credential bytes enter adapter-side parent code only in that excluded sender
and only for that one write. Concurrent invocations within one runtime resolve
the same composition-bound token independently; custody may rotate between
their replies, and each exact reply stays bound to that invocation's sender and
frame. Distinct-credential isolation is proved between two runtimes in one VM:
they carry different tokens, registries and custody processes, and neither
runtime's child or diagnostics observes the other's credential, so this is not
the process-wide slot one level down. The reference hosts — the CLI, the app-server
host and the daemon — read the operator's variable once where they compose and
delete it there, so the claim about the parent VM's environment is stated from
the completion of composition onward rather than for all time. The claim is
about *credential* reads: `ProviderLauncher` keeps reading the live
environment at each launch, because that read is ADR 0019's scrubbing of the
first spawned image and removing it would weaken an accepted decision, and the
proof shows it is never consulted for a credential. On acceptance, ADR 0034
will fix the token shape, the registry, custody and tracing-capability owners, when exclusion and
resolution happen, how rotation behaves, what bounds them, and what every
failure does. The maintainer set this as an M5 outcome on 2026-09-19 for two
reasons. A credential that must sit in the parent VM's environment for the
duration of every call is a weaker property than one held in host custody and
admitted to adapter-side parent code only in the excluded sender that writes
one private frame to the child that needs it; and that shared slot is what makes
eleven of the thirteen heavy provider test modules serial, which leaves the provider suite
as the fast check's critical path. The change stays inside the credential
plane: what a child may receive, from whom and when does not widen, and every
negative proof M0 to M2 established is carried to the new mechanism rather
than relaxed. It is its own workstream with its own security review, and its
measured result is part of closure.

The experimental public `complete_prompt/3` helper keeps its arity and result
union but changes its accepted options. Its caller now composes ephemeral
custody and a routing registry and passes their token and handle; an old
environment-only call refuses before launch. The milestone updates
`docs/operator/runtime.md`, `docs/developer/runtime-and-embedding.md` and the
compatibility-surface inventory with that migration. Runtime `Loopex.Model`
callbacks and public wire or durable records do not change.

M4's observability contract remains authoritative, while M5 implements the
missing trace exclusion ADR 0030 already required and makes its lifecycle
race-free; the accepted ADR itself is not amended. ADR 0030's emission
inventory is closed — five ports and six
coordinator cuts, with a new callback or cut instrumented only by amending
that ADR — and the daemon is a host above those ports, not one of them. So M5
adds no telemetry event and proposes no amendment. What it proves instead is
that the daemon's workflows drive the existing core spans end to end: a
session created, driven, taken over and aborted through the socket emits the
same command-admission, commit, effect-intent, publication, interaction, model,
store, policy and executor spans an embedded caller emits, with the same
bounded identity metadata. That, and nothing more, is M5's observability
claim.

Daemon-internal functions — the listener, the connection, the lease owners, the
residency stages — are proved by the daemon's own tests and its own logs, not
by a trace session. An earlier draft said a daemon-scoped trace session would
observe them, which ADR 0030 does not permit: a `Loopex.Trace` session traces
only processes the runtime owns, flagged from the runtime's supervisor with
`set_on_spawn`, and a process the runtime does not own is never covered. The
daemon's listener and lease owners are host processes above the runtime, so
they fall outside that scope by construction, and claiming otherwise would
have required widening ADR 0030's process scope. M5 does not. If the daemon
later needs events or trace coverage of its own, that is an ADR 0030
amendment with its exact events, metadata, bounds and tests, and it is not
M5's. The socket path is bounded by the platform's usable `sun_path`, one byte less
than the structure because of the terminator — at most 103 bytes on Darwin and
107 on Linux, derived per platform rather than assumed — and refused when too
long. Owner-only access is enforced first by the filesystem: the socket lives in a
`0700` daemon-owned subdirectory of the state root, is itself `0600`, and both
are verified after bind, the daemon refusing to serve without them. The root
itself keeps whatever mode it has — the foreground server creates it `0755`
under the ordinary umask, so requiring `0700` there would reject every
existing M4 root and contradict the rollback claim — and second by a fail-closed peer-credential read
whose mechanism is named per platform because no portable one exists: the
supported OTP 29 Darwin toolchain offers no `peercred` socket option at all.
A foreign peer is refused before initialize.
After the placement lock and Store marker are held, startup removes an existing
selected path only when a no-follow metadata read proves it is a Unix-domain
socket whose uid matches the acquisition-specific placement owner handle this
start created and retained. A regular file, symbolic link,
other file kind, owner mismatch, unreadable identity or failed removal is
preserved and refused as `socket_permission_unverified`.

The daemon never runs as a service-manager unit by itself: the documented
launch is a foreground command an operator or their service manager runs. That
makes its operator contracts part of the milestone rather than an afterthought,
so M5 fixes them. `loopex daemon` selects a root and a socket, prints exactly
one readiness line on standard output — and only once the host placement lock
and Store marker are held and
the socket is bound and permission-checked — attempts bounded, best-effort
diagnostics on standard error and, after its handler is installed, stops on
`SIGTERM` sent to it directly — and on any of `INT`, `TERM`,
`HUP` or `QUIT` sent to the launcher, which forwards all four as `SIGTERM`,
the route a terminal `SIGINT` takes since the emulator reserves that
signal — and exits `0`
for an operator stop or a unique non-zero status for each fatal class; a
best-effort reason line may be absent when standard error is blocked. There is no stop method on
the wire, because ending every client's session residency is not authority a
connection carries. A daemon takes the complete reference-host composition
input — state root, workspace, provider launch, policy, provider credential,
cleanup grace, root project context and project-skill packs — from the
per-input flag, environment, default or discovery source fixed in the
technical companion. A missing or invalid mandatory input, including an
unusable project-skill manifest, refuses with its own class. State-root and
explicit socket-path bytes are validated as UTF-8 at their shared input
boundary before path normalization or any filesystem, placement, Store or
socket work. An invalid root is `state_root_unusable` for both startup and
offline import; an invalid explicit socket is `invalid_socket_path`, while a
socket derived under an invalid root is never attempted and keeps the root
classification. Root project context keeps the released host rule instead:
the host shows the exact
`AGENTS.md` manifest to an interactive operator before taking a decision, and
an absent, excluded, malformed or unapproved resource withholds that content
without refusing daemon startup.

The root-resource prompt precedes signal-handler installation because it holds
no daemon resource and the shared terminal helper is synchronous. A direct
`SIGTERM`, or any of the launcher's four trapped signals forwarded as
`SIGTERM`, during that prompt therefore takes the BEAM emulator's default
signal handler, which stops the VM and reports status `0`. It emits no
readiness, wire record,
`daemon.stopping` record or lifecycle/fatal diagnostic and leaves no placement
lock, Store, socket or component.
The root-resource presentation and prompt already written to `stderr` may be
visible, as may the BEAM runtime's own shutdown notice. Neither is a daemon
lifecycle or fatal diagnostic. The daemon's orderly signal contract begins
only after handler installation.

If the daemon consumes `SIGTERM` after installing its handlers and before it
submits readiness to the lifecycle sentinel, it starts nothing further, reverse-cleans the
exact partial process inventory, emits no readiness or wire record and no fatal
diagnostic, and exits `0` only when that cleanup completes. Once readiness is in
flight, the sentinel is the sole disposition arbiter. It serializes the signal,
helper result or deadline, the owner's component-fatal notice and the owner's
post-success liveness-checked release authorization. Stop or fatal first keeps
the gate parked and makes every later candidate cleanup-only; the complete line
may already be visible, but no connection or wire state exists. The daemon
reverse-cleans and exits `0` for a stop unless that cleanup has its own non-zero
class. If release authorization wins before the deadline, the sentinel sends
exact `begin_accept`, startup is complete, and a later signal takes the ordinary
running-daemon shutdown path.

The live list and status forms each write one compact JSON object and one line
feed with fixed key order. List output carries the page, continuation or JSON
`null`, and `index_full`; status carries the daemon identity, socket, uptime and
current counts beside their limits. Strings use JSON escaping and an
`index_full` warning goes only to standard error, so standard output remains a
single machine-readable record.

Reaching a session over the socket is the daemon form of a command an operator
already knows: `loopex run --daemon` creates a session and drives it,
`loopex resume --daemon` acquires and probes attach: an active session attaches
and performs one bounded `session.inspect` before streaming without another
resume mutation. Exact `session_unavailable` means that this daemon's temporary
coordinator died: the client attempts to release while the socket remains
writable, exits non-zero and names restart-then-resume. `session_dormant`
instead verifies the dormant branch and is followed by resume with a fresh
command ID, a second attach and the same inspection. `loopex attach` joins one
that is already activated — as an observer, or as a one-shot controller with
`--take-over`.
There is no interactive multi-turn controller in M5, which is a restriction
stated rather than an omission. A live `run --daemon` drives its initial
request and at most one optional follow-up or steer. A live `resume --daemon`
repairs, attaches or resumes as needed and streams without admitting a user
command. Later one-shot control uses explicit `attach --take-over --prompt`.
Attaching never activates, so a client meets `session_dormant`
in either role and is told to resume — and `--take-over`, which acquires
before it attaches, releases that lease before exiting, so the remedy it names
is not blocked by the lease it just took. A reconnecting controller acquires
again and receives a fresh epoch before any further mutation. The released
offline `loopex sessions`, `run` and `resume` keep their grammar,
session-driving semantics and output, and each live form is a separate
explicit `--daemon` form of them. Outcome 6 separately changes the CLI host's
credential source and lifetime at composition.

Transport recovery follows the command phase rather than treating every EOF
alike. Live list and status queries retry once. A run whose create reply was
lost replays the same command identity, and run or resume may reacquire,
reattach, inspect and resume a dormant session after a daemon restart. An
observer and `attach --take-over` never activate; takeover releases before it
exits when a restarted daemon reports the session dormant. A complete
`daemon.stopping` record is terminal, while a bare EOF starts one bounded
recovery clock. A resume command whose result is still unknown keeps its exact
command ID across reconnection. If daemon replacement makes that ID resolve as
a completed replay but reattach still returns `session_dormant`, the completed
ID is retired and the client allocates a fresh resume command ID for the new
daemon lifetime. That retry and every further connection loss stay inside the
original fixed recovery clock; neither a resolved replay nor a new ID resets
it. A multi-step controller retains the exact next planned mutation
and its command identity. A step never attempted is sent after recovery. When a
write may have reached the daemon, the client reacquires authority and
re-presents the same method, durable command identity and semantic input; only
the connection-local request identity and writer epoch change. An accepted or
refused admission is the resolved result: core replays it when the first
presentation reached core and admits the command once when it did not. Exact
`admission_unknown` is neither branch; the client advances no later mutation,
reports that retained step unresolved and exits non-zero. Handled signals
detach a live client without aborting the daemon-owned session; a client still
holding a writable lease attempts one
bounded release first, while `SIGKILL` has no such path.

The live forms preserve only choices that belong to the request. A live `run`
may name one steer or follow-up. It refuses `--skill` and `--skill-resource`
before opening a socket because generation 2 exposes neither the immutable
workspace binding and pre-admission manifest data needed to construct the
exact project-skills decision nor a channel that hands that decision to the
reference client. Generation 2 still exposes the resource methods to a
host-integrated client that receives the exact project-skills decision out of
band. A live `run` also refuses `--policy`,
`--state-root`, `--workspace`, `--cleanup-grace-ms` and
`--context-token-budget`: those select or constrain the host composition the
already-running daemon owns. A live `resume` likewise refuses every released
composition flag, including the policy that the offline form requires. The
technical companion fixes the complete live-form grammar and the accepted and
refused flag matrix; the released offline parser behavior remains unchanged.

After signal-handler installation, a daemon ends in one of two ways and the
plan keeps them apart, because the code does. **A daemon-initiated stop** is a
drain and then a teardown: **close
admissions with one exact ref-tagged relay barrier and await its correlated
acknowledgement before advancing**, then stop and reap
the listener and close every already accepted uninitialized peer with EOF under
one fixed transport-cut deadline.
That acknowledgement is the admission instant: a request admitted before it
may enter core afterwards and is accounted under the pre-cut rules; every
post-initialize method presented after it is refused `daemon_stopping`, while
an uninitialized peer has no encoding and receives EOF. Then **quiesce the
runtime within the budget core derives**. If the runtime cannot enumerate
because `Control` restarted or is unavailable, classify the stop
`drain_failed` and use crash-equivalent fatal teardown without claiming a
census or fence result. Otherwise attempt one best-effort stop record per open
connection and close it; the registry moves each live slot to closing, the
relay kills and reaps its bound request workers, and one monitored worker per
slot obtains both core holder-cleanup acknowledgements before retirement;
the listener already being gone, **leave the socket pathname**,
which no exit path removes; stop the lease owners and then the runtime, which
ends crash-equivalently whatever the drain did not settle; stop the remaining
edges; and stop the Store last, which is when its `terminate/2` attempts the
marker's best-effort removal and parent-directory sync. The callback ignores
both filesystem results, so the healthy-path immediate-reopen witness proves
that run rather than a universal clean-stop guarantee.

**The drain has a mechanism, and it is core's.** M5 adds the daemon-scoped,
`@doc false` `quiesce/1` entry point to `Loopex.Runtime`. Its serialized first
operation installs the terminal gate and refuses a census with more than 64
writer-domain IDs before spawning per-session workers, while any number of
no-writer dormant entries are omitted from the bounded result, and it has three parts, in this
order, the last of them two
steps in a fixed order.
Its first `Control` operation atomically installs a terminal admission barrier
and returns the monotonic writer-domain set and its current coordinators, then
preserves that exact key set until fencing finishes. Create and resume execute their Store
work inside that same serialized `Control` mailbox: a call already being
handled completes its Store work and entry-or-dormant decision before the
barrier. Every resulting coordinator writer has an entry; a post-commit
   owner-start failure is dormant with no writer. Immediately after
   `DynamicSupervisor.start_child` succeeds, and before later attach or readiness
   work, Control sets a monotonic `writer_started?` fact, so an entry
   reset to unavailable after a partial start remains fence-eligible while a
   never-started dormant entry does not. A call ordered afterwards
refuses before Store access. Lifecycle messages may update
a retained entry but cannot add or remove one, and an owner-group `DOWN` after
the cut answers a waiting activation `runtime_unavailable` without deleting
its entry or starting another ordinary coordinator. Attach and
ordinary command routes ordered afterwards refuse; for a command that already
obtained a route, a drain-specific coordinator call closes ordinary admission
in that coordinator's mailbox before proposing the abort. A command processed
first is included in the abort, one processed later refuses, and internal
commit and recovery messages keep settling. Attach uses its pending-row
reservation as the barrier point: gate first refuses with no dispatcher state;
reservation first permits only that exact transaction to publish/finalize or
discard, with its relay ticket and charge retained. If publication commits as
the holder dies, core never restores a removed replacement target: the two
owners finish either live-then-ordinary-cleanup or directly released with no
live route, and the daemon retains the charge until they acknowledge the same
terminal state. Quiesce does not mistake
the transient attach for durable session truth. **The abort admission** then durably admits the
existing abort command for every active session and stops there, because ADR
0023 fixes that only a durable `session.abort` cancels and nothing may infer
cancellation from a signal. **The cancellation** is then released for every
session concurrently only when every admission is durably committed or
definitively refused with no active run — which is what makes "every abort
durable before any cancellation" true across the daemon rather than one
session at a time. A failed or ambiguous admission releases none. The record
   it writes is the one a client's own abort writes, under a `command_id` and
   Store transaction ID core deterministically derives from the session ID and
   its pre-admission owner epoch under a private `drain_abort` namespace. The
   Store binds that ID to the exact journal version, owner incarnation and
   canonical abort digest. After a crash, the current and predecessor epoch
   identities form the bounded recovery set. Namespace separation prevents
   accidental collision but cannot reserve a binary from a client. Core accepts
   a recovered candidate only after replay validates the exact abort type,
   digest and run binding; a different committed binding is a collision and not
   an abort. Predictability is harmless because a command ID grants no
   authority. There is no shutdown-specific field: the cause an operator wants
is reported on the wire where that bounded write succeeds, by the authoritative
exit status, and best-effort on `stderr`; a journal that says the same thing
again would have cost a persistent-schema decision for
nothing. It then drives what is in flight through the
cancellation sequence a coordinator already runs for an abort, under the
bounds core already derives from that session's committed cleanup grace. It
releases all paused cleanups only when every admission is durably committed or
definitively `rejected_no_active_run`; that refusal is conclusive because the
coordinator has already closed ordinary command admission. If any admission is failed or ambiguous,
it releases none and proceeds to termination. At the deadline it
**terminates every ordinary coordinator it enumerated — the ones that settled
   as well as the ones that did not — and only then asks core to start one
   one-shot, fence-mode `SessionCoordinator` for each frozen writer domain**.
   A never-started dormant entry is outside the projection and result. Each start uses a preallocated
   operation reference and a start/cancel/authorize handshake. Control and the
   fence process recheck one absolute deadline before `go` or Store work, and
   timeout cleanup kills and reaps the exact waiting pid. All eligible fences
   share one 125-second Store-work cutoff and a 130-second outer phase deadline;
   clocks never restart per entry. That
   coordinator is the session's sole serial writer. Before any fence mutation it
   resolves an ambiguous abort under the exact derived identity: a committed
   result is replayed and fenced from the resulting head; a terminal non-commit
   proceeds to the fence; and an absent result is explicitly non-terminal, so a
   fresh head-derived fence transaction decides the race. If the fence commits,
   the delayed abort cannot; if the fence is stale, the abort or another prior
   transaction moved the original head first and the session is conservatively
   superseded and unsettled. Store unavailability proposes no fence and returns
   an abort-stage unknown. It then performs exactly one
   Store-linearized owner-epoch fence and, on `commit_unknown`, one exact
   byte-identical re-presentation of that fence transaction,
then exits; the quiesce helper never calls the Store directly. The order keeps
each fence from racing a live ordinary writer and preserves the founding
single-owner rule;
because the runtime is killed at the teardown bound while the Store stays
alive for its own stop, so a settled session's straggler could otherwise
commit after the census that called it settled; so an older
transaction still in flight either wins before the fence and is observed or
loses after it and is refused as stale. **That fence's transaction ID and
incarnation derive from the session ID and expected owner epoch**, while the
Store binds that ID to the exact journal version and canonical digest. The live
fence owner re-presents those exact bytes once after `commit_unknown`. A fresh
process needs no drain result or stop line: from current epoch `E` it resolves
the bounded status identities for `drain_fence(E)` and, only if absent or proved
to be a client collision, `drain_fence(E - 1)`. A committed candidate is a
fence only when replay carries the exact owner-advance binding. Those distinguish a non-committing fence at the current
epoch, a committed fence that advanced it, and no fence. Unattributable or
unavailable results keep the session unavailable. Only after exact-ID recovery
does the successor commit ordinary fresh owner succession and admit commands.
The answer says, per session, what the fence
   actually did — not required, committed, superseded by a transaction that won
   the race, or unknown — because a fence whose failure no caller can observe
is not a fence anybody can rely on. Terminating the coordinator alone
would not have done it: a transaction already delivered to the Store completes
whether or not the process that sent it is still alive. It belongs in core
because core owns coordinator lifetime, cancellation and admission; a
daemon-side drain would have to reach into coordinator internals, which the
dependency direction forbids, or run a cancellation loop of its own, which is
the second loop this milestone forbids, and it could not admit a durable
command on its own authority at all.

**A graceful stop has a parameterized bound, with no useful
configuration-independent operational timeout for every root.** Cleanup grace
is durable session input and its accepted domain is much
larger than any useful service-manager timeout, so measuring one root cannot
bound the next. This pair fixes the **order** of the stop and the **guarantee**
at each step. The implementation reports the drain budget it derived from the
root's committed cancellation bounds and selects fixed admission-wait and
teardown values from the required maximum-population witnesses. Closure records
both values and their measurement conditions. The operator page explains those inputs and
recommends an unlimited service-manager stop timeout unless the operator
intentionally chooses forced cutoff; it never relabels one observed duration
as a universal maximum.

The successful stop has explicit fixed terms where no session cleanup grace is
involved: one **five-second** transport cut begun before the relay-cut send,
followed by the complete measured admission wait begun only when that cut
linearizes — the remaining transport work may overlap it, but the clocks do
not share a start instant; two sequential **five-second**
relay-control barriers; a **70-second** abort-admission phase; a **10-second**
status census; a **330-second** coordinator-termination phase; a **130-second**
fence phase; a **30-second** Store stop that attempts writer-marker release;
and a **five-second** placement-release attempt. The technical companion gives
their derivations and the exact expression with the selected fixed
`admission_wait_ms`, the root's `budget_ms`, and selected fixed `teardown_ms`.
The operator page must state that
complete maximum graceful-stop expression. Separately, a **fail-stop** exits in
at most **thirty-five seconds from its first fatal latch**; it is an alternative
tail after the graceful prefix already spent, not another term added to a
successful stop. Every other bound the implementation uses is stated there as an
**executed count** — a number a test asserts by running the path rather than
by reading it — which is the rule the earlier corrections earned. A service
manager that chooses a finite timeout shorter than the root-specific stop turns
the stop into a forced
shutdown — the journal stays crash-equivalent, but work that would have
settled does not, and the writer marker may be left for the next daemon's
verified recovery.

**Both halves of the outcome are stated.** Work that settles within the grace
has its ordinary terminal facts in the journal, `cancelled` among them where a
cancellation truly produced one. Work that does not settle is left claiming no
terminal outcome at all, its ambiguous mutation fenced as `commit_unknown` and
resolved to exactly one outcome at the next activation. A revision of this
plan withdrew the drain entirely for want of a mechanism; the maintainer
rejected that smaller design on 2026-09-20, and it is recorded here as the
option not taken — smaller, and a daemon that could tell an operator nothing
about whether its work had finished.

**A client learns by the record or by the close.** The stop record is one
bounded write attempt into a buffer that may be full, on a transport that may
already be gone, and on the one path where the connection registry itself
failed there is no surviving set or write interface. Listener loss leaves the
registry and accepted connections alive, so that class is attempted. The
promise is the honest one: a
client is told the reason where that write succeeds, and learns by EOF where
it does not.

**A store loss is not that sequence at all.** The local adapter answers an
append error by terminating itself and attempting its best-effort marker
release. The daemon's
independent placement lock remains held while the old daemon VM and Runtime
Control are live; a contender refuses on that live placement owner, and only
after the daemon halts may stale-owner recovery reclaim it. It is a fail-stop: refuse service, close
every connection with the reason, stop the executor, leave the socket
pathname where it is, exit non-zero. There is no "stop the Store last" step to run when the Store is what
died — though on a fatal class where the Store is still alive the daemon does
stop it, because the halt runs no `terminate/2` and the marker would otherwise
be left behind. The technical companion fixes both paths, the possible
complete residual, the fatal-class map and the reverse cleanup a failed
startup performs.

At the tested implementation candidate, every tracked file under
`docs/operator/` and `docs/developer/` is read for consistency with M5, for
relevance, links and indexing, and for stale foreground-only claims — including
the files M5 leaves unchanged. After the administrative closure commit changes
its five governed paths, including the context map and the root README's

That gate is only worth keeping if a reviewer can check it, so each run leaves
a record rather than an assurance. The indexed evidence-page scaffold already
exists at the tested candidate. Its administrative update carries the tested
candidate's checklist; the final administrative-SHA run is retained outside

Each checklist is derived from the revision it reviews — every tracked path
under `docs/operator/` and `docs/developer/` as

Four decisions are proposed with this plan. Each is accepted before the
implementation that depends on it, not before unrelated work.

The administrative transition that accepts ADR 0034 also changes ADR 0019's
index status to `Accepted (partially superseded by 0029 and 0034)`. Until that
transition, ADR 0019's current index row correctly names only accepted ADR
0029; a Proposed ADR does not supersede an accepted one.

**Three design decisions are settled here rather than in an ADR**, because
each is internal structure or a naming choice that no accepted decision binds.
They are recorded because getting any of them wrong would be expensive to
discover later.

**The protocol generations are named on one scheme, and generation 1 is
renamed to match.** The daemon serves `loopex.experimental/2`, and M5 renames
the released generation-1 string `loopex.session.v1-experimental` to
**`loopex.experimental/1`**. This is a break in an experimental surface, taken
under the policy the vision already states — experimental APIs may break in a
minor release with explicit migration notes — and `0.2.0` is a minor release.

The reason is that `v1` is reserved. The vision keeps "public protocol v1" for
the *stable* protocol, which cannot freeze before the daemon, the ACP mapping
and extension namespaces exist; an experimental line that had already spent
`v1` would leave the first stable release explaining why its `v1` is not the
one that shipped in `0.1.0`. `loopex.experimental/N` numbers the experimental
line on its own and leaves the stable name free. Doing it now is the cheap
moment: workstream 3 already restructures `LoopexProtocol.Session` per
generation, which is where the string lives.

**The strongest argument for it, found while planning this, is that the
released surface already disagrees with itself.** The two manifests an
independent client fetches and verifies —
`apps/loopex_protocol/priv/schema/loopex-experimental-1.json` and the matching
vectors file — **already declare `loopex.experimental/1`** and contain no
occurrence of `loopex.session.v1-experimental`, while the code that serves
them declares the old name. Nothing catches it, because the conformance module
pins each manifest by file digest and never compares the manifest's
`generation` with the one the code reports. So this rename does not introduce
a break in a consistent surface; it **closes a live discrepancy in a released
one**, making the code agree with artifacts that were published beside it. The
companion adds the missing assertion, so generation 2 cannot repeat it.

**Keeping `loopex.session.v1-experimental` beside `loopex.experimental/2` was
rejected**, because the two shapes would then coexist for as long as
generation 1 is served, and the collision above would still be waiting at the
freeze. The migration is one string, and the companion states it: a `0.1.0`
client is refused `unsupported_generation` and sends the new name; generation
1's contract is otherwise unchanged, while its schema digest is re-pinned
because the generation name is one of that digest's inputs; the repository's own Node
client is updated in the same change. No accepted ADR binds the literal, so
this is a plan decision rather than an amendment — ADR 0023 fixes that a
generation is negotiated exactly and that source version and generation are
independent, and never writes the string.

**The daemon owns its own lifetime, through an owner process rather than a
supervisor.** Its top-level component is one `GenServer` that traps exits and
`start_link`s a **fixed set** of them: the five the composition function
assembles in its caller's process — the Store adapter, the runtime root, the
artifact transfers owner where enabled, the workspace lease and the local
executor — plus six of the daemon's own: the credential routing registry, the
custody process and the tracing capability ADR 0034 gives the host, the
**admission relay** that holds one sequenced origin row per in-flight request
and a promoted ticket for each of the ten calls the daemon makes that change
core state — the eight lease-authorized mutations, `session.create` and
`session.attach` — bounded by 512 provisional — including aborting —, live or closing accepted slots times
32 active rows, and whose acknowledged cut is what an
orderly stop closes admissions with, the **connection registry** that owns
every connection's slot, monitor and output buffer, every daemon capacity
reservation and replacement borrow, and one monitored holder-cleanup worker
for each closing live connection, and the listener. Eleven where transfers are
enabled, ten where they are not. The connection registry traps exits while
retaining the exact daemon-owner identity and creates each waiting connection
linked inside the same serialized callback that binds its pid and monitor, so
an accepted socket never has an unrecorded child. **Beside them it links one
lease owner per session under lease or acquisition**, started at the first
lease operation rather than at activation, retired when the lease is free and
nothing is outstanding, and capped at 512 process slots across `starting_waiting_pop`, starting, live
and retiring owner rows. A retiring predecessor keeps its slot
until the daemon owner consumes its exact linked `EXIT`; a same-session
successor waits for that signal and takes the freed slot atomically, but starts
no child until the dead-owner mirror pop, classification acknowledgement and
terminal holder-close or correlated-refusal settlement complete, while an
unrelated 513th session remains refused. Its first grant additionally waits for
every predecessor ticket and retirement completion.
That one
class is session-scoped rather than daemon-fatal: the linked daemon owner is
the sole writer of each lease owner's exact routing-mirror install or clear, so
signal ordering makes a sent mirror request precede that owner's later exit;
its death closes that session's controller connection and leaves every other session serving, while
the relay is what keeps the replacement's first call from overtaking an older
one. It keeps every pid, because
each one is a component it must be able to name when that component dies. An
exit the owner did not ask for is fatal, by that process's own clause, and
that clause is what reads a dying Store's reason and turns it into the class
the daemon reports. The exits the owner's own stop sequence causes are
consumed rather than classified — otherwise stopping them all deliberately
would report a fatal class every time — and the technical companion states the
one field that tells the two apart. It is not
an OTP `Supervisor`: a supervisor offers no callback that can read a child's
exit reason, so `store_lost` and `store_capacity_exceeded` would be
indistinguishable, and `Loopex.Runtime.start_link/1` returns a struct rather
than `{:ok, pid}`, so the runtime is not a startable child at all. The
rejected alternative — a supervisor with zero restart intensity — is recorded
in the companion with all three reasons it fails.

The owner also resolves and monitors the exact `Control` and
`EventDispatcher` child pids that belong to the composed runtime generation.
A `DOWN` or replacement of either outside the owner's orderly-stop phase is
fatal `runtime_lost`, even when the runtime root itself survives. Those
children hold the daemon's attachment and session-accounting counterparts; a
transparent child restart would erase core state while leaving daemon counts,
leases and sockets live. During `quiesce/1`, runtime-root loss remains
`runtime_lost`; loss of the captured `Control` while that exact root is live is
instead the already-defined `drain_failed`, because it invalidates that drain's
census. If a child monitor event arrives first, the owner performs nonblocking
liveness checks of the retained exact root and Control pids before it latches a
class: a dead root is `runtime_lost`, a live root with dead Control is
`drain_failed`, and isolated dispatcher loss with both still live is
`runtime_lost`. Both paths fail-stop; where the Store is
alive, normal fatal teardown attempts marker release, while every fatal path
leaves the placement lock for recovery after the daemon halts.

**`loopex_composition` gains one narrow public function,
`LoopexComposition.start_edges/2`**, which validates the same host options as
`start/1` and assembles the
edges it already assembles but **in the caller's process**, returning them
instead of owning them — calling a caller-supplied interrupt checkpoint before
each edge, since the caller is inside one synchronous call for the whole
chain and can check nothing itself, and returning the edges it has already
started when that checkpoint stops it or an edge fails, so the caller can
unwind exactly what exists. Success is `{:ok, edges}`; every refusal is
`{:error, reason, partial_edges}`, where no key is present until that edge has
started and the optional `:transfers` key is absent when transfers are disabled.
The daemon's owner calls it from inside its own
trap-exit process, so every link lands where the daemon can act on it, and
`RuntimeOwner` calls the same function from its spawned process so `start/1`
and `with_runtime/2` are unchanged. The rejected alternative is the daemon
assembling the executor, artifact store, policy, runtime identity and tools
for itself: a second copy of a wiring layer, which the minimalism budget
rules out on its face. One function is the smaller change, and it unifies two
callers rather than adding a layer for one.

Three accepted decisions remain load-bearing and are not reopened wholesale.
M4's ADR 0023 fixes the protocol M5's generation 2 extends. M4's ADR 0030 fixes
the closed telemetry inventory M5 emits nothing outside of and the trace scope
M5 claims no witness beyond; M5 proposes no amendment to it. The post-M2 ADR
0019 remains Accepted; **if proposed ADR 0034 is accepted, it will narrowly
supersede the environment-as-sender-source, ready-sender-resolution, managed
raw-spawn and sole-guardian-ownership clauses**. ADR 0019's provider child, Port, OS guard and private
channel, launch-time enumeration and first-image scrubbing, failure teardown
and forensic-memory disclaimer remain in force. M5 deliberately changes the
parent-BEAM ownership of the token-free guardian and sender by placing managed
calls under `owner_workers`; the enumeration stays exactly where ADR 0019 put
it.

### How Each Outcome Is Verified

M5 runs through the three stages in the
[verification guide](../developer/verification.md#concept-verification-stages);
it adds no per-milestone runner and no check of its own.

**Change.** Every merge to `main` needs `bash scripts/check.sh` green in
hosted CI on that branch and an independent read of the diff. The fast check
is credential-free and needs no network, so it carries most of outcomes 1, 2,
3 and 4 — daemon lifetime and store fault injection on real local processes,
socket framing and generation negotiation, lease admission and fencing after
real kills, and the residency and delivery bounds — and the
parent-environment, concurrency-independence and re-pointed negative cases of
Outcome 6.

It does not prove them *in full*, and an earlier draft said it did. One
witness cannot be had there: the cross-UID socket refusal needs a second
unprivileged user, so it runs on the release check's Linux lane and nowhere
else. Outcome 2's owner-only claim is therefore complete only at closure, and
closure is bound to that lane's recorded result — a refused connection from a
foreign uid and an accepted one from the daemon's own — rather than to a fast
check that cannot reach it.

Beyond the fast check, a change selects only what its boundary asks for.
The rows of the
[selection table](../developer/verification.md#concept-verification-selection)
M5 reaches are five: the wire protocol, for generation 2's schema and
vectors; the CLI and operator-facing commands, for `loopex daemon`, the live
forms of `loopex run` and `loopex resume`, `loopex attach` and
`loopex sessions`; provider and credential handling, for
Outcome 6; the operating-system process boundary, because Outcome 6 changes
the provider child's spawn, control pipe and cleanup — a row that named only
the executor until M5 widened it, so widening both verification documents is
part of M5's own documentation work rather than something it may assume; and
durable records and the Store, whose durable bytes, private port callback,
arity, result union and existing best-effort marker-release behavior remain
unchanged while M5 adds the missing retained-create read projection. Every
completed Store `terminate/2`, including self-stop, calls that release, but its
ignored remove and parent-sync results mean completion does not prove the
pathname disappeared; the separate host placement lock keeps a successor out
until the daemon process has ended. The
toolchain floor and `.tool-versions` are unchanged, so nothing
selects that row. What each of the five costs, down to the command and its
parameters, is in the technical companion rather than repeated here.

**Close.** At one commit on `main` where every outcome maps to tests, retained
evidence or a demonstration and an indexed
`docs/evidence/M5-closure-runs.md` scaffold already exists: hosted CI's green
run on that candidate is the
current-pair Linux fast check; `bash scripts/check.sh` runs once under the
floor toolchain pair on Darwin, covering that platform's peer-credential and
socket-path branches; `bash scripts/check-release.sh` runs once on Linux with the provider
credential and pinned Node, which is where the attended two-process
demonstration of Outcome 5, the fresh-source build and Outcome 6's
real-provider lane are proved. Before that extracted tree is built, its
`scripts/source-archive-manifest.sh` command writes the tested manifest's exact
NUL-delimited bytes to retained storage outside the extraction; the scaffold
records their source SHA, entry count, reference and digest. Each
credential-consuming workflow gets its own
fresh child BEAM inherited from the release shell, and every such invocation
must report exactly one executed case; no test restores the consumed variable
inside a VM. Each run's revision, platform, toolchain,
result and measured duration is recorded on `docs/evidence/M5-closure-runs.md`
with the Outcome 6 security review's result, retained-report reference and
digest — **by the administrative commit**, the runs and review being of the
tested one. An independent reviewer reads the
candidate; the maintainer closes it.

That tested implementation commit itself moves M5 and both marked status
blocks from `In progress` to `In review`. A `Proved` outcome row there means
the implementation is complete and names its proof obligation; it does not
claim that a closure run or review performed after the commit already has a
result. Those later results and identities occupy the scaffold's predeclared
`Pending` fields. The administrative direct child makes only the `In review`
to `Closed` transition.

M5 closes on the two SHAs the
[milestone guide](../developer/milestones.md#concept-milestones-close) now
fixes: the **tested implementation SHA** every run above names and the
reviewer read, which is what this pair's Closure row records, and the
**administrative closure SHA** that carries that row — located by the
register's `Closed` transition and, if released, by the `v0.2.0` tag rather than written
into the row it is the content of — and confined to
[its five paths and allowed regions](../developer/milestones-technical.md#technical-milestones-confinement):
  the register row and current-status block, this pair's Closure row, the context-map entry,

### Rollout and Compatibility

`v0.2.0` identifies a numbered source release, not a compatibility freeze; all
surfaces stay experimental. Generation 2 is additive over generation 1's
method set under ADR 0023's exact-generation rule: the daemon serves
generation 2 only and refuses a generation-1-only initialize with nothing
created, while the foreground server keeps serving generation 1 with its
wire, its one-attachment rule and its behavior unchanged. No mixed-generation
stream is promised.

An operator running `0.2.0` runs the daemon on the local adapter and lives
within its limits: 256 MiB of log per state root, a 4 MiB frame ceiling, full
history with no compaction and full replay at open. Reaching capacity is a
truthful `store_capacity_exceeded` refusal of the append, never silent loss,
and on this adapter it is also the end of that daemon: the store terminates,
the caller sees `commit_unknown`, and the daemon closes the socket and every
connection and exits naming the capacity. The operator page states that
plainly, because capacity here is an outage to plan for rather than a
degradation to ride out. A root whose log is already past that bound is
refused at open as `store_log_too_large` rather than opened and truncated.
The documented recovery is to retire the root — stop the daemon, move the root
aside, start a fresh one — after which a session in the retired root is
reached only by reopening that root.

The private journal and its format are unchanged. The local adapter gains only
the retained-create read projection through its existing `runtime_command/2`
callback, changing no durable byte, callback arity or result union; the marker
query an earlier revision added went with the unlink it existed for. At the
Store and journal layer the daemon and foreground surfaces share the same
bytes. A first move from a populated M4 or `0.1.0` root into M5 requires the
one-time `loopex daemon prepare-index` import. That command installs its
signal lifecycle before acquiring either exclusion: a handled stop interrupts
and reaps its scan, runs bounded Store and placement cleanup, emits no readiness
or wire output, and exits with distinct non-zero
`prepare_index_interrupted`; a complete image already renamed remains
complete rather than being rolled back. Its exact success report and a late
stop use first-consumed arbitration: success first exits `0` and makes the
stop cleanup-only, while stop first retains the interrupted status. After a
valid index exists,
later switches only stop one surface before starting the other. Rollback is
direct: dropping back to `0.1.0` means stopping the daemon and using the M4
foreground server and CLI on the same root, which nothing durable prevents,
because no journal record depends on the lease, the session index or any
residency state.

**Three embedded transient behaviours change, and they are named here rather
than left to the mechanics because they are observable.** `Loopex.attach/3`
keeps its shape, but today a second attach to a session **supersedes the first
and never refuses it**: the dispatcher splits its attachment map on
`session_id` alone and core carries no `replace` option to ask for anything
else, while `Control` refuses only a *repeated* `request_id` under a different
binding, which is idempotency rather than a second attachment
(`control.ex:1312-1335`). ADR 0023's rule that a second attachment refuses
unless replacement is named is the **app server's** connection-level check,
not core's, which is why an embedded caller meets neither. After the
concurrent-attachment change, an ordinary second attach coexists with the
first, explicit replacement supersedes only the exact
`replace_attachment_id`, and holder death releases that holder's complete
attachment set and transfers. Non-prepared succession remains the one
session-wide exception: it invalidates every attachment for that session,
releases every transfer and notifies each live daemon holder with the
capacity-reserved `detached` record while keeping its connection open. A
boolean `replace: true` is not accepted by core because one holder may have
several live attachments and no implicit ordering chooses one. A caller that
attached twice to one session and relied on the older one going away must
retain and name that handle; one that names no target gets two live
attachments rather than a refusal. Every caller in this repository attaches
once and is unaffected.
The daemon-only `Runtime.command_for_daemon/2` discrimination and
`Runtime.classify_daemon_result/2` ordering barrier belong to this same
internal attachment change: they preserve the embedded
`Runtime.command/2` result and therefore are not a fourth embedded transient
behavior. The daemon serializes targeted replacement after predecessor mutation
origins instead of exposing a replacement-specific command result. One registry
CAS orders a still-pending replacement against succession: cut first publishes
no replacement handle and uses the one borrowed reserve for `detached` followed
by `attachment_conflict`; local publication first transfers that reserve before
ordinary succession of the new attachment.
Nothing durable is involved — attachments are runtime-local and transient — so
rollback needs no step.

Outcome 6 changes no public wire or durable surface. It does change the
experimental public `complete_prompt/3` helper's accepted options: an
environment-only call now refuses, and a caller passes a credential token plus
the handle for ephemeral routing and custody it composes. Runtime hosts make
the same composition change and supply the mandatory runtime-bound tracing
capability that excludes the sender before the token is routed.

## Workstreams

Six workstreams follow the technical companion's rejoin order. The core
changes needed by daemon behavior land before that behavior can be proved.
Workstream 5 is independent of daemon semantics and may land after ADR 0034,
but it carries workstream 1's trace-exclusion and managed-provider-lifetime
changes and therefore shares their core integration surface. The sixth runs
last because it describes what the others built. Workstream 1 lands
in two parts — the core change first, its daemon-side residency after the
lease — and the companion's rejoin order says where each part goes.

1. **Core's six changes, and the residency above them.** The narrow core
   change that lets distinct attachments to one session coexist without

**A core gap was found by the fresh review and closed in the design.** Core's
concurrent-attachment change removes unconditional same-session supersession —
and supersession is the only path that removes an attachment today. The final
maintainer decision permits several attachments under one holder, so both
`Control` and the dispatcher hold a holder-to-attachment-set keyed by the
attachment identity the handle carries. Each owns the monitor state it needs,
or one sends an explicit release notification to the other; one holder `DOWN`
drops that holder's complete set and releases every attachment's transfers.
The daemon never decrements its ceiling before core has acknowledged that
cleanup, so monitor-delivery order cannot admit a 513th installed attachment.

Replacement is explicit and exact inside core. Core receives
`replace_attachment_id`, binds it into idempotency, verifies that the caller's
stable holder owns that attachment for the same session, and replaces only
that target. A bare boolean is insufficient at that boundary because one
embedded holder may have several attachments. The wire remains unchanged:
the foreground and daemon adapters each permit one attachment per connection
and map their existing `replace: true` to that connection's sole attachment
identity. The connection first records an exact sequenced origin in the relay,
then obtains the connection registry's exclusive borrow of the replacement
target. The first request becomes the primary, an exact repeat waits on that
primary with no second task, and a distinct request conflicts. Only the primary
can promote; the relay starts its attach call in a monitored task before
acknowledging promotion and passes
the connection pid through the narrow internal attach-for-holder operation;
the task is transient, while the connection remains the installed holder. A
cut or primary death before promotion releases the borrow and terminalizes its
waiters rather than promoting one of them.
This keeps every ticket kind under the same admission rule without making the
relay task the attachment owner.

**One `0.1.0` defect was found during an earlier review and is recorded rather
than patched.** On 2026-09-20, checking what the generation rename would cost, the

code's, which is why nothing noticed. **No change is made to `0.1.0`**: the
defect is resolved by M5's rename, which makes the code agree with the

**One drift closed by implementing it, not by amending it.** Accepted
[ADR 0030](../adr/0030-observability-tracing-and-telemetry-technical.md#technical-depth)
says "the key-bearing call is excluded by match specification". `Loopex.Trace`
had no such mechanism: it installed one pattern per module, `{module, :_, :_}`,
with no function or arity selectivity, and its only exclusion was by pid.
An earlier revision of this plan recorded that as drift and leaned on
sink-time redaction instead — which cannot satisfy the requirement, because
tracing delivers the raw call to the tracer before any redaction runs, so a
host that named the adapter would create one more message holding the
credential.

M5 therefore **implements what the accepted ADR already requires**, as core's
third change in this milestone — and implements it as **one call installing
both mechanisms**, because neither alone is enough. The match specification
ADR 0030 names excludes the key-bearing bridge calls themselves; it cannot
reach what they *call*, and a trace session naming `:gen_tcp` sees the
credential frame `ProviderCodec.send/3` hands it whatever this adapter's own
functions are patterned. So `Loopex.Trace` gains
`exclude_self(capability, functions: [mfa])`: the **caller supplies its own**
key-bearing identities — core never names an adapter function, which is what
keeps the dependency direction intact — and core installs the
match-specification clear for them and the process flag for the caller, in
that one call. `Control` retains the live sender membership and ref-counted MFA
union; each trace session applies them, waits for OTP's delivery marker before
acknowledging a cleared process, purges that pid's pending call rows, and a
replacement trace session reapplies the exclusions. After the last sender
leaves each surviving session restores its own
previously selected MFA pattern. Destroying a trace session removes that
session's process flags rather than preserving them. The capability resolves
and forwards to the current `Control` dynamically; `Control` coordinates the
current tracer, so no caller retains either child pid. The managed sender's
exact initial arguments are its start reference, callback owner, guardian and
capability. It completes the acknowledged guardian-adoption gate and parks
until exact provider readiness. Only then does it exclude itself and confirm
both exclusion and delivery drain before the token and registry are sent to
it; no trace
*configuration* can name it back in. A `Control` restart destroys the old
trace sessions and, under `:rest_for_one`, every downstream owner group. The
managed provider-lifetime starter makes each guardian and sender a temporary
child of the existing owner-workers supervisor, whose synchronous teardown
kills and awaits them before the replacement tracer starts. New senders exclude
anew. A sender that meets `Control` mid-restart fails closed before the token
is routed. Both the
leak and the mechanism were reproduced by probe at both toolchain pairs before
this was written down. ADR 0030 is **not** edited — an accepted ADR changes through its own
amendment path — and its prose is honoured once this change lands. This is a
change to an accepted ADR's subject matter rather than to its text, so it is
flagged for the maintainer as such.
