## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Let independent client processes share one durable session without any of
them owning its lifetime. A local daemon owns every session in a state root:
it keeps sessions running while no client is connected, serves several client
processes over a Unix-domain socket with the same protocol the M4 foreground
server speaks, lets exactly one client drive while others observe, survives
the driver's crash with an explicit takeover, replays snapshot and cursor to a
reconnecting client without gaps or duplicates, cancels work across
processes, and does all of it on the existing local store adapter, which the
daemon holds for the root's lifetime.
Complete M5 as an operator-usable, source-only `0.2.0` release: from the
exact source candidate, an operator follows the documented setup, starts the
daemon, and drives one session from two real client processes with their own
inputs. Closure review and an explicit combined closure and release/tag
disposition then lead to an integrated closure commit on `main`, annotated
`v0.2.0` tag and verified source archive. The M5 closure workflow is complete
only when that post-tag evidence is retained.

M5 answers the vision's durable-service question and carries the roadmap's
v0.2 candidate rung. It reuses M4's protocol, interactions, transfers and
observability unchanged and adds the daemon and its collaboration rule above
the core. The core's attachment machinery gains narrow support for several
independent attachments to one session; it gains no lease, transport or
second loop. No new store adapter enters M5: the daemon-grade store and its
migration are the successor milestone's first decision.

<a id="concept-plan-scope"></a>
### Scope

The daemon owns session lifetime, the socket, attachment residency, the
collaboration lease and the local store root it holds. Core owns durable
session truth and supports several independent attachments to one session
through its existing race-free attach barrier and dispatcher. Hosts still
supply workspace, identity, policy, provider configuration and project
resources when the daemon starts; no client connection replaces any of them,
and the daemon's configuration may narrow who may take control but never
widens what host policy allows.

The socket carries ADR 0023's JSONL protocol unchanged and serves generation
`loopex.experimental/2` only, which adds the daemon methods and the lease
fields and lifts the one-attachment-per-process rule to residency limits. A
client offering only generation 1 is refused at initialize; generation-1
clients keep the M4 foreground server, whose wire and behavior do not change.
Attach is the runtime's race-free cursor transaction; the daemon adds a
bounded resident window, bounded per-attachment queues, detachment at the
last emitted cursor, idle eviction and `cursor_expired` beyond retention. The
residency and lease numbers are exact in the technical envelope and bound at
acceptance with the accepted ADRs 0032 and 0033: 64 attachments per session,
512 per daemon, a 1,024-event and 4 MiB per-attachment queue, a 4,096-event
and 16 MiB per-session resident window, 512 MiB of aggregate retained encoded
event bytes, ten idle minutes, and a thirty-second lease renewed every ten
seconds.

Session creation makes an uncontrolled session; a client then acquires
control before existing-session mutation. Exactly one controller holds a
daemon-owned lease per session; every other attachment is read-only. For an
existing session, the daemon admits a mutation only when its requesting
connection is the holder of a held, unexpired lease and carries its current
writer epoch. Takeover is explicit, only after release or expiry, and
advances the epoch before the successor's first command. The lease lives in
the daemon's memory for the daemon's lifetime, never in the session journal
or any durable record; the writer epoch carries the daemon incarnation, so a
restart leaves every session uncontrolled and every earlier epoch stale, and
the core keeps mandating no lease. Cancellation crosses processes because the
core owns dispatch: the current controller's `session.abort` cancels work an
earlier controller started, with the truthful two-phase outcome the core
already commits.

The daemon runs every session on the existing local store adapter: one state
root, the local log the M4 foreground server and CLI already write, and the
local writer marker held by the daemon for its lifetime. No new store
adapter, journal format version, migration or backup tooling enters M5. After
an orderly daemon stop the foreground server and the CLI reopen the same root
and sessions under the same placement identity, which is also M5's rollback.
The daemon-grade store, its selection experiments and its migration are the
successor milestone's first decision under the still-Proposed ADR 0031.

M4's observability continues without change: every daemon boundary emits the
ADR 0030 spans, and a trace session scoped to the daemon's runtime captures
identities only. The socket path is bounded by the platform and refused when
too long; the socket is owner-only and a foreign peer is refused before
initialize; the daemon never runs as a service manager unit by itself and the
documented launch is a foreground command an operator or their service
manager runs.

The release is one annotated `v0.2.0` tag on the exact reviewed closure
integration commit on `main`, and a source archive of that tagged commit. The
full gate first retains a report for a staged candidate archive and runs the
attended two-process workflow from its fresh extraction. After gate green and
independent closure review, a combined explicit closure and release/tag
disposition authorizes the closure transition, integration, tag creation and
post-tag archive verification. Those are required to complete M5's closure
workflow; the full gate cannot claim the future tag exists. The release
publishes no Hex package, binary, installer or service unit and freezes no
public protocol or embedded API.

At the final source candidate, audit every tracked file under
`docs/operator/` and `docs/developer/` for consistency with M5, relevance,
links and indexing where applicable, and stale foreground-only claims. New,
materially updated
and reviewed-unchanged files all receive a recorded per-file disposition;
the independent closure reviewer examines the inventory and any finding
resolution. The seven-row gate table still names the exact files M5 must
materially update. Release instructions describe the required `v0.2.0` tag
and archive workflow without claiming a tag before it exists.

<a id="concept-plan-non-goals"></a>
### Non-Goals

No controller lease, transport, socket or collaboration rule inside core. Its
only M5 change is independent concurrent attachment support. No daemon-grade
store adapter, journal format version, migration, backup tooling or NIF
dependency; no daemon-served generation 1; no durable lease record. No
WebSocket, HTTP, TCP, remote or native-BEAM transport; no multi-host or
multi-user identity, tenancy or authorization beyond the socket's owner-only
peer rule; no trusted extension activation, isolated hands, ACP mapping,
public-protocol freeze, hosted store, Hex package, binary, installer or
service-manager integration. Generation 2 adds daemon methods and lease
fields only; no other protocol breadth. Those capabilities retain their
vision barriers and require their own evidence.

## Workstreams

After M4 closes, reconstruct M5's valid opening checkpoint and settle the two
prerequisite decisions before M5 acceptance. After acceptance, land the one
application through its holder transaction and the narrow core attachment
change, then build daemon lifetime and socket over the local adapter, prove
collaboration and replay on that base, and join the two-process workflow with
the reference CLI and the TypeScript consumer before method breadth. Reuse
M4's focused checkpoints, clause witnesses and integrated self-audit; full
inherited checks remain at contract moments and scheduled CI. No second loop,
lease in core or transport registry.

**Revision of 2026-09-14.** On the independent review of
`dc81212360327caa7e8b0ed371cb5ed531b960d9`, the maintainer decided to narrow
this Open plan in three ways. The daemon-grade store, its selection
experiments and its migration leave M5 for the successor milestone, so ADR
0031 is no longer an M5 prerequisite and M5 adds one application. The daemon
serves generation 2 only, so no generation-1 exclusive lease exists. The
controller lease is daemon memory with an incarnation-scoped epoch, so no
durable daemon-control store exists. The rung question needs none of the
three, each doubled evidence without adding a proved capability, and the
daemon on the local adapter already reopens under the foreground server after
an orderly stop. The plan pair, gate, outcomes manifest and ADRs 0031 to 0033
were revised together in one commit.
