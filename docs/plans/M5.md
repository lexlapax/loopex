## Concept

Technical depth: [Durable service mechanics](M5-technical.md#technical-depth).

<a id="concept-plan-purpose"></a>
### Purpose

Let independent client processes share one durable session without any of them
owning its lifetime. A local daemon owns every session in a state root: it
keeps sessions running while no client is connected, serves several client
processes over a Unix-domain socket with the same protocol the M4 foreground
server speaks, lets exactly one client drive while the others observe,
survives the driver's crash with an explicit takeover, replays snapshot and
cursor to a reconnecting client contiguously and at least once with no gap,
cancels work across processes, and does all of it on the existing local store
adapter, which it holds for its process's lifetime within that adapter's
documented limits.

Finish M5 as an operator-usable, source-only `0.2.0` release candidate. From a
fresh extraction of the exact closure candidate an operator follows the
documented setup, starts the daemon, and drives one session from two real
client processes with their own inputs; a release-ready source archive of that
candidate extracts, compiles and carries that same workflow. The release
itself — one annotated `v0.2.0` tag on the integrated closure commit — is the
maintainer's separate decision after closure, as the
[milestone guide](../developer/milestones.md#concept-milestones-release) sets
out. It is not a closure condition, because closure cannot wait on a tag that
closure authorizes.

M5 also settles one debt M4's verification work left explicitly open. The
provider adapter resolves its credential by reading a process-wide environment
variable inside each call, which is both a weaker property than the rest of
its credential plane and the reason twelve heavy provider test modules cannot
run concurrently. M5 moves that handoff onto the private per-invocation
channel the launcher already opens.

M5 answers the vision's durable-service question and carries the roadmap's
v0.2 candidate rung. It reuses M4's protocol, interactions, transfers and
observability unchanged and adds the daemon and its collaboration rule above
the core. Core gains exactly two narrow things: support for several
independent attachments to one session, and one read-only query that answers
whether a session ID exists durably in the root. It gains no lease, no
transport, no second loop and no new durable command.

<a id="concept-plan-scope"></a>
### Scope

The daemon owns session lifetime, the socket, attachment residency, the
collaboration lease, its session index and the local store root it holds for
its process's lifetime. Core owns durable session truth, supports several
independent attachments to one session through its existing race-free attach
barrier and dispatcher, and answers one read-only question about it: given a
session ID, does this root hold that session durably.

That query is the second and last of core's M5 changes, and it exists because
the alternative was worse. The daemon has to validate durable existence before
it grants a lease, and before it records a session its index does not hold,
and it may not read Store internals to do it. Learning existence by *calling*
`attach` or `resume` — the earlier draft, rejected by the maintainer on
2026-09-20 — means taking a side effect to ask a question: `attach`
establishes a cursor barrier and an attachment incarnation, `resume` is a
durable mutation under ADR 0008's placement rules, and neither is safe to run
speculatively on an ID that may not exist. The query answers plain data,
creates nothing, changes nothing, and is the smallest thing that can be asked
honestly. Hosts still supply workspace, identity, policy,
provider configuration and project resources when the daemon starts; no client
connection replaces any of them, and the daemon's configuration may narrow who
may take control but never widens what host policy allows.

The socket reuses ADR 0023's framing, initialize handshake, admission,
snapshot, event and progress records and limits unchanged. Request records are
reused with one addition rather than unchanged, and the plan says so: every
existing-session mutation in generation 2 carries `writer_epoch`, which is
what ADR 0033's admission check reads. That is the one field generation 2 adds
to a request, and it is additive — a generation-1 client never sees it,
because the daemon serves generation 2 only. The daemon
serves generation `loopex.experimental/2` only, which adds `session.list`,
`daemon.status`, the two control methods and the writer-epoch field, and lifts
the one-attachment-per-process rule to residency limits. It adds no durable
method: core owns durable session truth and its M5 changes are concurrent
attachment and one read-only existence query, neither of which is a durable
command, so a daemon method that ended a session durably would have to add
one, which M5 does not do. Ending a client's involvement
is releasing control and disconnecting; the session itself keeps running,
which is the point of a daemon, and another client reaches it again by
acquiring control and attaching.

Dormancy is about attachments, never about a coordinator. A session the daemon
has activated keeps its coordinator until the daemon exits: idle eviction
releases an attachment, its resident window and its output buffer, and the
work beneath them continues. It has to be that way for two reasons. A session
with every client detached may still have a model request in flight, a tool
effect dispatched, an interaction awaiting an answer, a recovery running, an
unresolved `commit_unknown` or an admission executing inside core, so "idle"
is not "quiescent" and stopping on idleness would destroy exactly what
Outcome 1 exists to prove. And there is nothing to stop it with: core owns
coordinator lifetime and M5's only core change is concurrent attachment.

The cost is a real limitation and is recorded as one rather than hidden: at
most 64 sessions are activated per daemon lifetime, the 65th activation
refuses with a stable reason, and the operator's remedy is to restart the
daemon. Lifting it needs a core operation that can tell quiescent from idle,
which is its own decision and not M5's.

`session.list` is a daemon convenience, not an enumeration of durable truth.
It answers from a daemon-owned index built at start from the state root's
session directory, and that directory is not Store truth: a process that
commits a session and dies before the directory entry is written leaves a
session the Store holds and the directory does not. So `session.list` promises
exactly what it can keep true — the sessions this root records, each with its
identity, its recorded placement identity, whether the daemon currently holds
it active, and whether a controller lease is currently held — and no more.
Lineage, lifecycle state and committed sequence are not in a list entry,
because a daemon index cannot keep them current without reading the Store on
the request path; a client that needs them attaches, and the snapshot carries
them authoritatively.

A session missing from the list is never a lost session, and the plan says
exactly how it is recovered. The daemon learns durable existence from core,
through a read-only query that asks only that: given a session ID, does the
root hold it durably. No attach, no resume, no side effect, a plain-data
answer. The daemon reads no Store internals, so an incomplete index is never
a correctness problem. A client that never received the session ID — the cut where the
Store committed and the process died before the reply — recovers through the
create command's durable `command_id`, which returns the historical result
instead of creating a second session. If recording the directory entry fails
during activation, that failure is reported to the client, the session is
fully usable anyway, and the record is retried at the next activation. And if
the index is already at its 4,096-entry ceiling, a session reached by ID is
still activated, simply not recorded, with `session.list` carrying
`index_full` so an operator is told the listing is incomplete rather than
reading an omission as an absence. The ceiling is on recorded entries; it is
never on reachability.

A client offering only generation 1 is refused at initialize; generation-1
clients keep the M4 foreground server, whose wire and behavior do not change.
Attach is the runtime's race-free cursor transaction, and delivery is
contiguous and at least once: gaps are forbidden, duplicates are permitted,
and a client deduplicates by session ID, event sequence and event ID as the
vision requires. Core is the only replay owner: every attach, reattach and reconnect
goes through its cursor transaction, and the daemon's resident window is a
droppable cache of already-delivered encoded bytes that anchors no snapshot
and establishes no cursor. Above that the daemon adds daemon-owned bounded
socket output buffers, detachment at the last emitted cursor and idle
eviction; on the local adapter every durable event stays replayable until the
operator retires the root, so `cursor_expired` remains a defined protocol
response no M5 path produces.

Session creation makes an uncontrolled session; a client then acquires control
before existing-session mutation. Exactly one controller holds a daemon-owned
lease per session; every other attachment is read-only. For an existing
session, the daemon admits a mutation only when its requesting connection is
the holder of a held, unexpired lease and carries its current writer epoch.
Takeover is explicit, becomes eligible only after release or expiry, waits for
any mutation already in flight under the outgoing lease to resolve, and mints
a fresh epoch before the successor's first command. The lease lives in the daemon's memory
for the daemon process's lifetime, never in the session journal or any durable
record; every writer epoch is minted fresh and never reused, so a daemon
restart leaves every session uncontrolled with every earlier epoch stale, and
the core keeps mandating no lease. A lease owner's failure is fatal to the
daemon instance rather than survivable: it holds the session's in-flight
admission set, which is what a takeover waits on, so losing it silently could
let a successor be granted while a forgotten admission could still settle.
Every connection closes and the daemon restarts. Cancellation
crosses processes because the core owns dispatch: the current controller's
`session.abort` cancels work an earlier controller started, with the truthful
two-phase outcome the core already commits.

The daemon runs every session on the existing local store adapter, selected
for this release by ADR 0031: one state root, the local log the M4 foreground
server and CLI already write, and the local writer marker held by the daemon
from before the socket is bound until the daemon exits. The daemon asks for
stale-writer recovery explicitly, so a marker left by a dead daemon is
reclaimed where the adapter can prove its holder dead and refused where it
cannot. The adapter's limits are the daemon's limits and the operator
documentation states them: a hard 256 MiB log capacity, a log already past
that bound refused at open as `store_log_too_large`, a 4 MiB frame ceiling,
full-history retention with no compaction, and full replay at open.

Reaching capacity is not a survivable refusal on this adapter and the plan
does not pretend otherwise. The adapter answers `store_capacity_exceeded` for
the append and terminates the Store process, so the caller receives
`commit_unknown`; the daemon treats that exactly as it treats any other loss
of the store, closing the listener and every connection and exiting, with the
capacity named in the close so an operator is not left guessing. Nothing
committed is lost and nothing false is recorded. The root is then retired by
moving it aside and starting a fresh one; a root whose log is already past the
bound refuses at open rather than being opened and truncated. Making capacity
a definite pre-write refusal that a live daemon survives would be a change to
the Store adapter's own behaviour, with the conformance and fault-injection
evidence that carries; ADR 0031 records why that is the successor's work and
not M5's. No new store adapter, journal format version, migration or backup
tooling enters M5.

A daemon activates a session when a client reaches for it, not at startup.
Sessions the root records are dormant until then, and the daemon holds at most
a bounded number of active ones at a time; the rest stay dormant and cost
nothing. One root is one host composition, so a recorded session the daemon's
current composition cannot serve is reported at activation, by session, rather
than failing a startup that never reads it.

The credential handoff to a provider child moves from the process-wide
environment variable the adapter reads inside each call to the per-invocation
private channel the launcher already opens for the nonce and the build
manifest. The host passes an opaque credential token with each call and owns
both the registry that routes it and the custody process the bytes live in; the reference hosts — the CLI, the app-server
host and the daemon — read the operator's variable once where they compose and
delete it there, so the claim about the parent VM's environment is stated from
the completion of composition onward rather than for all time. The claim is
about *credential* reads: `ProviderLauncher` keeps reading the live
environment at each launch, because that read is ADR 0019's scrubbing of the
first spawned image and removing it would weaken an accepted decision, and the
proof shows it is never consulted for a credential. ADR 0034 fixes
the reference's shape, the resolver's owner, when it is resolved, how rotation
behaves, what bounds it, and what every failure does. The maintainer set this as an M5 outcome on 2026-09-19 for two
reasons. A credential that must sit in the parent VM's environment for the
duration of every call is a weaker property than one that exists only on a
private channel to the child that needs it; and that shared slot is what makes
the twelve heavy provider test modules serial, which leaves the provider suite
as the fast check's critical path. The change stays inside the credential
plane: what a child may receive, from whom and when does not widen, and every
negative proof M0 to M2 established is carried to the new mechanism rather
than relaxed. It is its own workstream with its own security review, and its
measured result is part of closure.

M4's observability continues without change, and "without change" is meant
exactly. ADR 0030's emission inventory is closed — five ports and six
coordinator cuts, with a new callback or cut instrumented only by amending
that ADR — and the daemon is a host above those ports, not one of them. So M5
adds no telemetry event and proposes no amendment. What it proves instead is
that the daemon's workflows drive the existing core spans end to end: a
session created, driven, taken over and aborted through the socket emits the
same command-admission, commit, effect-intent, publication, interaction, model,
store, policy and executor spans an embedded caller emits, with the same
bounded identity metadata. That, and nothing more, is M5's observability
claim.

Daemon-internal functions — the listener, the connection, the lease owner, the
residency stages — are proved by the daemon's own tests and its own logs, not
by a trace session. An earlier draft said a daemon-scoped trace session would
observe them, which ADR 0030 does not permit: a `Loopex.Trace` session traces
only processes the runtime owns, flagged from the runtime's supervisor with
`set_on_spawn`, and a process the runtime does not own is never covered. The
daemon's listener and lease owners are host processes above the runtime, so
they fall outside that scope by construction, and claiming otherwise would
have required widening ADR 0030's process scope. M5 does not. If the daemon
later needs events or trace coverage of its own, that is an ADR 0030
amendment with its exact events, metadata, bounds and tests, and it is not
M5's. The socket path is bounded by the platform's usable `sun_path`, one byte less
than the structure because of the terminator — at most 103 bytes on Darwin and
107 on Linux, derived per platform rather than assumed — and refused when too
long. Owner-only access is enforced first by the filesystem: the socket lives in a
`0700` daemon-owned subdirectory of the state root, is itself `0600`, and both
are verified after bind, the daemon refusing to serve without them. The root
itself keeps whatever mode it has — the foreground server creates it `0755`
under the ordinary umask, so requiring `0700` there would reject every
existing M4 root and contradict the rollback claim — and second by a fail-closed peer-credential read
whose mechanism is named per platform because no portable one exists: the
supported OTP 29 Darwin toolchain offers no `peercred` socket option at all.
A foreign peer is refused before initialize; the daemon never runs as a service-manager unit by itself, and the
documented launch is a foreground command an operator or their service manager
runs.

At the closure candidate, every tracked file under `docs/operator/` and
`docs/developer/` is read for consistency with M5, for relevance, links and
indexing, and for stale foreground-only claims — including the files M5 leaves
unchanged. The documentation the milestone changed is part of the closure
candidate, as it is for every milestone.

That gate is only worth keeping if a reviewer can check it, so it leaves a
record rather than an assurance. The closure evidence carries a checklist
derived from the candidate itself — every tracked Markdown path under
`docs/operator/` and `docs/developer/` as
`git ls-files -- ':(glob)docs/operator/**/*.md' ':(glob)docs/developer/**/*.md'`
lists them at that commit, sorted, one row each, with the count stated so an
empty derivation is visible rather than silently passing; the command returns
26 paths as of this revision — and every row is marked either *updated* or *reviewed
unchanged*, with any finding named and resolved before the packet is
assembled. A path present in the tree and absent from the list, or a row with
neither mark, is an unfinished gate. Deriving the list from the candidate
rather than writing it by hand is the point: a file added late cannot be
missed by a checklist that is generated from the same bytes the reviewer
reads.

<a id="concept-plan-non-goals"></a>
### Non-Goals

No controller lease, transport, socket or collaboration rule inside core. Its
only M5 change is independent concurrent attachment support. No daemon-grade
store adapter, journal format version, migration, backup tooling, compaction,
retention cutoff or NIF dependency; no daemon-served generation 1; no durable
lease record; no exactly-once delivery promise beyond the founding
at-least-once contract. No WebSocket, HTTP, TCP, remote or native-BEAM
transport; no multi-host or multi-user identity, tenancy or authorization
beyond the socket's owner-only peer rule; no trusted extension activation,
isolated hands, ACP mapping, public-protocol freeze, hosted store, Hex
package, binary, installer or service-manager integration. Generation 2 adds
daemon methods and lease fields only; no other protocol breadth. Outcome 6
changes where a credential is resolved and nothing about what a child may do
with it: no new credential scope, no credential store, vault or rotation
service beyond each reference host holding the one value it already reads at
composition, no change to the `Loopex.Model` callbacks or to ADR 0019's
process topology. The `req_llm` move to `~> 1.24.0` is an ordinary dependency
change and adds no dependency, no adapter capability and no provider surface. Those capabilities
retain their vision barriers and require their own evidence.

One decision is recorded for the milestone after M5 and deliberately bound
nothing here.
[ADR 0035](../adr/0035-typed-decision-models-as-policy-inputs.md#concept)
proposes that a typed decision model — one returning probabilities and
confidences rather than text — may be an input to a host's policy decision and
a journaled plain-data fact, never the decision itself. It is not an M5
prerequisite, no M5 outcome waits on it, and M5 runs no part of it. An
earlier draft admitted one bounded experiment inside the provider workstream;
that is withdrawn on 2026-09-20, because it would have put a real call to a
second provider, needing a second credential the release check does not carry
and a per-provider credential token ADR 0034 does not define, inside a
check M5 is required to pass. A milestone whose required check depends on a
decision that has not been accepted is not a complete set. ADR 0035 stays
Proposed and wholly deferred.

### Design Decisions

Four decisions are proposed with this plan. Each is accepted before the
implementation that depends on it, not before unrelated work.

| Decision | What it settles | Outcomes that wait on it |
| --- | --- | --- |
| [ADR 0031](../adr/0031-daemon-grade-store-selection-and-migration.md#concept) | The daemon's store for `0.2.0` is the existing local adapter, with its 256 MiB log capacity, 4 MiB frame ceiling, full retention, `store_capacity_exceeded` refusal, the capacity-as-store-loss consequence and the operator root-retirement procedure documented; a daemon-grade adapter and any migration are left open for a separate decision and prescribed nowhere | 1, 5 |
| [ADR 0032](../adr/0032-daemon-attachment-residency-and-replay.md#concept) | The Unix-domain-socket transport reusing ADR 0023 unchanged, generation 2 and its methods, refusal of a generation-1-only client, owner-only peer access, marker-first startup, race-free attach with at-least-once contiguous delivery, the resident window, daemon-owned output buffers, detachment, idle eviction and bounded session pages | 1, 2, 4 |
| [ADR 0033](../adr/0033-collaboration-controller-lease-and-takeover.md#concept) | One daemon-owned in-memory controller lease per session with a fresh opaque writer epoch per grant, admission that binds holder connection, held state, unexpired term and epoch together, explicit takeover, and cross-process abort through the core's own cancellation | 3 |
| [ADR 0034](../adr/0034-provider-credential-handoff-over-bootstrap-channel.md#concept) | The provider credential is a per-invocation input named by an opaque token, routed by a host-owned registry that holds routing only, and resolved from a host-owned custody process inside the sender that writes it to the child's private channel, after the child proves its identity and before the invocation frame; the token's shape, registry and custody ownership, rotation, the guardian-enforced deadline, `:unavailable` on loss with no reconstruction, and every failure are exact; the adapter reads no environment variable for a credential, while the launcher's ADR 0019 scrubbing read stays and is proved never consulted for one | 6 |

Three accepted decisions remain load-bearing and are not reopened: M4's
ADR 0023 fixes the protocol M5's generation 2 extends, M4's ADR 0030 fixes the
closed telemetry inventory M5 emits nothing outside of and would have to amend
to add a daemon event, and the post-M2 ADR 0019 fixes the provider process
topology ADR 0034 refines.

<a id="concept-plan-verification"></a>
### How Each Outcome Is Verified

M5 runs through the three stages in the
[verification guide](../developer/verification.md#concept-verification-stages);
it adds no per-milestone runner and no check of its own.

**Change.** Every merge to `main` needs `bash scripts/check.sh` green in
hosted CI on that branch and an independent read of the diff. The fast check
is credential-free and needs no network, so it carries most of outcomes 1, 2,
3 and 4 — daemon lifetime and store fault injection on real local processes,
socket framing and generation negotiation, lease admission and fencing after
real kills, and the residency and delivery bounds — and the
parent-environment, concurrency-independence and re-pointed negative cases of
Outcome 6.

It does not prove them *in full*, and an earlier draft said it did. One
witness cannot be had there: the cross-UID socket refusal needs a second
unprivileged user, so it runs on the release check's Linux lane and nowhere
else. Outcome 2's owner-only claim is therefore complete only at closure, and
closure is bound to that lane's recorded result — a refused connection from a
foreign uid and an accepted one from the daemon's own — rather than to a fast
check that cannot reach it.

Beyond the fast check, a change selects only what its boundary asks for.
The rows of the
[selection table](../developer/verification.md#concept-verification-selection)
M5 reaches are five: the wire protocol, for generation 2's schema and
vectors; the CLI and operator-facing commands, for `loopex daemon`,
`loopex attach` and `loopex sessions`; provider and credential handling, for
Outcome 6; the operating-system process boundary, because Outcome 6 changes
the provider child's spawn, control pipe and cleanup — a row that named only
the executor until M5 widened it, so widening both verification documents is
part of M5's own documentation work rather than something it may assume; and
durable records and
the Store, which M5 touches only through the daemon's use of the unchanged
adapter. The toolchain floor and `.tool-versions` are unchanged, so nothing
selects that row. What each of the five costs, down to the command and its
parameters, is in the technical companion rather than repeated here.

**Close.** At one commit on `main` where every outcome maps to tests, retained
evidence or a demonstration: hosted CI's green run on that candidate is the
current-pair fast check; `bash scripts/check.sh` runs once under the floor
toolchain pair; `bash scripts/check-release.sh` runs once with the provider
credential and pinned Node, which is where the attended two-process
demonstration of Outcome 5, the fresh-source build and Outcome 6's
real-provider lane are proved. Each run's revision, platform, toolchain,
result and measured duration is retained on `docs/evidence/M5-closure-runs.md`
with the security review of Outcome 6. An independent reviewer reads the
candidate; the maintainer closes it.

**Release.** The release is one annotated `v0.2.0` tag on the exact integrated
closure commit, reusing the closure evidence because the source is unchanged,
plus a verified source archive of that commit. It publishes no Hex package,
binary, installer or service unit, and freezes no public protocol or embedded
API.

### Rollout and Compatibility

`v0.2.0` identifies a numbered source release, not a compatibility freeze; all
surfaces stay experimental. Generation 2 is additive over generation 1's
method set under ADR 0023's exact-generation rule: the daemon serves
generation 2 only and refuses a generation-1-only initialize with nothing
created, while the foreground server keeps serving generation 1 with its
wire, its one-attachment rule and its behavior unchanged. No mixed-generation
stream is promised.

An operator running `0.2.0` runs the daemon on the local adapter and lives
within its limits: 256 MiB of log per state root, a 4 MiB frame ceiling, full
history with no compaction and full replay at open. Reaching capacity is a
truthful `store_capacity_exceeded` refusal of the append, never silent loss,
and on this adapter it is also the end of that daemon: the store terminates,
the caller sees `commit_unknown`, and the daemon closes the socket and every
connection and exits naming the capacity. The operator page states that
plainly, because capacity here is an outage to plan for rather than a
degradation to ride out. A root whose log is already past that bound is
refused at open as `store_log_too_large` rather than opened and truncated.
The documented recovery is to retire the root — stop the daemon, move the root
aside, start a fresh one — after which a session in the retired root is
reached only by reopening that root.

The private journal, its adapter and its format are unchanged, so moving a
state root between the daemon and the foreground surfaces is stopping one and
starting the other. That is also the rollback: dropping back to `0.1.0` means
stopping the daemon and using the M4 foreground server and CLI on the same
root, which nothing durable prevents, because no journal record depends on the
lease, the session index or any residency state. Outcome 6 changes no public
or durable surface at all; its one visible effect is that a host composing
this adapter passes a credential token with the call and composes a routing registry and a custody process behind it.

## Workstreams

Six workstreams, listed in the order the technical companion's rejoin order
puts them in, which is the order of what each needs to exist before it can be
proved. Core concurrent attachment comes first, because the daemon's attach
path cannot be proved without it; the fifth is independent of all of them; the
sixth runs last because it describes what the others built. Workstream 1 lands
in two parts — the core change first, its daemon-side residency after the
lease — and the companion's rejoin order says where each part goes.

1. **Core's two changes, and the residency above them.** The narrow core
   change that lets distinct attachments to one session coexist without
   implicit replacement, and the read-only session-existence query the
   daemon's acquire and activation paths need — both land first, because
   nothing about the daemon can be proved without them — and then, once the lease
   exists, the daemon-side residency over it: the resident window as a
   droppable cache, per-connection output buffers, detachment at the last
   emitted cursor, idle eviction, dormancy and the aggregate byte ceiling with
   its deterministic reclamation.
2. **The daemon.** One new application, `loopex_daemon`: marker-first startup
   on the local adapter with explicit stale-writer recovery, session lifetime
   with zero attachments, orderly stop and abrupt death, lazy activation after
   restart under the same placement identity, active and dormant residency
   with its ceiling, the session index with its bound and its bounded pages,
   activation refusal for a session this composition cannot serve, shutdown on
   store loss, capacity as one such loss, and reopening under the foreground
   server after an orderly stop.
3. **The socket transport.** The listener, its owner-only peer check and path
   bound, ADR 0023's framing and records reused, generation 2's schema and
   vectors beside generation 1's, negotiation and the generation-1-only
   refusal, and the differential conformance that the facade, the foreground
   server and the socket produce the same durable identities.
4. **The collaboration lease.** The in-memory lease record, the per-session
   owner that serializes lease transitions with admission handoff, the
   combined holder, epoch, state and term check, explicit takeover with a
   fresh epoch and the expiry linearization, fencing after a real kill, and
   cross-process abort through the core's existing durable command.
5. **The credential handoff and the provider dependency.** ADR 0034's change
   to the provider adapter and to the host composition sites that read the
   operator's variable, the re-pointed credential-plane proofs, the new proofs
   of the token, the routing registry, the guardian-enforced deadline and
   every failure, its own security review by someone other than its
   implementer, and the measured effect on the provider suite once its modules
   can run concurrently.

   This workstream also carries one bounded dependency item, which is
   **explicit M5 scope** rather than a convenience: `req_llm` moves from
   `~> 1.17.1` to `~> 1.24.0` in `apps/loopex_llm_reqllm/mix.exs` and
   `mix.lock`. The pin is `~> 1.24.0`, not `~> 1.24`, so the version reviewed
   is the version built against and a later minor cannot arrive unreviewed.

   Its M5-specific reason is stated rather than left implicit: the
   maintainer's direction of 2026-09-20 is that the milestone after M5 will
   accommodate the typesafe.ai model, that work needs `1.24.0`, and taking a
   seven-release dependency step inside M5 — where the adapter and
   streaming-conformance suites and the existing real-provider case at closure
   already exercise it — keeps the later milestone's cost to its own decision
   rather than bundling a large dependency move into it.

   It is separate from
   [ADR 0035](../adr/0035-typed-decision-models-as-policy-inputs.md#concept)
   and not conditional on it: that decision is deferred, no part of it runs in
   M5, and the upgrade stands on its own dependency reasoning whatever happens
   to it. It is an ordinary dependency decision, so it lands as its own
   reviewed change carrying its own dependency review: the version floor, the
   reviewed changelog diff across the intervening releases, the adapter and
   conformance suites green, and the existing real-provider case at closure
   run against it. It is sequenced before the credential change where both
   touch the adapter, so the credential proofs are written once against the
   upgraded library rather than twice. It adds no M5 call path: nothing in the
   milestone calls anything `1.24.0` makes newly reachable. It touches no
   daemon application code,
   and no daemon workstream touches the adapter's library tree — but it is not
   file-disjoint from them: host composition, the integration scripts, the
   provider pages and the closure evidence page are reached by both, and the
   companion names them as the integrator's to sequence.
6. **Documentation and the `0.2.0` release candidate.** The operator daemon
   guide and the developer daemon pair, the updates M5 forces on the existing
   operator and developer pages, the changelog and the indexes, the `VERSION`
   change to `0.2.0`, the archive-carried source identity both build paths
   accept in place of `.git`, and the release-ready source archive proved by
   extracting it, building the CLI and its provider companion inside the
   extraction, and running the two-process workflow there.

Parallel work uses one worktree per writer over the non-overlapping paths the
technical companion assigns, with one integrator owning the rejoin.
