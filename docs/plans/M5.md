## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Let independent client processes share one durable session without any of
them owning its lifetime. A local daemon owns every session in a state root:
it keeps sessions running while no client is connected, serves several client
processes over a Unix-domain socket with the same protocol the M4 foreground
server speaks, lets exactly one client drive while others observe, survives
the driver's crash with an explicit takeover, replays snapshot and cursor to a
reconnecting client contiguously and at least once with no gap, cancels work
across processes, and does all of it on the existing local store adapter,
which the daemon holds for its process's lifetime within that adapter's
documented limits.
Complete M5 as an operator-usable, source-only `0.2.0` release candidate:
from the exact source candidate, an operator follows the documented setup,
starts the daemon, and drives one session from two real client processes
with their own inputs, and the full gate proves a staged, release-ready
source archive of that candidate. Closure review and an explicit combined
closure and release/tag disposition then lead to an integrated closure
commit on `main`. Creating the annotated `v0.2.0` tag on that commit and
verifying its archive is the release completion this plan requires after
closure; it is not a closure condition, because closure cannot wait on a tag
that closure itself authorizes.

M5 answers the vision's durable-service question and carries the roadmap's
v0.2 candidate rung. It reuses M4's protocol, interactions, transfers and
observability unchanged and adds the daemon and its collaboration rule above
the core. The core's attachment machinery gains narrow support for several
independent attachments to one session; it gains no lease, transport or
second loop. No new store engine enters M5: ADR 0031 selects the existing
local adapter for this release, with its 256 MiB log ceiling, full-history
retention and root-retirement procedure documented, and reserves the
daemon-grade adapter, its selection experiments and migration for the
successor milestone.

<a id="concept-plan-scope"></a>
### Scope

The daemon owns session lifetime, the socket, attachment residency, the
collaboration lease, its session index and the local store root it holds for
its process's lifetime. Core owns durable session truth and supports several
independent attachments to one session through its existing race-free attach
barrier and dispatcher. Hosts still supply workspace, identity, policy,
provider configuration and project resources when the daemon starts; no
client connection replaces any of them, and the daemon's configuration may
narrow who may take control but never widens what host policy allows.

The socket reuses ADR 0023's framing, initialize handshake, request,
admission, snapshot, event and progress records and limits unchanged, and
serves generation `loopex.experimental/2` only, which adds `session.list`,
`session.stop`, `daemon.status`, the two control methods and the
writer-epoch field, and lifts the one-attachment-per-process rule to
residency limits. A client offering only generation 1 is refused at
initialize; generation-1 clients keep the M4 foreground server, whose wire
and behavior do not change. Attach is the runtime's race-free cursor
transaction, and delivery is contiguous and at least once: gaps are
forbidden, duplicates are permitted, and a client deduplicates by session
ID, event sequence and event ID as the vision requires. The daemon adds a
bounded resident window, daemon-owned bounded socket output buffers,
detachment at the last emitted cursor and idle eviction; on the local adapter
every durable event stays replayable until the operator retires the root, so
`cursor_expired` remains a defined protocol response no M5 path produces.
The credential handoff to a provider child moves from the process-wide
environment variable to the per-invocation bootstrap channel the launcher
already opens for the nonce and build manifest. The maintainer set this as an
M5 baseline on 2026-09-19: the environment handoff makes the twelve heavy
provider test modules serial, which pins the fast check near the provider
suite's length, and a credential that lives in the parent VM's environment is
a weaker property than one that exists only on a private channel to the child
that needs it. The change stays inside the credential plane: what a child may
receive, from whom and when does not widen; every negative proof M0–M2
established is carried to the new mechanism, not relaxed. It is scheduled as
its own workstream with its own security review, and its measured result is
part of closure.
The residency and lease numbers are exact in the technical envelope and bound
at acceptance with the accepted ADRs 0032 and 0033: 64 attachments per
session, 512 per daemon, a 1,024-event core queue and 4 MiB socket output
buffer per attachment, a 4,096-event and 16 MiB per-session resident window,
512 MiB of aggregate retained encoded event bytes, ten idle minutes, 256
sessions per list page, and a thirty-second lease renewed every ten seconds.

Session creation makes an uncontrolled session; a client then acquires
control before existing-session mutation. Exactly one controller holds a
daemon-owned lease per session; every other attachment is read-only. For an
existing session, the daemon admits a mutation only when its requesting
connection is the holder of a held, unexpired lease and carries its current
writer epoch. Takeover is explicit, only after release or expiry, and mints
a fresh epoch before the successor's first command. The lease lives in the
daemon's memory for the daemon process's lifetime, never in the session
journal or any durable record; every writer epoch is minted fresh and never
reused, so a restart of the daemon or of a session's lease owner leaves that
session uncontrolled with every earlier epoch stale, and the core keeps
mandating no lease. Cancellation crosses processes because the core owns
dispatch: the current controller's `session.abort` cancels work an earlier
controller started, with the truthful two-phase outcome the core already
commits.

The daemon runs every session on the existing local store adapter, selected
for this release by ADR 0031: one state root, the local log the M4
foreground server and CLI already write, and the local writer marker held by
the daemon from before the socket is bound until the daemon exits. The
adapter's limits are the daemon's limits and the operator documentation
states them: a hard 256 MiB log capacity refused as `store_capacity_exceeded`,
a 4 MiB frame ceiling, full-history retention with no compaction, and full
replay at open; a root at capacity is retired by stopping the daemon, moving
the root aside and starting a fresh root. No new store adapter, journal
format version, migration or backup tooling enters M5. After an orderly
daemon stop the foreground server and the CLI reopen the same root and
sessions under the same placement identity, which is also M5's rollback. The
daemon-grade adapter, its selection experiments and its migration are the
successor milestone's first decision under the same ADR.

M4's observability continues without change: every daemon boundary emits the
ADR 0030 spans, and a trace session scoped to the daemon's runtime captures
identities only. The socket path is bounded by the platform and refused when
too long; the socket is owner-only and a foreign peer is refused before
initialize; the daemon never runs as a service manager unit by itself and the
documented launch is a foreground command an operator or their service
manager runs.

The release is one annotated `v0.2.0` tag on the exact reviewed closure
integration commit on `main`, and a source archive of that tagged commit. The
full gate retains a report for a staged candidate archive, extracts it,
compiles it and runs the attended two-process workflow from that extraction;
that staged proof is the last Purpose obligation. After gate green and
independent closure review, a combined explicit closure and release/tag
disposition authorizes the closure transition, integration, tag creation and
post-tag archive verification. The tag and its verification complete the
release after closure; the full gate cannot claim the future tag exists, and
closure does not wait for it. The release publishes no Hex package, binary,
installer or service unit and freezes no public protocol or embedded API.

At the final source candidate, audit every tracked file under
`docs/operator/` and `docs/developer/` for consistency with M5, relevance,
links and indexing where applicable, and stale foreground-only claims. New,
materially updated
and reviewed-unchanged files all receive a recorded per-file disposition;
the independent closure reviewer examines the inventory and any finding
resolution. The seven-row gate table still names the exact files M5 must
materially update. Release instructions describe the required `v0.2.0` tag
and archive workflow without claiming a tag before it exists.

<a id="concept-plan-non-goals"></a>
### Non-Goals

No controller lease, transport, socket or collaboration rule inside core. Its
only M5 change is independent concurrent attachment support. No daemon-grade
store adapter, journal format version, migration, backup tooling, compaction,
retention cutoff or NIF dependency; no daemon-served generation 1; no durable
lease record; no exactly-once delivery promise beyond the founding
at-least-once contract. No WebSocket, HTTP, TCP, remote or native-BEAM
transport; no multi-host or multi-user identity, tenancy or authorization
beyond the socket's owner-only peer rule; no trusted extension activation,
isolated hands, ACP mapping, public-protocol freeze, hosted store, Hex
package, binary, installer or service-manager integration. Generation 2 adds
daemon methods and lease fields only; no other protocol breadth. Those
capabilities retain their vision barriers and require their own evidence.

## Workstreams

After M4 closes, reconstruct M5's valid opening checkpoint and settle the
three prerequisite decisions before M5 acceptance. After acceptance, land the
one application through its holder transaction and the narrow core
attachment change, then build daemon lifetime and socket over the local
adapter, prove collaboration and replay on that base, and join the
two-process workflow with the reference CLI and the TypeScript consumer
before method breadth. Reuse M4's focused checkpoints, clause witnesses and
integrated self-audit; full inherited checks remain at contract moments and
scheduled CI. No second loop, lease in core or transport registry.

**Revision of 2026-09-14 (first).** On the independent review of
`dc81212360327caa7e8b0ed371cb5ed531b960d9`, the maintainer decided to narrow
this Open plan in three ways. The daemon-grade store, its selection
experiments and its migration leave M5 for the successor milestone, so M5
adds one application. The daemon serves generation 2 only, so no
generation-1 exclusive lease exists. The controller lease is daemon memory,
so no durable daemon-control store exists. The rung question needs none of
the three, each doubled evidence without adding a proved capability, and the
daemon on the local adapter already reopens under the foreground server after
an orderly stop.

**Revision of 2026-09-14 (second).** On the independent review of
`6e8319da299dc92ef0c2441da8e0443262292fb8`, the maintainer accepted every
finding and two recommendations. Delivery is stated as the founding
at-least-once contract with client deduplication, because a stronger daemon
promise would contradict the vision and no other surface honors it. ADR 0031
returns as an M5 prerequisite, selecting the existing local adapter with its
256 MiB ceiling, full retention and root-retirement procedure documented,
rather than being deferred outright: the reference daemon runs on an
ADR-selected store and the roadmap ties operational claims to store
selection, so the daemon needs a recorded selection even when the selected
adapter is the existing one; the daemon-grade adapter and migration stay with
the successor. The closure and release cycle is broken by ending the last
Purpose outcome at the staged, release-ready source archive and making the
tag a post-closure release completion. The `cursor_expired` witness is
removed because the local adapter retains everything until the root is
retired, so no truthful path reaches it. `session.list` is kept with an exact
bounded page contract over a daemon-owned index, because observers without
filesystem access to the root would otherwise have no discovery; removal was
the cheaper alternative and was rejected for that reason. Writer epochs are
minted fresh per grant so a lease-owner restart can never reuse one; startup
acquires the store writer marker before touching the socket and store loss
closes the listener; byte limits live in daemon-owned socket output buffers
while core keeps its event-count queues; the report validator requires
exactly `0.2.0`; and wording now says the daemon process's lifetime and
names the reused and added protocol parts precisely.

These Open M5 planning bytes were drafted on branch `m5` from the integrated
M4 acceptance checkpoint `6f973f774a403f76330058e3d0a59f7b83e038f1`.
M4 is Accepted and remains the sole implementation authority; these bytes
grant no M5 implementation authority and do not establish a valid lookahead
opening. The inherited M1 and M2 gates were unavailable on this base, and
the M4-specific waiver and deferral do not authorize an M5 exception. Before
M5 acceptance, reconstruct its branch-only opening checkpoint on M4's exact
Closed, integrated, inherited-green product base, re-prove every inherited
gate green and M5's distinct behavioral red, settle prerequisites, and obtain
fresh exact-SHA review. No candidate produced by this unavailable opening is
eligible for acceptance or integration.
