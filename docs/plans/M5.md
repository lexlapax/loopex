## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Let independent client processes share one durable session without any of
them owning its lifetime. A local daemon owns every session in a state root:
it keeps sessions running while no client is connected, serves several client
processes over a Unix-domain socket with the same protocol the M4 foreground
server speaks, lets exactly one client drive while others observe, survives
the driver's crash with an explicit takeover, replays snapshot and cursor to a
reconnecting client without gaps or duplicates, cancels work across
processes, and keeps all of it on a store built for a long-lived service.
Complete M5 as an operator-usable, source-only `0.2.0` release: from the
exact source candidate, an operator follows the documented setup, starts the
daemon, and drives one session from two real client processes with their own
inputs. Closure review and an explicit combined closure and release/tag
disposition then lead to an integrated closure commit on `main`, annotated
`v0.2.0` tag and verified source archive. The M5 closure workflow is complete
only when that post-tag evidence is retained.

M5 answers the vision's durable-service question and carries the roadmap's
v0.2 candidate rung. It reuses M4's protocol, interactions, transfers and
observability unchanged and adds the daemon, its store and its collaboration
rule above the core. The core's attachment machinery gains narrow support for
several independent attachments to one session; it gains no lease, transport
or second loop.

<a id="concept-plan-scope"></a>
### Scope

The daemon owns session lifetime, the socket, attachment residency, the
collaboration lease and its own store root. Core owns durable session truth
and supports several independent attachments to one session through its
existing race-free attach barrier and dispatcher. Hosts still supply
workspace, identity, policy, provider configuration and project resources
when the daemon starts;
no client connection replaces any of them, and the daemon's configuration may
narrow who may take control but never widens what host policy allows.

The socket carries ADR 0023's JSONL protocol unchanged. Generation
`loopex.experimental/2` adds the daemon methods and the lease fields and lifts
the one-attachment-per-process rule to residency limits. Generation-1 wire
records and methods stay unchanged; the daemon grants one internal exclusive
lease before generation-1 attach or resume enters core and refuses concurrent
generation-1 or generation-2 access to that session. Attach is the
runtime's race-free cursor transaction; the daemon adds a bounded resident
window, bounded per-attachment queues, detachment at the last emitted cursor,
idle eviction and `cursor_expired` beyond retention. The residency and lease
numbers are exact in the technical envelope and bound at acceptance with the
accepted ADRs 0032 and 0033: 64 attachments per session, 512 per daemon, a
1,024-event and 4 MiB per-attachment queue, a 4,096-event and 16 MiB
per-session resident window, 512 MiB of aggregate retained encoded event
bytes, ten idle minutes, and a thirty-second lease renewed every ten seconds.

Generation-2 session creation makes an uncontrolled session; a client then
acquires control before existing-session mutation. Exactly one controller holds a daemon-owned
lease per generation-2 session; every other attachment is read-only. For an
existing session, the daemon admits a mutation only when
its requesting connection is the holder of a held, unexpired lease and carries
its current writer epoch. Takeover is explicit, only after release or expiry,
and advances the epoch durably before the successor's first command. The
lease lives in a separate durable daemon runtime-control store surface, never
in the session journal, and the core keeps mandating no lease. Generation-1
exclusive lease preserves a single writer without adding a lease field
to that wire generation. Cancellation crosses
processes because the core owns dispatch: the current controller's
`session.abort` cancels work an earlier controller started, with the truthful
two-phase outcome the core already commits.

The daemon-grade store is a new adapter behind the unchanged private Store
ports, selected between a BEAM-native segmented-log candidate and a
SQLite-backed candidate by the shared conformance and fault-injection suites
in isolated, disposable contract experiments after M4 closes and before ADR
0031 and M5 are accepted; the recommendation is the native candidate. The
selected implementation imports an M4 local log one way, retains the
original as the rollback pair, and records every migration step. The exact
M4 binary safely refuses a daemon root as an invalid store file; it cannot
name a format version it does not know. The foreground server and the CLI
keep working on the local adapter.

M4's observability continues without change: every daemon boundary emits the
ADR 0030 spans, and a trace session scoped to the daemon's runtime captures
identities only. The socket path is bounded by the platform and refused when
too long; the socket is owner-only and a foreign peer is refused before
initialize; the daemon never runs as a service manager unit by itself and the
documented launch is a foreground command an operator or their service
manager runs.

The release is one annotated `v0.2.0` tag on the exact reviewed closure
integration commit on `main`, and a source archive of that tagged commit. The
full gate first retains a report for a staged candidate archive and runs the
attended two-process workflow from its fresh extraction. After gate green and
independent closure review, a combined explicit closure and release/tag
disposition authorizes the closure transition, integration, tag creation and
post-tag archive verification. Those are required to complete M5's closure
workflow; the full gate cannot claim the future tag exists. The release
publishes no Hex package, binary, installer or service unit and freezes no
public protocol or embedded API.

At the final source candidate, audit every tracked file under
`docs/operator/` and `docs/developer/` for consistency with M5, relevance,
links and indexing where applicable, and stale foreground-only claims. New,
materially updated
and reviewed-unchanged files all receive a recorded per-file disposition;
the independent closure reviewer examines the inventory and any finding
resolution. The seven-row gate table still names the exact files M5 must
materially update. Release instructions describe the required `v0.2.0` tag
and archive workflow without claiming a tag before it exists.

<a id="concept-plan-non-goals"></a>
### Non-Goals

No controller lease, transport, socket or collaboration rule inside core. Its
only M5 change is independent concurrent attachment support. No
WebSocket, HTTP, TCP, remote or native-BEAM transport; no multi-host or
multi-user identity, tenancy or authorization beyond the socket's owner-only
peer rule; no trusted extension activation, isolated hands, ACP mapping,
public-protocol freeze, hosted store, Hex package, binary, installer or
service-manager integration. Generation 2 adds daemon methods and lease
fields only; no other protocol breadth. Those capabilities retain their
vision barriers and require their own evidence.

## Workstreams

After M4 closes, reconstruct M5's valid opening checkpoint, then run the two
isolated ADR 0031 contract experiments under explicit bounded authorization
and settle the three prerequisite decisions before M5 acceptance. After acceptance,
land the narrow core attachment change and a separate durable daemon-control
store surface, then build daemon lifetime and socket over the local session
adapter. Prove collaboration and replay on that base before the selected
daemon-grade session adapter and migration rejoin; then join the two-process
workflow with the reference CLI and
the TypeScript consumer before method breadth. Reuse M4's focused
checkpoints, clause witnesses and integrated self-audit; full inherited checks
remain at contract moments and scheduled CI. No second loop, lease in core or
transport registry.

These Open M5 planning bytes were drafted on branch `m5` from the integrated
M4 acceptance checkpoint `6f973f774a403f76330058e3d0a59f7b83e038f1`.
M4 is Accepted and remains the sole implementation authority; these bytes
grant no M5 implementation authority and do not establish a valid lookahead
opening. The inherited M1 and M2 gates were unavailable on this base, and
the M4-specific waiver and deferral do not authorize an M5 exception. Before
M5 acceptance, reconstruct its branch-only opening checkpoint on M4's exact
Closed, integrated, inherited-green product base, re-prove every inherited
gate green and M5's distinct behavioral red, settle prerequisites, and obtain
fresh exact-SHA review. No candidate produced by this unavailable opening is
eligible for acceptance or integration.
