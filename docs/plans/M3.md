## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Make compatible project skills useful through the local runtime, and finish the
core admission, availability and retention repairs needed to extend it safely.
An operator imports a pinned skill, inspects and admits its exact content,
selects it before a run, and uses the existing tool and artifact-inspection
workflow through both embedding and the reference terminal.

Keep M3 and M4 separate. M3 proves this bounded local capability; M4 adds durable
operator interactions, bounded artifact ranges and external protocol consumption.
Those M4 contracts still belong to core and its ports before the wire maps them.
Resource packs do not require trusted OTP extension activation, and the vision's
serial barriers and separate compatibility freezes remain intact.

M2's delays came from product defects found in post-closure audits, broad work
without early integrated proof, and brittle locks. M3 addresses all three:
prove one complete workflow early, audit failure paths across every entrypoint,
and use focused checkpoints with clause witnesses instead of freezing mutable
test inventories. Exact-candidate validation remains required at contract
moments; the Technical envelope records the maintainer's M3-only replacement
for the new inherited aggregate at plan acceptance.

<a id="concept-plan-scope"></a>
### Scope

Reference discovery enumerates only `.agents/skills/<name>/SKILL.md` under the
canonical workspace, then performs one bounded content-independent walk inside
each selected pack directory. A selected Git directory supplies its bounded
supporting files. No home/configured root, workspace-history discovery, HTTPS
single-file import or traversal chosen by content is included. M3 acquisition is
credential-free public HTTPS Git; private sources and credential channels are
deferred. A workspace repository origin enters the resource manifest only as an
already-canonical credential-free public HTTPS identity; every other raw remote
becomes nil before display, retention or digest construction.

Installation and session admission are separate: installation never grants
context trust or execution authority. Runtime Control commits the acquisition
command, intent, bound grant and attempt through the Store before dispatch. The
host owns the canonical workspace-root/reference/lease binding and the existing
policy callback explicitly authorizes the exact acquisition. Runtime Control and
Store own command, intent, attempt, reconciliation query/result, terminal truth
and commit-unknown recovery. The local hand validates the current binding and owns
Git, process and staging lifetime, retained execution receipts, and solicited
reconciliation responses. It syncs prepared provenance through an atomic
operation-owned slot before one no-replace publication
and commits the final destination binding only after complete revalidation.
For first installation it creates only fixed ordinary project parents through
no-follow, sync-and-reopen steps and stages in a same-filesystem sibling outside
the discovery root. The reference CLI retains the active member of one bounded
locator-journal family before every Store call; a lost binding or command
acknowledgement replays only the same authorized bytes, while a safely abandoned
or completed administrative runtime gains the family's compact retirement marker
before its large retained snapshot is released. A settled import
is used only by a different freshly bound runtime after complete rediscovery and
a new trust decision. The live administrative runtime remains on its immutable
launch snapshot; a later start derives normal or recovery-only mode from fresh
attestation against that binding.
Composition only wires these owners. Acquisition uses its own administrative
request/grant/receipt family, never a session `JobRequest`, registry entry or
model-visible tool, and carries no fictitious session/run/turn/tool-call/tool
identity.

An uncertain operation cannot retry blindly, clean unproved staging, publish or
establish remote provenance. Append-only solicited reconciliation may prove exact
non-dispatch or current process absence and release process quarantine. It never
automatically deletes staging or destination bytes or rewrites an unknown outcome.
An existing destination refuses without mutation. Across interruption cuts,
attempt-owned writes leave the destination absent or complete; an unrelated
racing writer may leave other bytes, which remain untouched and are never
attributed to the attempt. A complete pack without matching committed hand and
Store truth is local. Rediscovery advertises remote provenance
only while the Store terminal, hand receipt, provenance generation, destination
identity and complete current bytes match. An explicit trusted-host resource
binding supplies exactly the workspace reference, zero or one bound manifest,
fresh current-workspace attestation and durable binding intent. It commits or matches immutably before children
start; changed or unavailable current bytes allow only exact recovery and
settlement, while omitting it keeps the runtime resource-
disabled and preserves core-only and genuine M2 starts. Trust binds workspace repository
identity and the complete source-qualified manifest transitively; changed bytes
require a new runtime binding and operator decision.

Admission, skill selection and selection of already manifested supporting labels
are explicit operator/host commands while the session is settled, before a new
run. Each run retains an immutable selection. Model output cannot activate a
skill or issue a resource command. Before a decision, the operator reviews every
manifested file identity and body through bounded, ordered, digest-bound terminal
or structured pages. An absent decision withholds content while
ordinary coding continues. Unsupported vendor execution fields are diagnosed;
scripts, hooks, command interpolation and `allowed-tools` remain inert data.
Ordinary tool requests still cross the existing host policy and executor grant
boundary. A hostile pack must leave the tool set, an identical request's policy
result and the grant set unchanged.

M3 adds experimental resource queries, session command/receipt variants, one
pre-child resource-binding Store transaction with its durable host pre-submit
intent, one runtime-control acquisition
transaction family, one bounded CLI locator/retirement journal family, and one narrow executor-
side acquisition hand. Existing
root AGENTS.md discovery, M2 histories and refusal meanings remain unchanged.
New records are versioned; an M2 binary refuses a session containing any resource
command before effects, even when that command was refused. Sessions without a
resource command retain M2-compatible journal forms, but an M2 binary cannot
safely open a Store/hand root containing a resource snapshot binding or M3
acquisition records. CLI locator journals are M3 host-private siblings that M2
does not interpret and therefore cannot use as rollback or refusal evidence. A genuinely unbound M2 runtime remains usable only in
resource-disabled mode and cannot be upgraded in place. Rollout uses
fresh development roots and retained old Store/hand root plus binary pairs for
rollback, with no in-place downgrade or public compatibility promise. Artifact inspection uses the existing integrity-
checked full-object fetch and its limits; M3 makes no bounded-range or bounded-
allocation claim. The accepted Elixir/OTP pins remain unchanged; Proposed ADR
0025 adds the stated C11 source-build prerequisite and packaged private Port
helper for the local executor. There is no release, tag or publication.

Trusted model/executor launch configuration must behave consistently in CLI,
embedding and prepared recovery. M2 provider protection, prepared handoff,
settlement-v2, cleanup grace and Bash prerequisite are inherited guarantees.
M2 remains Closed; skills are new M3 scope.

The maintainer-approved
[CLI exception](../developer/agent-context-map.md#override-disposition-m3-cli-extension-ratification-2026-09-10)
preserves all five inherited commands and permits `skill`; it does not require a
separate Closed-M2 amendment transaction. Further inherited restrictions change
only through explicit scoped approval.

<a id="concept-plan-non-goals"></a>
### Non-Goals

Durable policy defer/answer, range reads and the development-floor refresh are
M4 scope. M3 adds no second policy evaluator, interaction record/event family,
new app or Hex package dependency, ordinary executor `JobRequest` kind, default tool,
private credential channel or generic administrative-effect framework; its one
narrow resource-acquisition family and repository-owned libc-only Port helper
are the stated exceptions. Building the local executor on supported Darwin and
Linux targets requires a C11 compiler and platform headers; the runtime ships the
built helper and needs no compiler. Model-driven
skill activation, implicit remote installation, hosted skill APIs, marketplace
search, automatic updates, configurable discovery roots, generic context
providers, daemon lifetime and VM-global plugin activation remain outside M3.
The local framework is the fixed resource seam plus existing tool registration;
no generic plugin loader is required for this capability.

## Workstreams

One integrator owns the candidate and integration. Contract and prerequisite
settlement precedes the thin integrated workflow; independent repairs may then
proceed in isolated worktrees. Breadth rejoins incrementally behind working
shared contracts. Final self-audit precedes independent closure review.

**Research and scope rationale**

Research reviewed for this proposal on 2026-09-09 distinguishes portable
resource directories, discovery catalogs and hosted services:

- [Agent Skills specification](https://agentskills.io/specification) defines
  SKILL.md metadata, instructions and optional supporting files. Its
  [client guidance](https://agentskills.io/client-implementation/adding-skills-support)
  informs discovery, explicit selection and progressive loading. Compatibility
  is a declared tested subset, not permission to inherit every vendor field.
- [skills.md documentation](https://skills.md/docs) describes hosted execution
  through service interfaces. Downloadable resource packs meet M3's local
  foundation outcome; adding a hosted execution provider is separate scope.
- [skills.sh](https://skills.sh/) and the
  [Vercel installer source](https://github.com/vercel-labs/skills/blob/main/src/local-lock.ts)
  inform distribution and local lock/provenance. The previous blanket claim
  that this installer carries no checksums or provenance is incorrect: its
  lock records source information and a computed content hash.
- [GitHub CLI skill installation](https://cli.github.com/manual/gh_skill_install)
  illustrates explicit sources and pinned revisions. Loopex still makes its own
  acquisition, containment, retention and trust decisions.
- [SkillsMP](https://skillsmp.com/) is a discovery index, and
  [Tessl evaluation](https://docs.tessl.io/evaluate) supplies evaluation signals;
  neither is a runtime authority or substitute for Loopex's negative tests.
- [Claude Code skills](https://code.claude.com/docs/en/skills) include richer
  execution and invocation semantics. Preserve manual-only restrictions and
  diagnose unsupported execution fields; do not import tool permission grants.
- [OpenClaw skills](https://docs.openclaw.ai/skills) illustrates another skills
  and registry ecosystem. Package discovery and trusted code activation remain
  separate decisions in Loopex.

A skill is the first resource-pack capability, not the definition of the whole
foundation milestone. Resource identity, explicit launch wiring and safe core availability/retention
complete this milestone. M4 adds durable interactions and bounded artifact access
at those existing owners before projecting them to external clients.
