## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Make the local runtime useful to extend and safe for another client to consume.
An operator can acquire a compatible Agent Skill, inspect and admit its exact
content, select it for a coding session, answer a durable policy question, and
inspect the resulting artifact. Embedded callers and the reference terminal
exercise the same session semantics. M4 then exposes these working capabilities
to an independent program.

Keep M3 and M4 separate because they have different outcomes and useful review
boundaries: M3 proves reusable local behavior; M4 proves external consumption.
Neither test counts nor separate compatibility surfaces alone mandate a split.
A merged gate would still need the same ordered contract and integration proof.
Resource packs do not require trusted OTP extension activation. The vision's
multi-client and activation barriers remain intact.

M2's two weeks of repeated implementation and review exposed missing composition,
lifetime, compatibility and evidence checks. This milestone addresses those
causes before breadth: settle shared decisions, run one integrated workflow
early, review the actual boundary witnesses, and audit every entry path before
final independent review. A larger checklist or a promised number of review
rounds is not the success criterion.

<a id="concept-plan-scope"></a>
### Scope

Skills use the portable Agent Skills directory format. The reference host
searches `.agents/skills/<name>/SKILL.md` and explicitly configured host roots;
it does not implicitly search a user's home. Duplicate names are diagnosed and
require an explicit source-qualified selection. Git imports include the selected
skill directory and bounded supporting files; a direct HTTPS import includes
only the named SKILL.md and follows no links in its content.

Installation records provenance and publishes an inspectable local pack. It does
not admit its content into a session or grant tool authority. Trust binds the
workspace, source/revision and complete manifest digest. Changed bytes require a
new decision. An absent decision withholds that content while ordinary coding
continues. Explicit skill selection is available to operators and model-driven
selection is limited to the admitted catalog. Unsupported execution-oriented
vendor fields produce diagnostics; manual-only restrictions are preserved.

Scripts remain resources until an ordinary tool request passes host policy and
executor admission. Hooks, imports, command interpolation and `allowed-tools`
metadata never become authority. Resource retention has its own identity;
skills are not mislabeled as tool-output artifacts.

The local framework consists of fixed resource classes and the existing scoped
tool registry, plain host configuration, durable interactions and public query
boundaries. M3 supplies no generic plugin loader. Host-selected model options
and executor probe configuration must reach the CLI, embedding composition and
recovery path consistently; selection is fixed at launch/session admission, not
an untrusted wire option or mid-run model switch.

The existing root AGENTS.md behavior, provider protection, explicit prepared
handoff, settlement-v2 provenance, cleanup grace and reference-executor Bash
prerequisite are inherited M2 behavior. They are regression obligations, not new
M3 deliverables. M2 remains Closed; skills are new M3 scope, not a retrospective
M2 gate generation.

<a id="concept-plan-non-goals"></a>
### Non-Goals

Hosted skills services, marketplace search, automatic updates, implicit remote
installation, arbitrary URL crawling, automatic script execution, generic
context-provider registration, memory/retrieval products, daemon lifetime,
concurrent-client leases, VM-global extension activation, new default coding
tools, mid-session model switching and public compatibility freezes stay out.
Skill directories and hosted APIs using the name “skills” are distinct products.

M3 creates no release, tag or package publication. Runtime-floor and Closed-gate
amendment decisions are separate prerequisites; this plan's acceptance cannot
supply those decisions.

**Research and scope rationale**

Research reviewed for this proposal on 2026-09-09 distinguishes portable
resource directories, discovery catalogs and hosted services:

- [Agent Skills specification](https://agentskills.io/specification) defines
  SKILL.md metadata, instructions and optional supporting files. Its
  [client guidance](https://agentskills.io/client-implementation/adding-skills-support)
  informs discovery, explicit selection and progressive loading. Compatibility
  is a declared tested subset, not permission to inherit every vendor field.
- [skills.md documentation](https://skills.md/docs) describes hosted execution
  through service interfaces. Downloadable resource packs meet M3's local
  foundation outcome; adding a hosted execution provider is separate scope.
- [skills.sh](https://skills.sh/) and the
  [Vercel installer source](https://github.com/vercel-labs/skills/blob/main/src/local-lock.ts)
  inform distribution and local lock/provenance. The previous blanket claim
  that this installer carries no checksums or provenance is incorrect: its
  lock records source information and a computed content hash.
- [GitHub CLI skill installation](https://cli.github.com/manual/gh_skill_install)
  illustrates explicit sources and pinned revisions. Loopex still makes its own
  acquisition, containment, retention and trust decisions.
- [SkillsMP](https://skillsmp.com/) is a discovery index, and
  [Tessl evaluation](https://docs.tessl.io/evaluate) supplies evaluation signals;
  neither is a runtime authority or substitute for Loopex's negative tests.
- [Claude Code skills](https://code.claude.com/docs/en/skills) include richer
  execution and invocation semantics. Preserve manual-only restrictions and
  diagnose unsupported execution fields; do not import tool permission grants.
- [OpenClaw skills](https://docs.openclaw.ai/skills) illustrates another skills
  and registry ecosystem. Package discovery and trusted code activation remain
  separate decisions in Loopex.

A skill is the first resource-pack capability, not the definition of the whole
foundation milestone. Durable interactions, resource identity, bounded artifact
access, explicit launch wiring and safe core availability/retention are the
other shared requirements that would otherwise be discovered while building M4.
