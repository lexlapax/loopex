## Concept

Technical depth: [M8 installed durable operator](M8-technical.md#technical-depth).

M8 is the Open planning successor to the Closed
[M7 coding-agent proof](M7.md#concept). M7 closed on 2026-10-13 and is the
source release `v0.4.0`. M8 was drafted as the installed operator plan, first
numbered M6 and then M7; historical records keep those names. It was rescoped
to the delivered M7 baseline on 2026-10-13 and completed for implementation
the same day under the maintainer decisions below. Its release label is
`0.5.0`. It authorizes no publication.

<a id="concept-plan-purpose"></a>
### Purpose

Technical depth: [Prerequisites](M8-technical.md#technical-plan-prerequisites).

M7 made Loopex a capable coding agent, but it runs only from a source checkout
with an Elixir/OTP toolchain. M8 makes it something an operator installs,
configures once, leaves running, talks to from any terminal, and backs up.

An operator should be able to:

- install a verified archive on a clean supported machine with no toolchain;
- configure one home and inspect what a new session would use and why;
- start, stop and diagnose the durable service, and have it started on demand;
- hold M7's conversation, including its read-only helper roles, through that
  service, leave the terminal without ending the work, and reconnect to it;
- back up a stopped root and restore it on the same machine with two commands,
  including when a root cannot be served;
- trust that the installed release opens only roots in its own current format,
  refuses any other root before writing to it, adopts a root the M7 source
  build wrote only after reading all of it, and offers backup and restore
  under the matching build as the way back;
- sign in to a provider with a ChatGPT plan or a Google Cloud project instead
  of an API key, where the provider admits Loopex as its own client.

M7 delivered the pieces M8 builds on:

- the foreground conversation, explicit configuration, saved roles, provider
  routing, compaction, questions and bounded helpers;
- the `loopex.experimental/3` foreground and `loopex.experimental/4` daemon
  wire generations, including daemon control, configuration and compaction;
- daemon detach and reattach at a cursor without cancelling the run;
- helper-history classification, stop-only recovery and the helper route guard
  in the daemon, without a daemon-hosted helper parent;
- host-embedded restore of a current-format root under
  [ADR 0051](../adr/0051-current-format-physical-restore.md#concept);
- per-connection transfer accounting under
  [ADR 0066](../adr/0066-owned-artifact-transfer-opening.md#concept);
- the retirement of superseded surfaces under
  [ADR 0070](../adr/0070-pre-1-superseded-surface-retirement.md#concept).

M8 adds installation, lifecycle, attachment, service-hosted helpers, operator
backup and restore, and provider sign-in around them. It adds no model-facing
tool. Sign-in adds provider routes and a credential form, not a new authority.

The store remains the existing local adapter within its documented limits. The
engine that removes the 256 MiB ceiling, its measured selection and its
migration are the store successor's work, in the
[M9 draft](../drafts/m9-store-engine-successor.md#concept). Trusted extension
activation is the [M10 draft](../drafts/m10-governed-extension-runtime.md#concept).

<a id="concept-plan-scope"></a>
### Scope and Non-Goals

Technical depth: [Packaging](M8-technical.md#technical-plan-packaging).

Technical depth: [What M8 inherits from M7](M8-technical.md#technical-plan-inherited).

Technical depth: [Compatibility](M8-technical.md#technical-plan-compatibility).

**Scope.** The eight outcomes. M8 owns installation, home discovery,
configuration writers, service lifecycle and readiness, conversation
attachment, service-hosted helpers, the operator backup, restore and adopt
commands, the current-format root marker, and provider sign-in. Operator and
developer documentation accompanies every outcome, with copyable commands and
semantic review.

M8 inherits M7's instruction-bearing roles, model switching and bounded
helpers, and runs them through the service as well as in the foreground. It
introduces no second role, provider or configuration schema. ADR 0073 adds
three sign-in routes and an `oauth` credential form as additive members of ADR
0049's schema version 1. A home's existence never turns the ephemeral `ask`
into durable operation. ADR 0028's per-connection transfer accounting and its
1 GiB cumulative allowance were delivered by M7 under ADR 0066 and are not M8
work.

An attached conversation works in the workspace its service was started with.
The service is the host: it alone chooses workspace, policy, provider binding,
credentials, roles and tracing, and a connected terminal can name none of
them. One home serves one state root and one workspace; another workspace is
another service on another root. Attachment is local, over the daemon's
existing Unix-domain socket, for the same operating-system user.

**Non-goals.**

- **Store:** no engine implementation, engine selection, migration or capacity
  change. The 256 MiB log ceiling and its retirement procedure remain.
- **Compatibility:** no upgrade from an older-format root, no older-root
  reader and no cross-version rollback proof, under the
  [pre-1.0 rule](../process/agent-context-map.md#disposition-pre1-current-contract-2026-10-02).
  Adoption marks only a root the current decoders already read in full.
- **Recovery:** no per-session quarantine. A root with an unreadable session
  history is recovered by restoring a backup.
- **Restore scope:** what ADR 0051 admits, as amended by ADR 0072. That means
  the same machine, with the original workspace directory at its recorded
  physical identity. Another host, a lost or recreated workspace, partial or
  selective rewind and automatic removal of uncertain effects stay out.
  Restore does not back up or restore workspace contents or the configuration
  file, and never rewrites configuration.
- **Credentials:** no file, keychain or command source for API keys, and no live
  rotation of an environment credential or reload of configuration. Sign-in
  tokens, their host-owned store and their same-account refresh are in scope
  under ADR 0073. No other product's OAuth client identity is used, except
  that the `adc` source refreshes the grant in gcloud's own file under that
  file's client (D20), and the consumer Gemini CLI and Code Assist sign-in is
  out.
- **Helpers:** no parallel helpers within one parent conversation, no writable
  helpers and no nested children. A helper child is never prompted, steered,
  configured, compacted, answered, aborted or resumed by a client.
- **Attachment:** no network transport, no cross-user attachment, no
  multi-workspace service and no observer mode on the conversation command.
- **Residency:** the daemon's existing limit of 64 session activations per
  daemon lifetime is unchanged, and helper children count toward it. A service
  left running eventually refuses new work until it is restarted.
- **Service management:** no launchd or systemd unit installation.
- **Surface:** no full-screen terminal interface and no MCP.
- **Other rungs:** no extension activation, no protocol or API freeze.
- **Publication:** no package publication, signing, notarization or name
  clearance is authorized by this plan.

Any added capability needs its own scoped acceptance decision.

<a id="concept-plan-rollout"></a>
### Rollout and Compatibility

Technical depth: [Compatibility](M8-technical.md#technical-plan-compatibility).

Technical depth: [Current-format roots and recovery](M8-technical.md#technical-plan-migration).

Before 1.0, each boundary keeps only its current contract. The installed
`0.5.0` release reads only roots in its own current format. It never infers
support from the container, and it migrates nothing. A root without the
marker, including one written by the M6 or M7 source builds, is refused by
name before any write and stays byte-identical. An operator may adopt such a
root once the M7-built writer is stopped: adoption first writes an `adopting`
marker that every `0.5.0` command refuses, reads every record with the current
decoders, and makes the marker current only when all of them decode and the
root did not change. Adoption changes no record, except that an executor
ledger bound through an alias path gains a generation bound to the physical
path, carrying its open authority unchanged (D45, D48). A killed adopt or a changed
root leaves the `adopting` marker, and a rerun of adopt audits the root again
in full (D17). Any change to a durable member, shape or encoding of a root
requires a new format number, in any release including a patch (D28), and so
a `0.5.x` build that changed the format would refuse a format-1 root by name
rather than misread it, until a separately decided migration exists. The fast
check holds part of that rule: a retained format-1 root and the retained M7
root must pass the full audit, the pure codecs must re-encode them exactly,
and a named set of limits is checked at the edge. A change the retained roots
do not reach, or one inside a writer that still leaves them readable, is
caught by review under D28.

The way back from an unsupported or unservable root is a backup restored under
the build whose format it is. A backup is the whole state root, so a restored
root starts as the backed-up root would have. Restore preserves session
history and effect uncertainty and does not undo workspace effects. Work done
after the backup is lost; restoring an older backup requires the operator to
say so with `--discard-later-work`, and the documentation says so plainly.

Sign-in adds configuration members, a token store outside the state root,
one public failure reason, the `daemon.stopping` reason
`fatal:sign_in_route_lost` (D42) and the `loopex.ask/1` status-1 codes
`sign_in_route_lost`, `provider_sign_in_required` and `sign_in_unavailable`
(D38, D50). A build without them refuses the new members by
name; before 1.0 no older reader is supported.

<a id="concept-plan-workstreams"></a>
## Workstreams

Technical depth: [Ownership and rejoin](M8-technical.md#technical-plan-ownership).

Technical depth: [Implementation order](M8-technical.md#technical-plan-order).

Five workstreams with non-overlapping paths, each writer in its own worktree,
and one integrator who owns rejoin, conflicts, shared files and post-rejoin
verification:

- **Integration** owns the launcher's discovery, configuration writers,
  lifecycle commands, readiness, the service's configuration reader and the
  attached conversation.
- **Daemon helpers** is the integrator's own second piece: the service hosting
  helper parents and children, after the attached conversation works.
- **Packaging** owns the release recipe, manifest, verifier, companion
  relocation and the installed lane.
- **Backup and restore** owns the root marker, adopt, backup and restore.
- **Provider sign-in** owns the sign-in routes, token store, refresher,
  `auth` commands, the reply ceiling and the public failure reason.

The marker lands first, because it changes every path that opens a root,
together with the shared separation check the home module calls. The first
rejoin is one installed workflow: install, configure, start, converse,
detach, reconnect and stop, from a locally built archive. Helpers, backup and
restore, and sign-in rejoin after it; failure matrices and the installed
demonstration follow.
