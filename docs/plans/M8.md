## Concept

Technical depth: [M8 installed durable operator](M8-technical.md#technical-depth).

M8 is the Open planning successor to the Accepted
[M7 coding-agent proof](M7.md#concept). It was drafted as the installed
operator plan, first numbered M6 and then M7; historical records keep those
names. It cannot be accepted or implemented until M7 closes, and it selects no
release version.

<a id="concept-plan-purpose"></a>
### Purpose

Technical depth: [Prerequisites](M8-technical.md#technical-plan-prerequisites).

After M7, Loopex is a capable coding agent that runs only from a source
checkout with an Elixir/OTP toolchain. M8 makes it something an operator
installs, configures once, leaves running, converses with from any terminal,
backs up and upgrades.

An operator should be able to:

- install a verified archive on a clean supported machine with no toolchain;
- configure one home and inspect what a new session would use and why;
- start, stop and diagnose the durable service, and have it started on demand;
- hold M7's conversation through that service, detach, and reconnect to it;
- back up a closed root and restore it, including as the documented exit when
  a root cannot be served;
- upgrade from an M7 root and return to the exact state before the upgrade.

M7's conversation, explicit configuration, saved roles, provider routing,
compaction, questions and helpers are predecessor deliverables, conditional on
M7's closure. M8 adds installation, lifecycle and attachment around them. It
adds no model-facing capability.

The store remains the existing local adapter within its documented limits. The
engine that removes the 256 MiB ceiling, its measured selection and its
migration are the store successor's work, in the
[M9 draft](../drafts/m9-store-engine-successor.md#concept). Trusted extension
activation is the [M10 draft](../drafts/m10-governed-extension-runtime.md#concept).

### Outcomes

Technical depth: [Evidence mapping](M8-technical.md#technical-plan-evidence).

| # | Outcome | Evidence class |
| --- | --- | --- |
| 1 | **Installed artifact.** One installed command from a verified platform-specific OTP release archive with bundled ERTS and the protected provider companion | Manifest, linkage and install proof on a clean host of each supported platform |
| 2 | **Installed home and configuration.** A default home, automatic loading of its configuration file and atomic configuration writers over M7's single schema and resolver; explicit-file use remains available | Precedence, origin, invalid-input and write-fault tests |
| 3 | **Store readiness.** A container-format marker, a reader boundary that checks durable-record support before serving a root, and backup and restore of a closed root as one verifiable archive | Exact reader and archive fixtures, fault cuts and negative tests |
| 4 | **Service lifecycle.** Start, stop, status and diagnostic commands and start-on-demand over the existing daemon and controller contracts, with a truthful readiness report | Process races, readiness, drain and operator-recovery tests |
| 5 | **Attached conversation.** `loopex chat` holds M7's conversation as a client of the running service: it prompts, steers, answers, follows up, configures and compacts under the controller lease, detaches without ending the run, and reconnects | Terminal and piped-input tests against a real daemon, lease and replay negatives, attended reconnect |
| 6 | **Installed operator demonstration.** Install, configure, converse, detach and reconnect, stop, restart, inspect, back up, restore and remove the installation | Real-provider installed-artifact lane on each supported platform and an attended record |
| 7 | **Upgrade and rollback.** An M7 root opens under the installed candidate; an unsupported reopening is refused before any write; rollback restores the pre-upgrade backup for the matching prior build | Exact binary and record combinations, backup restore under the prior build, unsupported-reader negatives |
| 8 | **Transfer accounting.** ADR 0028's artifact-transfer concurrency counted per connection and its accepted 1 GiB cumulative transfer-work allowance, replacing the disclosed per-attachment divergence | Multi-attachment boundary tests, cumulative-work refusal and the real daemon Node client lane |

<a id="concept-plan-scope"></a>
### Scope and Non-Goals

Technical depth: [Packaging](M8-technical.md#technical-plan-packaging).

Technical depth: [What M8 inherits from M7](M8-technical.md#technical-plan-inherited).

Technical depth: [Compatibility](M8-technical.md#technical-plan-compatibility).

**Scope.** The eight outcomes. M8 owns installation, home discovery,
configuration writers, service lifecycle, conversation attachment and store
readiness. It retains the maintainer-directed 2026-09-26 ADR 0028 transfer
bound repair as outcome 8. Operator and developer documentation accompanies
every outcome, with copyable commands and semantic review.

M8 inherits M7's instruction-bearing roles, model switching,
environment-reference-only credential custody and bounded helpers unchanged.
It introduces no second provider, role or configuration schema, and a home's
existence never turns the ephemeral `ask` into durable operation.

An attached conversation works in the workspace its service was started with.
The service is the host: it alone chooses workspace, policy, provider binding
and credentials, and a connected terminal can name none of them. One home
serves one state root and one workspace; another workspace is another service
on another root. Attachment is local, over the daemon's existing Unix-domain
socket, for the same operating-system user.

**Non-goals.**

- **Store:** no engine implementation, engine selection, migration or capacity
  change. The 256 MiB log ceiling and its retirement procedure remain.
- **Recovery:** no per-session quarantine. A root with an unreadable session
  history is recovered by restoring a backup, as M7 states.
- **Credentials:** no file, keychain or command credential source, and no live
  rotation or configuration reload.
- **Helpers:** no parallel helpers within one parent conversation, no writable
  helpers and no nested children.
- **Attachment:** no network transport, no cross-user attachment and no
  multi-workspace service.
- **Service management:** no launchd or systemd unit installation.
- **Surface:** no full-screen terminal interface and no MCP.
- **Other rungs:** no extension activation, no protocol or API freeze.
- **Publication:** no package publication, name clearance or release version
  is authorized by this plan.

Any added capability needs its own scoped acceptance decision.

### Design Decisions

Technical depth: [Prerequisites](M8-technical.md#technical-plan-prerequisites).

| Decision | Work it governs |
| --- | --- |
| [ADR 0037](../adr/0037-host-configuration-and-path-discovery.md#concept) | Installed discovery, configuration writers and lifecycle commands, with a narrow ADR 0003 home-reading amendment, reusing ADR 0049 |
| [ADR 0038](../adr/0038-installed-distribution-and-release-artifact.md#concept) | Artifact, manifest, native linkage, supported hosts, install and rollback proof |
| [ADR 0050](../adr/0050-daemon-attached-conversation.md#concept) | The conversation as a daemon client, and the service as the host that reads configuration |
| [ADR 0051](../adr/0051-store-readiness-marker-backup-and-restore.md#concept) | Format marker, reader boundary, backup and restore, separated from the engine decision |

Accepted [ADR 0028](../adr/0028-bounded-artifact-retrieval.md#concept)
constrains outcome 8 with its existing limits and refusal contract.

**Opening instruction, 2026-09-30.** The maintainer directed that M8 open from
the [zoom-out analysis](../developer/agent-context-map.md#disposition-m8-opening-2026-09-30)
made as M7 was accepted. That instruction opens this pair for planning and
review. It accepts none of the proposals below.

**Proposals the analysis made, for the maintainer to select or change.** Each
is a reversible author proposal until this plan is accepted.

| # | Question | Proposal in this plan |
| --- | --- | --- |
| P1 | Does the conversation attach to the service in M8? | Yes, as outcome 5. Without it the installed demonstration cannot show detach and reconnect with the conversation M7 built |
| P2 | Where does the store engine decision belong? | With M9. ADR 0051 takes the marker, reader boundary, backup and restore; ADR 0036 keeps the engine, its measured selection and migration |
| P3 | What is the rollback predecessor, given that no installed release exists? | The closed M7 source build. M8 proves upgrade from M7 roots and rollback by restoring the pre-upgrade backup for that build. Upgrade between two installed releases is claimed by the release after M8 |
| P4 | How does a service started on demand get credentials? | Environment references only. It inherits the environment of the command that starts it, and that command refuses by name before starting when a configured reference is absent |
| P5 | Is attachment implicit when a home exists? | No. A conversation attaches only when the command asks for the service; the foreground conversation remains and refuses a root a service holds |
| P6 | How is an unreadable session history recovered? | By restore from backup, with the diagnostic command naming the session. No quarantine |

**Choices only the maintainer can make before acceptance.**

| # | Choice | What is known |
| --- | --- | --- |
| C1 | Installed version label | Not selected. M6's released `0.3.0` is a historical source identity and M7 has selected no version |
| C2 | Supported hosts and minimum base systems | ADR 0038 proposes macOS on Apple silicon and Linux on x86-64, with the Linux base measured at glibc 2.35 from an Ubuntu 22.04 container; the macOS minimum is fixed from its build environment |
| C3 | macOS download path | Signing and notarization under a developer account, or a documented quarantine-removal step after manifest verification. This plan authorizes no publication, so the documented step is sufficient for its proof; notarization can join a publication decision |

Before acceptance, the four Proposed pairs are reconciled with the exact closed
M7 baseline, and every cell they mark as fixed at acceptance is filled.

<a id="concept-plan-verification"></a>
### How Each Outcome Is Verified

Technical depth: [Evidence mapping](M8-technical.md#technical-plan-evidence).

Extend the existing conformance, command, process and release lanes. The
installed lane runs on each claimed clean platform without a toolchain or any
library the archive promises to carry. Complete outputs, archive manifests and
digests are retained outside the repository. No real-provider, install or
rollback proof is replaced by mocked results. The engine selection experiment
is not M8 evidence.

<a id="concept-plan-rollout"></a>
### Rollout and Compatibility

Technical depth: [Compatibility](M8-technical.md#technical-plan-compatibility).

Technical depth: [Migration and rollback](M8-technical.md#technical-plan-migration).

Storage container format, durable-record capabilities and binary version are
three separate things. An unchanged container does not mean an older binary
understands M7's configuration, checkpoint, maintenance, question or
host-ledger records. M8 proves exact reader combinations and never infers one
from the container.

An unsupported downgrade uses the pre-upgrade backup and the matching prior
build. Restoring that backup discards every later fact; it is not reopening a
newer root. The prior build is a source build with no installed layout and no
restore command, so the runbook restores with the candidate's tool into a
separate empty root and then opens that root with the prior build.

<a id="concept-plan-workstreams"></a>
## Workstreams

Technical depth: [Ownership and rejoin](M8-technical.md#technical-plan-ownership).

One integrator owns the launch, configuration and attachment rejoin. Packaging
and store readiness may proceed independently after their contracts settle,
each with its own writer worktree. The first rejoin is one installed workflow:
install, configure, start, converse, detach, reconnect and stop. Failure
matrices follow it.
