<a id="concept-plan-purpose"></a>
### Purpose

Technical depth: [Prerequisites and acceptance points](M7-technical.md#technical-plan-prerequisites).

Technical depth: [Comparison basis](M7-technical.md#technical-plan-comparison).

**M7 is the coding-agent proof.** Its product question is:

> Given a real coding problem, can Loopex work on it the way a person expects
> of a coding agent: remember the conversation, follow instructions the host
> wrote, keep going when the context fills, ask when it is unsure, hand a
> bounded piece of work to a helper, and finish the task?

Loopex already has the loop. Within one run the model calls tools, reads
their real output and is called again, with `read`, `write`, `edit` and `bash`
and declared bounds. What is missing sits around the loop:

| Capability | Today | M7 target |
| --- | --- | --- |
| Memory across prompts | Each prompt or follow-up starts a conversation holding only its own text | A new run sees the session's retained history |
| Instructions | One fixed three-sentence block compiled into core | The host composes instructions; core stages and digests them |
| Long tasks | A run that outgrows its context budget fails | Compaction of earlier runs' history keeps the session working; one run that outgrows the budget by itself still fails |
| Model control | One model per session; only an output limit is sent | Model and reasoning level are chosen per run |
| Questions | Only a host policy can ask the operator something | The model can ask a question and wait for the answer |
| Conversation surface | One-shot `ask`, then `resume` with flags | A line-oriented conversational command |
| Helpers | None | A host tool runs a bounded child session |
| Proof | Workflow tests of single tasks | A retained set of real coding tasks, completed end to end |

**Shape.** M7 retains seven workspace tool implementations, a short default
prompt, no plan mode and no todo tool. The accepted narrow amendment to both
vision files permits the question tool and an opt-in host helper tool. The
[accepted section 13.4 amendment](../developer/agent-context-map.md#disposition-m7-acceptance-2026-09-30)
also permits core's bounded continuation validation/accounting and retained
host-resolved descriptor while adapters interpret native provider data. It retains
the bans on a core scheduler, parallel helpers within one conversation and
writable helpers. The
maintainer accepted both paired amendments with M7 on 2026-09-30. The 2026-09-29 comparison is summarised in the
[technical companion](M7-technical.md#technical-plan-comparison).

<a id="concept-plan-scope"></a>
### Scope and Non-Goals

Technical depth: [Evidence obligations and mapping](M7-technical.md#technical-plan-evidence).

**Scope.** The nine outcomes, primarily in the durable profile. Ephemeral
embedding gains explicit startup options for host instructions and their
system-class ceiling, initial model/reasoning selection, named provider
credential references, an explicitly selected summarizer with maintenance
instructions, opt-in owner-managed tracing, and host-answered questions within
the one-shot `run/2` wrapper; the technical prerequisite table's ADR 0039 row
lists the additions. The maintainer
selected that addition on 2026-09-29. The released ephemeral `start_session/1`,
`ask/3`, `answer/3`, history and stop APIs already support multiple prompts.
M7 preserves them and extends their answer path for model questions. Each
one-shot `run/2` still owns and cleans up its single temporary session. One-shot `ask` continues to support unattended
callers; questions require an explicitly configured answer path. Operator and
developer documentation changes with each outcome. Branching, forking, lineage
merges and in-place tool-set/catalog changes remain future work; ordinary
prompts and promoted follow-ups are the M7 continuity path.

**Non-goals.**

- **Modes and planning aids:** no plan mode, no todo tool, no named agent
  types in core. Saved role names belong to host configuration.
- **Prompt engineering in core:** no per-model or per-provider prompt files,
  no learned or optimized prompts.
- **Secondary model calls:** no title generation or automatic model routing.
  Compaction and explicitly enabled bounded helpers are the only additional
  model-call workflows; the host explicitly selects the summarizer and may
  choose a different model for each helper role.
- **Scheduling:** no sub-agent scheduler, no parallel children within one parent
  conversation, no nested
  children, no model switching inside a run.
- **Surface:** no full-screen terminal interface.
- **Other rungs:** no installed distribution, automatic user/project
  configuration discovery, store engine or extension activation. No MCP.
- **Freezes:** no public-protocol or embedded-API freeze.

<a id="concept-plan-configuration"></a>
### Explicit configuration

Technical depth: [Configuration scope and remaining contract](M7-technical.md#technical-plan-configuration).

**Maintainer scope decision, 2026-09-29.** The maintainer selected option A:
CLI flags plus an explicitly selected config file for model, reasoning,
prompt files and bounds in M7. This brings a bounded part of the installed
operator's configuration work forward. That scope decision did not itself accept this plan or its
prerequisite ADRs.

The maintainer also requested tracing enablement and other command-line
controls. M7 includes a documented option inventory covering model/reasoning,
instructions, run/context bounds, tools/skills, workspace/state, output and
tracing. It identifies each command's supported options and the matching
config-file values, retaining existing option meanings where applicable.
ADR 0049 specifies the accepted command grammar and schema. These commands
are implementation obligations, not features already available in M6.

The host reads the selected file and passes resolved options inward.
Embedding callers continue to supply explicit options. Automatic discovery
of user or project configuration remains outside M7. System-prompt
replacement and appending use explicitly selected host content; project
instructions and skills retain their existing admission and provenance.

ADR 0049 owns the closed JSON schema, flag mapping, precedence, resume behavior
and validation. Proposed ADR 0037 now covers only successor discovery and
management over that foundation. It is not an M7 prerequisite.

**Summarizer decision, 2026-09-30.** The maintainer selected
[B: an explicit separate summarizer](../developer/agent-context-map.md#disposition-m7-maintenance-model-2026-09-30)
so always-on thinking models can remain conversation models. File
`maintenance.model` or `--compaction-model` selects the summarizer; it may equal
the conversation model but must support verified thinking-off maintenance.
No setting means compaction is unconfigured, with ordinary work still available.
Each episode retains its selection through restart. Existing summary spending,
source and request limits remain; helper sessions are not involved.

**Run-limit decision, 2026-09-29.** The maintainer selected options A and C
together: retain the current limits as documented starting values, and
require explicit run limits in the selected config file before a
conversation starts. The baseline is 16 turns, 10 minutes and 1,000,000
tokens per run. CLI flags may override configured values. Increases to the
recommended baseline require coding-task measurements and disposition;
the draft's 64-turn, 60-minute, 4,000,000-token defaults are not selected.
One-shot `ask` and core retain their existing defaults.

**Context-storage decision, 2026-09-29.** The maintainer selected option A:
M7 preserves the 65,536-byte serialized model-request record ceiling and
compacts against both byte and token limits. Content that cannot fit after
bounded compaction is refused explicitly. A larger model context window
does not enlarge the stored-request ceiling. On 2026-09-30 the maintainer
selected retained artifacts plus bounded excerpts for bulky tool results, with
explicit bounded retrieval through the existing read tool. M7 adds no
artifact-backed storage for whole model-request records. The maintainer selected
marked bounded excerpts when an eligible older group cannot fit the
summary source, retaining its complete originals and disclosing omissions in
later summaries. This covers large prompts, generated arguments and group
metadata; current input and the recent protected tail remain verbatim.
The maintainer also selected bounded provider continuation on 2026-09-30. Required thinking blocks
remain exact private data, count within the same request ceiling, and cannot
be replaced with tool-output excerpts or summaries.

The maintainer selected both interactive and piped chat on 2026-09-30. Both
use the same session contract, with explicit input ordering, question answers,
EOF and failure rules in ADR 0049.

Tracing uses the existing runtime-scoped observability contract. Operators
can enable it, select its level and scope, inspect its effective limits and
dropped-entry counts, and stop it with the owning host. Diagnostic output
stays separate from model answers and protocol output. Tracing does not
expose raw payloads or grant a client or model authority over the runtime.

<a id="concept-plan-specialization"></a>
### Specialized agents and the milestone boundary

Technical depth: [Pi research and scope mapping](M7-technical.md#technical-plan-specialization).

**Maintainer scope decision, 2026-09-29.** The maintainer selected option B:
serial helpers plus saved named roles and separate model choices per role.
M7 uses Loopex-native sessions with one opt-in read-only child at a time per
parent conversation, including unresolved cleanup across runs. The maintainer
[selected this scope](../developer/agent-context-map.md#disposition-m7-helper-concurrency-2026-09-30):
separate parent conversations may run helpers concurrently. There is no shared
runtime-wide helper slot or queue.
Repository investigation and code review provide two concrete role examples.
The parent remains responsible for edits and integration.

Roles live in the explicitly selected host configuration. The host resolves a
role into bounded instructions and exact model settings before it creates the
child. Core receives ordinary session configuration and gains no named agent
type or scheduler. Role selection cannot widen the host's policy or the
read-only child tool set. ADRs 0046 and 0049 specify the role schema and selection. Every enabled role
names its exact model; the parent-session catalog is retained across restart.

The maintainer selected option A for invocation: once helpers and their limits
are enabled, the parent may choose a host-enabled role and delegate
automatically within policy and budgets. M7 requires no additional operator
confirmation for every allowed delegation. The operator can inspect the
selected role, task, provider/model, child identity, outcome and usage.
Unknown or disabled roles refuse; model output cannot create another role or
change its authority.

**Delegation-budget decision, 2026-09-30.** The maintainer selected option A:
parent runs and delegation have separate explicit budgets, with combined
usage shown to the operator. The host enforces the delegation allowance and
each child's bounds; core's per-run token counter is unchanged. A parent
cannot obtain unbounded work by making repeated child calls.

ADR 0046 replaces parent-model inheritance with exact retained role settings
and a durable host allowance ledger. It does not introduce parallel children
within one parent conversation, nested children, a Pi dependency
or automatic routing between agents. The router keeps active job
classifications in a bounded table that reclaims capacity after settlement.
Late unclassified cancellation fences that job ID; only exhaustion of the separate
bounded tombstone table closes host helper admission until restart. Durable helper
bindings route historical receipts without a live active row. The ledger byte
ceiling can refuse before the configured maximum child count.

**Provider scope decision, 2026-09-29.** The maintainer selected option B:
multiple providers per runtime, with each role selecting its provider and
model through separate credential references. M7 therefore includes host
provider routing and validation of each role's resolved configuration. Raw
credentials do not belong in the role file, session history or diagnostics.
Each provider invocation preserves the credential custody and cleanup
contract of its durable or ephemeral profile.

The maintainer selected option A for credential sources: named environment
variable references only. M7 adds no credential-file reader, keychain
integration or credential-retrieval command. The host resolves the selected
reference through the applicable profile's custody path; the config file
contains no API-key value.

ADR 0034's baseline fixes one model configuration and credential binding per
runtime. Accepted ADR 0048 amends that rule narrowly with host-owned selection
across multiple providers.
It also permits explicitly named ephemeral credential variables without
changing that profile's audience or cleanup guarantees.

The proof includes a parent and a serial helper using different providers.
The maintainer also selected option B for existing conversations: M7 permits
provider changes between runs while preserving history. Each change is an
explicit committed configuration decision. In-flight requests retain their
recorded configuration, and unavailable credentials or incompatible settings
refuse instead of silently selecting another provider. A real A→B→A workflow
proves history conversion within one session in addition to the child proof.

| Work | Recommended placement |
| --- | --- |
| Host instructions, project admission, reusable skills, saved named roles and serial read-only helpers with per-role models | M7, through outcomes 2, 4, 6 and 7, selected by the maintainer |
| Model, reasoning, prompt files, bounds and tracing through flags and an explicit config file | M7, within outcomes 2, 4 and 6, selected by the maintainer |
| Installed command, automatic home/configuration discovery, backup/restore, readiness and lifecycle runbooks | Installed durable operator successor, M8 draft; explicit configuration moves into M7 |
| Store engine, migration and capacity guarantees | Store successor, M9 draft |
| Trusted contribution loading and rollback | Extension runtime successor, M10 draft |
| Parallel workers within one parent conversation, writable workers, shared task queues and automatic multi-agent handoffs | A separately proposed host capability after M7 evidence demonstrates the need |
| Launching Pi processes or mapping Pi RPC/session formats | Separately scoped interoperability work; no commitment in M7 |

The later host capability does not automatically belong to the extension
milestone. Concurrent writers need workspace ownership, aggregate budgets,
cancellation, recovery and integration rules whether or not extensions are
used. Human-run terminals may already share a runtime's sessions, but terminal
panes and conversation branches supply no workspace isolation.

<a id="concept-plan-operator-validation"></a>
### Operator validation

Technical depth: [Scenario steps and evidence](M7-technical.md#technical-plan-operator-validation).

Outcome 9 is a product deliverable. A reader should be able to take a named
build, follow the instructions in a disposable workspace, and decide whether
the promised behavior works without reading implementation code.

The runbook covers setup and explicit configuration, a multi-prompt repair, instruction admission,
steering and follow-up, questions, compaction, model changes, bounded helpers,
policy refusal, cancellation, restart, tracing and the upgrade/rollback
fixture procedure. Each scenario distinguishes the
operator's observations from invariants established by automated fault tests.
The coding tasks and the runbook share fixtures and acceptance checks. The
same prescribed task execution supplies both coding-task and operator evidence;
collecting the final results does not rerun that task. Separate restart,
ephemeral and failure cases retain their own prescribed executions. All
required cases and their evidence owners are fixed before provider work begins.
The maintainer selected agent-run approved tests plus independent harness
reruns on 2026-09-30. The fixture grants only its named test command through a controlled
executable path; the default shell policy is unchanged.

**Demonstration decision, 2026-09-30.** The maintainer selected option C:
the repeatable fixtures plus a task in another real repository they choose.
Record the repository, starting commit, bounded task, allowed changes and
objective acceptance command before the demonstration. Run in a disposable
checkout and retain its diff and verification output. The external repository
and task are pending selection. The maintainer explicitly deferred choosing
them until testing, so an unnamed target does not block plan acceptance.
Choose and record the target and pass criteria before its demonstration
attempt. The demonstration does not authorize merging or publishing changes
there.

**Maintainer scope decision, 2026-09-29.** The maintainer selected option A:
the maintainer or a named operator runs the core workflow before closure,
while automated tests cover the full failure matrix. The attended workflow
covers conversation and its key recovery paths. Automated transcripts alone
do not establish that an operator followed the instructions. The technical
companion fixes the mandatory attended subset. The fixed manifest declares case keys,
owners and oracles; immutable execution records hold the later run identities
and results. Required attended cases run once inside the full logical closure matrix
with a named human. Each case reports pass, product failure, model nonconformance,
unavailable evidence or a reviewed provider-side outage. A missed required model action still blocks closure;
a new commit alone does not authorize retrying it. A model miss goes to the
maintainer, who keeps the case pending a causal product correction, approves a
revised pinned model or witness for a new candidate, or proposes a named scope
or evidence-rule amendment. A product failure with no assertion-preserving
correction, and lost post-dispatch evidence with no reviewed causal fix, take
that same amendment route; lost evidence otherwise needs a reviewed causal fix
and a new candidate. None of these grants a waiver or an accepted limitation. The closure
record identifies who ran each required step and its objective result. Missing
or unavailable required evidence blocks closure. The implementation candidate
may carry Proved rows with the repository-sanctioned Pending exact-run/review
scaffold slots; those slots are filled only from that candidate's evidence.

**Recorded maintainer decisions.**

- **Vision amendment.** The maintainer authorized drafting a narrow change to
  both vision files on 2026-09-30. It explicitly permits question and opt-in
  serial read-only helper tools alongside seven workspace tools, and the authorized
  bounded continuation/mapping amendment in section 13.4 for the shared
  configuration, projection and maintenance contracts. Both amendments gate the
  whole coordinated packet and its outcome/proof obligations. Their exact paired
  bytes were accepted with the packet; the evidence obligations remain.
- **Accepted clauses amended.** The ADRs name context projection/artifact reads,
  instruction budgets, maintenance, configuration/genesis, interactions, immutable
  session selection, absolute deadlines and provider bindings. The technical
  prerequisite table maps each accepted clause; unrelated guarantees remain.
- **Outage verdict.** The maintainer selected a separately reviewed environment-failure
  verdict for fully recorded provider-side outages after the case is recorded started.
  Retain the failed attempt and permit the affected case only on a new candidate;
  model misses and lost recordings retain their stricter disposition rules. The
  class is provider-side only: transport failure to the provider, provider
  server errors and provider-side timeout. Rate limits, quota exhaustion and
  loss of the runner's own network are operator prerequisites, not outages. A
  new candidate always runs its own complete closure matrix.
- **One logical closure matrix.** Plan acceptance lets a matrix that stopped
  before a case's first dispatch continue on the same commit through a
  mandatory hash-chained attempts index. No started case or completed lane runs
  again; a resumed invocation rebuilds the fresh-source extraction only as a
  prerequisite, never as evidence. Any failure of a started case stops the matrix, which then cannot
  resume. This stop rule is a reversible author choice the maintainer did not
  select. Resumption changes what "the release check runs once" means for M7
  explicitly. A pre-merge lane that stopped before a case's dispatch is suspended
  and may continue on the same commit. A follow-up commit records the index head
  under Progress and Evidence once an indexed lane or a stopped matrix has
  ended, or a lane has been abandoned because its prerequisite repair needs a
  commit; an ended lane does not run again on that commit. The attempts index is
  a trusted single-writer procedure, not distributed fencing. A lost index stops dispatch, and only a recorded maintainer
  disposition can start a successor campaign on a new candidate. A reviewed
  outage in a pre-merge lane is recorded in the index, and the lane runs again
  only on a later commit.
- **Ordinary thinking support.** The maintainer selected ordinary availability
  for the chosen model/level cells at M7 closure. Register them in the tested
  implementation after deterministic conformance and require their counted live
  witnesses before closure; no later registration edit or calibration run. After
  a cut tool run, the witness proves the provider accepts the next request and,
  on each cell that requires continuation, that thinking resumes on the exchange
  after it; the two cells without thinking stay without it. Provider B's
  thinking-off summarizer is one further registered row, pinned before dispatch.
- **Helper history at startup.** The maintainer selected a fixed 60-second,
  resumable classification bound per durable host start, with no configuration
  key. The accepted packet adopts the author's reversible repair choice that
  the durable host admits no session work until that classification
  completes, over later starts or for two recorded cases only under a resident
  host, and that one unreadable session history keeps it closed until the root
  is restored from backup.
- **Rollback proof.** Plan acceptance retires the v0.2.0-to-current-candidate
  pairing. The frozen v0.2.0↔v0.3.0 pair preserves the historical assertions;
  v0.3.0↔M7 proves the new reader/restore boundary. It claims no v0.2.0 reading
  of the candidate and changes what that check proves explicitly.
- **Reasoning compatibility.** The maintainer selected bounded provider
  continuation in M7. ADR 0044 defines exact retention, privacy, recovery and
  model-switch rules for selected Claude thinking modes. The maintainer accepted
  these contracts with the complete packet; implementation and integrated
  evidence remain required.
- **Thinking capacity.** The maintainer selected
  [local references and an initial reserve](../developer/agent-context-map.md#disposition-m7-thinking-capacity-2026-09-30).
  ADR 0044 stores canonical text/tool arguments once per owning representation,
  reconstructs exact provider blocks and charges their full expanded size.
  Before a thinking exchange, earlier history may compact and eligible excerpts
  may shorten to leave room. The existing request and private-data ceilings
  remain; the reserve guarantees no fixed number of tool rounds.
- **Thinking delivery.** The maintainer selected
  [live streaming](../developer/agent-context-map.md#disposition-m7-thinking-streaming-2026-09-30).
  Preserve live answer text on the existing streaming path, with bounded
  complete-block assembly and interruption/recovery proof. Partial text cannot
  authorize a tool. The existing buffered ephemeral path stays buffered.
- **Reasoning visibility.** The maintainer selected
  [verified provider summaries](../developer/agent-context-map.md#disposition-m7-reasoning-summary-2026-09-30)
  through existing transient reasoning progress. Exact provider/model modes
  determine eligibility; unverified thinking, signatures and redacted data stay
  private. A summary is distinct from the final answer and durable history.
- **Requested file ranges.** The maintainer selected
  [up to 4 KiB per explicit read](../developer/agent-context-map.md#disposition-m7-artifact-range-size-2026-09-30).
  A larger bounded result reduces retrieval calls; unsolicited excerpts keep
  their smaller limit and the complete request still cannot exceed 64 KiB.
- **Older inline results.** The maintainer selected
  [reuse when the complete request fits](../developer/agent-context-map.md#disposition-m7-legacy-inline-2026-09-30).
  Old frozen tool generations keep exact saved inline content without acquiring
  artifact access. This exception preserves request limits and prior truncation
  or spill notices; it cannot recover missing bytes.
- **Helper recovery.** The maintainer selected stop-only recovery after the
  helper manager crashes: recover completed results and stop unfinished work.
  ADR 0046 defines the durable fence and truthful cleanup evidence; automatic
  unfinished-helper resumption is outside M7.
- **Oversized summary input.** The maintainer selected
  [marked bounded excerpts](../developer/agent-context-map.md#disposition-m7-compaction-excerpts-2026-09-30)
  while retaining complete originals. ADR 0043 defines the complete-prefix
  preference, whole-unit excerpt fallback, deterministic byte allocation and
  inherited omission flag. The choice is incorporated in the accepted packet;
  implementation and integrated evidence remain required. The small-prefix rule
  that summarizes a short unit together with an oversized one, and the recorded
  limitation for a lone short unit before the protected tail, are a reversible
  author choice the maintainer did not select. Compaction during a run covers
  only history from before that run.
- **Protocol compatibility.** Both foreground and daemon contracts gain the
  same session capabilities while preserving their distinct authority rules.
  The maintainer selected
