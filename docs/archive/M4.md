## Normative Concept Envelope

<a id="concept-plan-purpose"></a>
### Purpose

Let a separate program operate the coding session M2 provides without linking
Elixir internals or creating another loop. A client launches one foreground
Loopex app-server process, initializes an exact experimental protocol, starts or
resumes a durable session, submits the same explicit session commands, watches
durable events and transient progress, answers a policy question, and retrieves
bounded artifacts over strict stdio JSONL.

M4 is a headless application boundary, not a service milestone. The app-server
owns framing, correlation, and bounded delivery; the public `Loopex` facade and
one serial session owner retain commands, durability, policy, and recovery. A
process restart may resume durable state, but no session stays resident because
the app-server disappeared and no second client takes over a live attachment.

This draft is retained, not opened. It was written as the M3 lookahead against
integrated M2 governance at `main@cf7716504cdaa5873b8d6e2f7e888174b6b6dd6f`; the
maintainer then made kernel consolidation M3 and moved this milestone to M4, so
it carries no lifecycle state and authorizes nothing. Opening it means moving
this triple into `docs/plans`, giving it an `Open` register row, refreshing it
onto the then-current closed product base, re-proving every inherited gate
green, re-proving M4's distinct red on that base, and receiving a fresh
exact-SHA review.

product, not another outcome. One non-Elixir client drives the shipped
app-server through a genuine coding task on the real provider and executor
paths, observes progress, handles project-resource trust, retrieves one spilled
artifact, resolves one deferred policy interaction, and verifies the settled

credential presence and a provider-declared response identifier do not by
themselves prove a network call; closure review checks the provider account

<a id="concept-plan-scope"></a>
### Scope

Product code intended to survive the milestone: transport-neutral public DTOs,
validation, schema identity, and vectors in `loopex_protocol`; durable interaction
state and policy resumption in `loopex`; one new `loopex_app_server` client
application; one strict foreground stdio JSONL mapping; bounded snapshot,
event, progress, trust, artifact, and interaction projections; and executable
Elixir, Python, and JavaScript reference clients.

The app-server uses the shipped M2 reference composition and public facade. It
does not depend on the human command application and does not reach a concrete
Store, coordinator, model, executor, journal, or cursor internal. It takes no
external production dependency at all: the raised bootstrap floor puts Elixir's
standard-library `JSON` module inside the toolchain, so the app-server encodes
and decodes protocol frames with it and neither core nor `loopex_protocol`
acquires a codec dependency.

The foreground host takes a policy implementation plus bounded policy identity
and revision as required trusted launch configuration and ships no implicit
policy. Protocol input cannot name a module or profile. The deterministic gate
policy is a gate-owned host fixture loaded at process start, not a wire option or
product default.

The source-tree `VERSION` becomes `0.1.0` only at M4 closure. The protocol
generation and schema identity are separate experimental identities. M4 creates
no Git tag, Hex package, archive, publication, release, or compatibility freeze.

Technical depth: [Prerequisites and acceptance points](M4-technical.md#technical-plan-prerequisites).

Three obligations carry into `M4` from `M2`'s closure and are in scope here.

The first is decided. `M2` closed with the requirement that existing gates stay
green met by a maintainer waiver and one retained run, not by a check, because
no repository entrypoint enforces that rule. `M4` owns the durable answer: a
governed closed-gate aggregate whose **own invocation is structurally verified**,
because an aggregate each successor gate is merely expected to call reproduces
that blind spot one level up. A closed gate that cannot pass then blocks every
successor, which is a designed consequence here rather than a surprise
discovered during closure.

The second is not decided and is owed before this plan pair is accepted. The
bootstrap runtime floor is Erlang/OTP 26 with Elixir 1.17, and today that is a
development and validation target rather than a released support statement. Once
`Loopex` makes its first support statement the floor becomes a promise to
embedders and raising it becomes a breaking change with a migration. `M4` is
therefore the cheap moment to decide it, and the decision is which hosts
`Loopex` expects to be embedded into — not what a capture lane costs. Raising it
is an amendment to accepted ADR 0002; the floor and current pairs must remain
distinct, because a floor that tracks the current release is not a floor.

The third is decided and is a debt rather than a question. Accepted ADR 0009
requires the cleanup grace period to be a declared *session* configuration value
reported in the run's terminal outcome evidence, so an operator can tell a clean
cooperative stop from a forced kill that was confirmed and from a termination
that could not be confirmed at all. `M2` ships it as a start option of the local
executor, written into every receipt and readable back from the running executor,
and there it stops: the shipped composition neither accepts nor forwards it, the
coordinator's receipt reconstruction does not carry it, and no terminal reports
it. The same is true of the program that executor asks whether a process group
still has members, which `M2` also made a start option after finding that a
hardcoded `/bin/ps` reports every command unproven on an image that ships `ps`
elsewhere.

`M2`'s obligation was narrowed to what its code performs and the shortfall was
recorded as an approved deferral rather than left implied, on the maintainer's
disposition of 2026-08-28. A narrowed plan obligation does not narrow an accepted
ADR: the ADR sentence still stands unmet, and `M4` owns closing it — threading
both values through the shipped composition, carrying them across the coordinator
boundary, and projecting the period onto the run's terminal evidence, together
with whatever amendment to ADR 0009 the final shape requires. It is named here
because a deferral that lives only in the milestone that deferred it is a loss
with a better name.

<a id="concept-plan-non-goals"></a>
### Non-Goals

M4 does not ship or claim a daemon, background service, Unix socket, TCP, HTTP,
WebSocket, network authentication, concurrent independent clients, controller
and observer roles, leases, takeover, fencing between clients, fairness,
residency, eviction, daemon Store selection or migration, live cancellation from
another process, or attachment survival across app-server process death. Those
need the M4 service and concurrency evidence.

Also excluded are session fork/branch, compaction, model switching, ACP,
extension activation, isolated or remote hands, a generic transport behavior, a
generic composition toolkit, public packaging, and a compatibility freeze. M4
exposes M2's fixed project-resource stage; it does not trigger the later context-
pipeline decision for registered providers, transformers, selectors, or
observers.

## Workstreams

| Workstream | Mutable implementation ownership | Rejoin condition |
| --- | --- | --- |
| A — Protocol contract | `apps/loopex_protocol`, gate-owned schemas and vectors | DTO validation, identity ownership, exact schema digest, and malformed-value vectors are green without a runtime or JSON dependency |
| B — Durable interaction and facade completion | `apps/loopex` | Interaction reducer, recovery, policy resumption, public events, and required facade operations are green with no transport knowledge |
| C — Foreground app-server | `apps/loopex_app_server` | Stdio framing, correlation, bounded writer, facade-only mapping, and stdout purity are green against A and B |
| D — Independent consumers and closure | sample clients, documentation, version and retained evidence | All three clients execute, the real demonstration passes, inherited gate generations are separately accepted, and closure documentation is current |

Rejoin order is A → B → C → D. Workstreams may explore independently, but C
does not invent temporary interaction state or a private Store path while B is
incomplete, and D does not change the protocol to accommodate one client.
