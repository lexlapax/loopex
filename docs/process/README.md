# Development Process

How Loopex itself is developed: which checks a change needs, how a milestone is
planned, run, closed and released, how documentation is shaped, and where to
read for a given task. Part of the [documentation index](../README.md).

| Document | Purpose |
| --- | --- |
| [Verification](verification.md#concept) · [technical](verification-technical.md#technical-depth) | The rule book for checking work: three stages with one question each, how a changed boundary selects its checks, the rules that keep checks honest, and the measured speed plan; then what each stage runs, the repository check entrypoints, where each boundary's checks live and which tests prove each product claim, and the measurements. |
| [Milestones](milestones.md#concept) · [technical](milestones-technical.md#technical-depth) | How to plan, run, close and release a milestone: the plan pair, small reviewed merges, the documentation correctness review, the two-commit closure and the pre-tag proofs; then the exact plan sections, register row, closure commands, confinement rule and tag. |
| [Development charter](development-charter.md#concept) · [technical](development-charter-technical.md#technical-depth) | Clarity before mechanism: the two-depth documentation pairs, traceable links, report and decision-packet form, capability routing, proportional documentation, portable enforcement, and how the charter itself changes. |
| [Agent context map](agent-context-map.md) | Task-oriented routing into Concept first and exact Technical depth second, current client facts and capability mappings, and the indexed record of maintainer dispositions. |

The verification, milestone and charter documents are Concept and Technical
depth pairs changed and reviewed as one authority. The context map is a routing
and decision record; it is deliberately unpaired and may link both depths.
